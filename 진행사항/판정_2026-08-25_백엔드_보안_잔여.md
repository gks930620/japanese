## 사실 정정 — `username` 노출은 **실재한다** (C-1)

계정 감사에 대해 "`/api/community`가 비로그인에 `NOT_AUTHENTICATED`를 준다"는 반증이 제기됐다.
**그 경로는 오타다.** 실제 매핑은 `/api/communities`(복수)이고, 단수 경로는 매핑이 없어 화이트리스트 밖 → 401이 나온 것이다.

라이브 재현(로컬 8083, **비로그인**):

```
GET /api/community          -> 401  (매핑 없음 — 이 응답이 반증의 근거였다)
GET /api/communities?size=1 -> 200  {"userId":6,"username":"user6","nickname":"박서준", ...}
GET /api/communities/1/comments?size=1 -> 200  {"userId":15,"username":"user15","nickname":"하준혁", ...}
```

`SecurityConfig`가 `GET /api/communities`·`/api/communities/*`·`/api/communities/*/comments`를 **명시적으로 permitAll**한다.
따라서 **감사의 지적이 옳고, 반증은 경로 오타에서 비롯됐다.** 음성 결과로 정정하지 않는다.

## 근거 상세 — 결정이 갈린 지점만

### A. 토큰 (A-1 ~ A-5)

**A-1 `jti`를 넣는다 — access·refresh 둘 다.**
JWT의 `iat`·`exp`는 **초 단위**로 직렬화되므로, 같은 사용자가 같은 초에 두 번 로그인하면 클레임이 완전히 같아
**서명까지 같은 문자열**이 나온다. 라이브 확인: 동시 로그인 6건이 전부 동일한 refresh 토큰을 돌려받았다.

피해는 추상적이지 않다. `PasswordChangeApiIntegrationTest.password_change_kills_tokens_issued_before_it`은

```java
Tokens otherDevice = loginDefaultUser();
Tokens thisDevice  = loginDefaultUser();
```

로 **"다른 기기 2대"를 만들려 하는데, 같은 초에 실행되면 두 변수는 같은 토큰**이다.
테스트는 통과하지만(`tv`가 사용자 단위라 결과가 같다) **검증하려던 시나리오가 구성되지 않는다.**
`refresh_entity.token`에 UNIQUE가 걸려 있어 저장 경합 시 제약 위반 여지도 남는다.

> access에도 넣는 이유: 서버는 무상태 검증이라 `jti`가 필요 없지만, **두 세션을 구분할 수 없으면 테스트도 사고 조사도 못 한다.**
> "서버가 안 쓰니 불필요"는 위 테스트가 반증한다.

**A-2 `tv` 없는 토큰을 더 이상 받아 주지 않는다.**
`getTokenVersion`의 "없으면 0" 은 *이 기능 이전에 발급된 토큰* 과의 호환 장치다.
그런데 **이 제품은 배포된 적이 없다**(`진행사항/README.md` — 배포 ❌). 밖에 나가 있는 구토큰이 **0개**이므로 호환 대상이 존재하지 않는다.
호환 코드는 공짜가 아니다 — `tv`가 없는 토큰을 유효로 보는 경로가 남아 있는 한, 그 경로가 무엇을 통과시키는지 매번 따져야 한다.
**없으면 무효**로 바꾸고, 프론트가 갱신을 시도하도록 `TOKEN_EXPIRED`로 답한다(04 §4의 갱신 배선과 같은 코드).

**A-3 리프레시에는 `tv`를 싣지 않는다(현행 유지).**
리프레시는 **DB에 행이 있다**. 폐기 수단이 이미 있는데(행 삭제) 클레임을 하나 더 두면 같은 사실이 두 곳에 생긴다(08 C-7).
`tv`는 애초에 *무상태라서 폐기 목록을 둘 수 없는* access를 위한 장치다 — 상태가 있는 쪽에 같은 장치를 복제하는 것은 설계 후퇴다.
**다만 그 폐기가 실제로 동작하는지 아무도 검증하지 않았다** → A-4.

**A-5 회전×비밀번호 변경 경합은 한계로 기록한다.**
`rotate()`가 "행 조회 → 삭제 → 신규 저장"인데, 비밀번호 변경의 `deleteByUserId` 직후에 신규 저장이 끼어들면
**삭제된 줄 알았던 세션이 새 행으로 되살아난다.** 막으려면 `rotate()`에서 사용자 행을 잠가야 하는데(08 B-11과 같은 방식),
그러면 **모든 토큰 갱신이 계정 쓰기와 직렬화**된다 — 갱신은 30분마다 전 사용자가 타는 경로다.
재현 조건(탈취된 리프레시 + 같은 순간의 비밀번호 변경)에 비해 상시 비용이 크고, 결정적 테스트도 불가능하다. **지금은 감수한다.**

### B. 로그인 시도 제한 (B-1) — 계약 명세

라이브러리를 넣지 않는다(bucket4j·resilience4j 등). 인메모리 카운터로 충분하고, 이 저장소에는 같은 성격의 선례가 있다
(`InMemoryAuthorizationRequestRepository` — 5분 만료 + 다중화 시 Redis TODO).

| 항목 | 값 | 근거 |
|---|---|---|
| 키 | **username 단위** | IP 단위는 NAT·모바일에서 무고한 사용자를 함께 막는다 |
| 임계 | **연속 실패 5회** | 사람의 오타 여유(3~4회)보다 크고, 자동 시도에는 충분히 낮다 |
| 차단 | **15분**, 그 사이 요청은 **비밀번호가 맞아도 429** | "맞으면 통과"면 제한이 아니다 |
| 해제 | 창 만료 **또는 성공 로그인 시 카운터 리셋** | 오타 낸 사용자가 다음 로그인부터 정상으로 돌아와야 한다 |
| 응답 | `429` + `errorCode: TOO_MANY_LOGIN_ATTEMPTS` | 04 §1-2 표에 추가한다(senior-dev) |
| 한계 | 인스턴스별 카운터 | 지금은 단일 인스턴스다. 다중화 시 Redis — `InMemoryAuthorizationRequestRepository`와 같은 시점에 함께 옮긴다 |

**"비밀번호를 4자로 둔 것"은 건드리지 않는다**(B-2) — 사용자 결정이다.
다만 시도 제한은 그 결정의 **대가를 줄이는 조치**이지 상쇄가 아니다. 근본 해법은 B-3(운영에서 로컬 가입을 닫는 것)이고, 그건 기획 결정이다.

### C. `username` 노출 (C-1) — 계약 변경 명세

**공개 응답에서 `username`을 뺀다.** 대상: `CommunityDTO`, `CommentDTO`(둘 다 비로그인 GET으로 나간다).

- 화면은 이미 `nickname`을 우선 표시한다(`{post.nickname || post.username}`) → 표시에는 영향이 없다.
- **소유자 판정만 바꾸면 된다**: 지금 프론트는 `post.username === user.username`으로 판정하는데,
  응답에 이미 `userId`가 있고 `/api/users/me`가 `id`를 준다 → `post.userId === user.id`로 바꾼다.
  (08 F-11은 "작성자 판정이 **id 기준**"이라고 이미 적어 두었다 — **문서가 맞고 코드가 어긋나 있던 것**이다.)
- 서버 인가는 그대로다(`isWrittenBy(username)`는 토큰 주체로 서버에서 판정한다).

### D. 범위 밖 페이지 (D-1)

**동작은 바꾸지 않는다.** 08 B-3이 이미 "서버가 0으로 보정하고 응답 `page`에 실제 번호를 담는다"로 결정했고,
라이브 응답(`page=99` → `page: 0`)이 그 결정과 정확히 일치한다. 프론트는 **응답의 `page`만 신뢰**하면 된다.

문제는 **04에 이 규칙이 없어서** 프론트가 "요청한 페이지와 다른 데이터가 왔다"를 결함으로 읽은 것이다.
→ `설계/04` §1(공통 규약)에 페이징 규칙을 명시한다. 빈 배열을 주는 대안은 채택하지 않는다:
"마지막 페이지에서 삭제가 일어나 페이지가 줄어든 경우" 사용자는 **빈 화면이 아니라 목록**을 봐야 한다.

## ⚠️ 테스트를 쓰다가 드러난 것 — `jti` 부재가 **계약을 실제로 깬다** (A-1 격상)

A-1을 "테스트 시나리오가 구성되지 않는다"로 적었는데, 테스트를 돌려 보니 **그보다 나쁘다.**

```
RefreshRevocationContractIntegrationTest
  a_refresh_token_issued_before_a_password_change_is_discarded  ->  Status expected:<401> but was:<200>
```

**비밀번호를 바꿨는데 그 이전에 발급된 리프레시 토큰이 그대로 살아 있다** — AC-A-28("다른 기기가 즉시 풀린다")이 깨진다.

**원인**: `AccountService.changePassword`는 ① 옛 리프레시 행을 전부 삭제하고 ② **새 리프레시를 발급·저장**한다.
그런데 `jti`가 없어 `createRefreshToken(username)`은 같은 초에 **바이트 단위로 같은 문자열**을 만든다.
→ ②가 저장하는 "새 토큰"이 ①이 지운 옛 토큰과 **같은 값**이라, 결과적으로 **옛 토큰이 되살아난다.**

**재현 조건은 "같은 초"다.** 라이브(로컬 8083)에서 로그인과 비밀번호 변경을 1초 이상 간격으로 실행하면
정상적으로 `401 TOKEN_DISCARDED`가 나온다 — 즉 **실사용에서 늘 터지는 결함은 아니다.**
그러나 두 동작이 같은 초에 겹치는 것은 얼마든지 가능하고(스크립트·자동화·빠른 조작), **`jti` 하나로 원천 제거된다.**

> 판정 변경 없음(A-1 = 고친다). **근거만 강해졌다** — "테스트가 시나리오를 못 만든다"가 아니라 **"계약이 깨진다"**가 이유다.
> A-3(리프레시에 `tv`를 싣지 않는다)도 그대로다: 이 결함의 원인은 `tv` 부재가 아니라 **토큰 값이 유일하지 않은 것**이다.

## §후속 — `설계/08_결정기록.md`에 남길 문장 (다른 세션 소유라 senior-dev가 직접 쓰지 않았다)

아래 5건은 **결정과 그 근거**라 08에 들어가야 한다. 코디네이터가 넘겨 주면 된다.

1. **B-11 보강**: 사용자 행 잠금의 대상은 "사용자 소유 데이터"였는데, **회원가입은 그 밖에 있었다**.
   `existsByUsername` → `save`의 check-then-insert가 남아 있어 동시 가입이 500이 될 수 있었다(판정 M6).
   결론: **제약 위반은 409로 번역한다**(`DataIntegrityViolationException` 핸들러) — 잠금은 사용자 데이터에만 쓴다.
2. **F-11 정정**: "작성자 판정은 id 기준"이라고 적혀 있지만 **프론트는 `username`으로 비교하고 있었다**.
   공개 응답에서 `username`을 제거하면서 판정을 `userId`로 옮겼다 — **문서가 맞고 코드가 어긋나 있던 사례**다.
3. **토큰 식별자(jti)**: 같은 초에 발급된 토큰이 바이트 단위로 같아 **비밀번호 변경이 옛 리프레시를 되살리는** 결함이 있었다
   (삭제 후 재발급이 같은 문자열이라 결과적으로 부활). `jti` 하나로 원천 제거. **토큰의 유일성은 시각이 아니라 식별자로 보장한다.**
   곁가지: 클레임이 늘면 토큰 길이도 는다 → `refresh_entity.token`을 512로. **JWT를 저장하는 컬럼은 여유를 둔다.**
4. **관대한 기본값에 유효기간을 둔다**: `tv` 없는 토큰을 0으로 보던 호환 처리는 **운영 배포 0회 = 호환 대상 0개**라 제거했다.
   호환 코드는 "언제 없앨지"를 함께 정하지 않으면 영원히 남는다.
5. **A-5(회전×비밀번호 변경 경합)는 감수한 위험이다**: 막으려면 토큰 갱신을 계정 쓰기와 직렬화해야 하는데
   갱신은 30분마다 전 사용자가 타는 경로다. 재현 조건이 좁고 결정적 테스트도 불가능해 **지금은 감수**한다(D 절 후보).
