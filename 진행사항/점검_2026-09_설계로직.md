## 1. 높음

### H1. 영어 문법을 보관함에 담을 수 있고, 담으면 **개수와 목록이 영원히 어긋난다** [실측]

**무엇이 이상한가**
`PUT /api/bookmarks/grammar/{영어 문법 id}` 가 **200으로 저장된다.** 그 뒤 개수 API는 1을 말하고 목록 API는 0건을 준다.

로컬 8083에서 신규 계정으로 재현한 그대로:

```
PUT  /api/bookmarks/grammar/9001   → 200 {"type":"GRAMMAR","targetId":9001,"bookmarked":true,
                                          "counts":{"kanji":0,"grammar":1,"vocabulary":0,"total":1}}
GET  /api/bookmarks/ids            → {"kanji":[],"grammar":[9001],"vocabulary":[]}
GET  /api/bookmarks/summary        → {"kanji":0,"grammar":1,"vocabulary":0,"total":1}
GET  /api/bookmarks/grammar        → {"content":[],"totalElements":0,"totalAll":0,...}   ← 0건
```

(9001 = `GET /api/en/library/expressions`… 가 아니라 `GET /api/en/library/grammar`의 첫 항목, `level: "E1"`.)

**왜 문제인가**
- `설계/04 §6-4`가 두 가지를 계약으로 못 박았다: **"없는 대상(자료실에 없는 항목 포함) 404"**, 그리고 **"개수·id 집합은 '지금 존재하는 항목'만 센다"**.
  영어 문법은 (일본어) 자료실에 없는 항목이므로 404여야 하는데 200이고, 저장된 뒤에는 개수에만 잡히고 목록에는 없다.
- **같은 "존재한다"의 판정이 종류마다 다르다.** 어휘는 `LibraryVocabularyService.resolveEntryId`가 `CourseLanguage.JA`로 조회하므로 영어 id에 정확히 404를 준다(위 재현에서 `PUT /api/bookmarks/vocabulary/9101` → 404 `존재하지 않는 어휘입니다: 9101`). 한자는 영어 대역 행이 아예 없어 문제가 드러나지 않는다. **문법 하나만 언어를 안 본다.**
- 프론트가 살려 주고 있을 뿐이다 — `frontend/src/components/library/ListItems.jsx:70`의 `{!latin && <ItemStar .../>}` 가 영어 문법 행에서 ★를 렌더하지 않는다. **화면이 막고 있는 것이지 서버가 막고 있는 게 아니다.**

**근거**
- `src/main/java/com/test/test/library/repository/LibraryGrammarQueryRepository.java:87-98` — `findExistingIds()`에 `COURSE.language` 조건이 없다. 같은 파일의 다른 조회(`findLearnedInUnit`)와 `LibraryGrammarService.getGrammarListByIds`(`:52-55`, `CourseLanguage.JA` 고정)는 언어를 본다.
- `src/main/java/com/test/test/bookmark/BookmarkService.java:155-161`(`requireExistingTarget`) → `:196-206`(`filterExisting`) → 위 메서드.
- 어휘 쪽 대조군: `src/main/java/com/test/test/library/LibraryVocabularyService.java:93-100`.

**고치는 비용**: 작다. 존재 판정 질의에 언어 조건을 넣고(또는 `filterExisting`이 언어를 받게 하고), 고정 테스트 1건(`PUT /api/bookmarks/grammar/{EN id}` → 404 + `/ids`에 안 뜸)을 추가하면 된다.

**안 고치면 언제 터지나**
① 영어 자료실에 ★를 켜는 이터레이션에서 즉시(개수 배지와 목록이 다른 화면).
② 그 전에도 `POST /api/me/merge`가 같은 `filterExisting`을 타므로(`BookmarkService.normalizeExisting`), 낡은/조작된 payload 하나로 계정에 **목록에 안 보이는 유령 개수**가 영구히 남는다. 사용자는 "담은 34개 중 12개"가 왜 안 맞는지 알 방법이 없다.

### H2. `page` 범위 초과 보정이 **커뮤니티·댓글에는 없다** — 04 §1-5가 "공통 규칙"이라고 적은 그 규칙 [실측]

**무엇이 이상한가**
`설계/04 §1-5`는 목록 API의 **공통** 규칙으로 "`page`가 총 페이지 수 이상이면 **0페이지 내용 + 응답 `page: 0`** (404도, 빈 배열도 아니다)"를 못 박았고, 적용 대상을 **"`Page`/`LibraryPageResponse`"** 라고 명시했다. 자료실은 지키는데 커뮤니티·댓글은 안 지킨다.

```
GET /api/library/kanji?page=99999&size=60      → page:0,  n:60   ✅ 보정됨
GET /api/communities?page=9999                 → page:9999, n:0  ❌
GET /api/communities/1/comments?page=9999      → page:9999, n:0  ❌ (totalPages:2, last:true)
```

**왜 문제인가**
- 04 §1-5가 이 규칙을 도입하며 든 **근거 시나리오가 정확히 커뮤니티다**: *"마지막 페이지를 보는 중에 글이 삭제돼 총 페이지가 줄어드는 일이 흔하다. 그때 사용자가 볼 것은 빈 화면이 아니라 목록이다."* 규칙이 필요한 바로 그 화면에 규칙이 없다.
- 04 §1-5는 또 "클라이언트는 요청한 `page`가 아니라 **응답의 `page`를 신뢰한다**"고 적었다. 커뮤니티에서는 응답의 `page`가 9999이므로, 이 계약을 믿는 클라이언트가 그대로 9999를 표시한다.
- `frontend/src/components/Pagination.jsx`는 `page=9999, totalPages=3`을 받으면 버튼을 [1][2][3]으로 그리고 **어느 것도 active가 아닌** 상태로 렌더한다(이전 버튼만 활성). 빈 목록 + 선택된 페이지 없음.

**근거**
- `src/main/java/com/test/test/common/dto/PageResponse.java:29-39` — `from(Page)`가 `page.getNumber()`를 그대로 옮긴다. 보정 로직이 없다.
- 대조군: `src/main/java/com/test/test/library/LibraryPaging.java:32-37` — `resolvePage()`가 "총 페이지 이상 → 0"을 구현한다. **보정 규칙이 자료실 패키지 안에만 산다.**
- `설계/04 §1-5` 표 및 그 아래 "페이지 보정을 **서버가 하는 이유**: 프론트 3개 화면이 각자 같은 보정 로직을 구현하면 어긋난다".

**고치는 비용**: 작다. `PageResponse.from`에 같은 보정을 넣거나(단, `Page`는 이미 잘린 뒤라 재조회가 필요해 컨트롤러/서비스 레벨 보정이 맞다), 혹은 계약 문서에서 "`Page`"를 빼고 "자료실 전용 규칙"으로 범위를 좁힌다. **어느 쪽이든 결정이 필요하다 — 지금은 문서와 코드가 서로 다른 말을 한다.**

**안 고치면 언제 터지나**
게시글 삭제로 총 페이지가 줄어들 때, 그리고 누군가 `?page=`가 담긴 주소를 공유할 때. 빈도는 낮지만 **문서를 믿고 짜는 다음 클라이언트(앱)가 반드시 밟는다** — 계약서에 "공통"이라고 적혀 있기 때문이다.

### H3. 콘텐츠 전수 검증 테스트가 **6개 코스 중 4개만** 돈다 — 입문·N1은 규칙이 강제되지 않는다 [실측]

**무엇이 이상한가**
`CourseApiIntegrationTest`에는 **코스 목록이 두 벌** 있다.

```java
// src/test/java/com/test/test/integration/CourseApiIntegrationTest.java:267
/** 입장 가능한 4개 코스 전 유닛 순회 — {courseId, 유닛 수} */
private static final int[][] AVAILABLE_COURSES = {{2, 20}, {3, 20}, {4, 25}, {5, 25}};
```

같은 패키지의 `CourseCatalog.java`가 **"테스트가 보는 콘텐츠 사실의 단일 출처"** 를 자처하며 6개 코스를 전부 들고 있는데(`CourseCatalog.java:57-63`), 아래 세 테스트만 옛 배열을 쓴다:

- `all_units_follow_kana_notation_contract` (`:276`) — kana 표기 계약
- `vocabulary_is_not_duplicated_within_a_course` (`:330`) — 코스 내부 어휘 중복 금지
- `all_vocabularies_have_valid_part_of_speech` (`:397`) — 품사 전량 기입

따라서 **입문(코스 1, 10유닛·어휘 150)과 N1(코스 6, 25유닛·어휘 450)은 이 세 규칙의 검증을 한 번도 받지 않는다.** 20+20+25+25 = **90유닛**만 돈다(전체 125유닛).

**왜 문제인가**
- `설계/06 §9`는 "전수 검증하는 것들" 표에 **"kana 표기 규칙 위반 (90유닛 전 콘텐츠)"** 이라고 적어 두었다. 이 "90"은 **오래된 총계가 아니라 지금 구멍의 크기 그대로다** — 문서가 구멍을 정확히 기록해 놓고 "전 콘텐츠"라고 부르고 있다.
- `설계/03 §8-6`도 "`06`의 수량·표기 규칙을 지킨다. **테스트가 전수 검증한다**"고 적는다. 새 코스 담당자는 이 문장을 믿는다.
- `CourseCatalog`의 존재 이유가 정확히 이 문제였다("입문이 열리자 하드코딩된 숫자를 가진 기존 테스트 11건이 한꺼번에 깨졌다 … 앞으로는 이 표의 한 줄만 고치면 된다"). **이관이 절반만 끝났고, 남은 절반이 조용히 커버리지를 깎았다.**

**지금 실제 데이터는 깨끗하다** [실측]. 라이브 8083에 일본어 6코스 125유닛을 전수 조회해 같은 세 규칙을 직접 검사한 결과:

```
KANA 계약 위반         : 0
코스 내부 어휘 중복    : 0
partOfSpeech 위반      : 0
```

즉 **지금 결함이 있다는 게 아니라, 결함이 생겨도 `./gradlew test`가 잡지 못한다**는 것이 이 건이다.

**고치는 비용**: 매우 작다. 세 테스트의 순회 대상을 `CourseCatalog.available()`로 바꾸고 `AVAILABLE_COURSES` 상수를 지운다. 데이터가 이미 깨끗하므로 Green 상태 그대로 커버리지만 늘어난다.

**안 고치면 언제 터지나**
다음 코스(또는 N1·입문 콘텐츠 개정)에서 kana 규칙을 어긴 시드가 들어가는 순간. 이 규칙은 **qa가 화면에서만 잡을 수 있는 종류**(같은 문장이 두 줄로 렌더)라, 테스트가 놓치면 사람이 125유닛을 눈으로 봐야 한다.

## 2. 중간

### M1. 실력 진단의 계단이 **레벨 코드 5개를 하드코딩**한다 — 바로 위 주석이 "하드코딩하지 않는다"고 적혀 있다 [실측]

```js
// frontend/src/lib/diagnosis.js:17
export const STAGE_LEVEL_CODES = ["N5", "N4", "N3", "N2", "N1"];
```

**무엇이 이상한가**
- 같은 파일 3행: *"코스명·레벨을 하드코딩하지 않는다 — 계단은 `GET /api/courses`의 AVAILABLE 코스에서 계산한다(08 C-6)."*
- `설계/09 §3-1`: *"계단 = AVAILABLE 코스의 레벨을 낮은 것부터. **코스명·레벨을 하드코딩하지 않고** `GET /api/courses`에서 계산한다(08 C-6)."*
- 실제로는 코스 목록에서 **필터링만** 하고, **어떤 레벨이 계단이 될 수 있는지와 그 순서**는 이 배열이 정한다(`stagePlan`이 `STAGE_LEVEL_CODES.indexOf(...)`로 정렬한다 — `courseNo`로 정렬하지 않는다).

**왜 문제인가**
- **탈락 사유가 바뀐다.** 09 §3-1은 입문이 계단에서 빠지는 이유를 "한자가 0자라 측정할 수 없어서"라고 적었지만, 코드가 실제로 하는 일은 "`INTRO`가 배열에 없어서"다. 이유와 구현이 다르면, 다음에 한자 0자인 코스가 또 생겨도 아무도 그 사실을 근거로 판단하지 않는다.
- **새 레벨이 조용히 사라진다.** JLPT 사이의 보충 코스든 뭐든 새 `level_code`가 생기면 `libraryLevelOfCourse()`가 `null`을 돌려주고, `stagePlan`에서 **에러 없이 빠진다.** 테스트도 안 깨진다.
- **영어에는 아예 작동하지 않는다.** `E1`~`E5`는 전부 `null`이 되어 `stagePlan(enCourses)`가 빈 배열 → `recommend()`가 `null`. 지금은 진단이 일본어 전용이라 무해하지만, 코드 어디에도 "일본어 전용"이라고 적혀 있지 않다.
- 같은 종류의 하드코딩이 프론트에 **하나 더** 있다: `frontend/src/lib/libraryQuery.js:33-34`의 `JA_LEVELS`/`EN_LEVELS`. 백엔드는 `CourseLevelCatalog`가 DB `course.level_code`를 읽어 단일 출처를 지키는데(`src/main/java/com/test/test/course/CourseLevelCatalog.java`), **프론트는 같은 목록을 두 벌 따로 들고 있다.**

**고치는 비용**: 중간. 계단 자격을 "레벨 코드가 목록에 있는가"가 아니라 **응답에서 판정 가능한 사실**(예: 코스 상세 `summary.kanjiCount > 0`)로 바꾸고, 순서는 `courseNo`로 잡으면 09 §3-1의 서술과 코드가 일치한다. 최소한으로는 "이 배열은 일본어 전용이며 새 레벨이 생기면 여기도 고쳐야 한다"는 사실이 **테스트로** 붙어야 한다.

**안 고치면 언제 터지나**: 코스가 하나 더 열리는 날. 그때 화면은 에러 없이 **한 단계가 사라진 진단**을 보여준다.

### M2. `설계/09 §3-1`에 **되돌린 원칙이 그대로 남아 있다** — "근거는 `courseNo`" [실측]

```
설계/09_학습도구_동작규칙.md:139
| 자료실 `level` 파라미터 | **코드** — `"N5"`. 근거는 `courseNo`이지 `levelLabel`이 아니다 | `GET /api/library/**` 필터 |
```

`설계/03 §1`과 `설계/04 §3-1`은 같은 문장을 **⚠️ 표시까지 붙여** 뒤집어 놓았다: *"레벨은 `course.level_code` 컬럼이다 — `courseNo`에서 파생시키지 않는다. **2026-08-20에 뒤집힌 원칙이다(되돌리지 말 것)**."* 04는 심지어 이 정정을 헤더 변경 이력에 적어 두었다(*"§2-1·§2-2·§3-1의 레벨 서술을 `level_code` 기준으로 정정 — `courseNo` 파생 서술이 03만 고쳐지고 여기 남아 있었다"*).

**왜 문제인가**: **같은 정정을 09에서 한 번 더 놓쳤다.** 04가 "03만 고쳐지고 04에 남아 있었다"고 기록한 그 사고가 09에서 반복됐다. 이 서술은 3단계 qa 치명 결함의 뿌리라고 두 문서가 명시한 바로 그 문장이라, 남아 있는 한 다음 사람이 다시 파생 구현을 시도할 근거가 된다.

### M5. 기본 프로파일이 **편집 모드·H2 콘솔을 켠 채** 배포 산출물에 들어간다 — "안전한 기본값"이 역전돼 있다 [실측]

`src/main/resources/application.yml`:
```yaml
spring.h2.console.enabled: true
app.editor.enabled: true
```

이 값들은 `application-prod.yml`이 명시적으로 `false`로 되돌리고(`:52-55`, `:110-112`), `RailwayDeploymentValidator`가 prod에서 `true`면 기동을 거부한다. **여기까지는 정확히 설계대로 작동한다.**

문제는 **방어가 전부 `prod` 프로파일에 매달려 있다**는 것이다:
- `RailwayDeploymentValidator`는 `@Profile("prod")`다(`:20`) — prod가 아니면 **검증 자체가 없다.**
- `prod` 활성화의 유일한 근거는 `Dockerfile`의 `ENTRYPOINT ... -Dspring.profiles.active=prod` 한 줄이다.
- 즉 **`bootJar` 산출물을 prod 프로파일 없이 실행하면** H2 콘솔 열림 + 편집 모드(무인증 콘텐츠 쓰기) 열림 + 쿠키 `Secure=false` + 시드 `always` + **검증기 없음**이 한꺼번에 성립한다.

또 하나, 코드가 사실과 다른 말을 한다. `SecurityConfig.java:57`:
```java
@Value("${spring.h2.console.enabled:false}")   // 주석: "기본값 false: 이 값이 없는 환경은 곧 '콘솔 없음'이다(안전한 기본값)"
```
**이 `:false` 기본값은 절대 적용되지 않는다** — `application.yml`이 항상 이 키를 `true`로 정의하기 때문이다. 같은 문장이 `RailwayDeploymentValidator.java:38,46`에도 있다. 주석이 주장하는 안전망이 실물에는 없다.

**왜 문제인가**: 기본값이 "열림"이면, 방어의 개수와 무관하게 **새 실행 경로가 생길 때마다 열린 상태가 기본이 된다**(staging 프로파일 추가, 로컬 jar 실행, 다른 PaaS로의 이전). `설계/07 §1-1`이 강조한 원칙 — *"설정 한 줄로 끄는 것은 방어가 아니다"* — 를 뒤집으면 *"설정 한 줄로 켜 두는 것도 기본값이 아니어야 한다"* 가 된다.

**고치는 비용**: 중간. 두 값을 `application.yml`에서 빼고(= 미정의 → `@Value` 기본값 false가 실제로 작동), 로컬만 `application-local.yml`이나 `.env`/실행 인자로 켜는 방향. 다만 **로컬 개발 편의를 깎는 변경**이라 사람 결정이 필요하다.

**안 고치면 언제 터지나**: 프로파일 지정 없이 돌리는 환경이 하나라도 생기는 날. 지금 당장은 터지지 않는다 — Dockerfile이 유일한 배포 경로인 동안에는.

### M6. **웹/앱 판별자가 두 가지**다 — 로그인은 `Accept`, 갱신·비밀번호 변경은 `Authorization` [실측]

| 엔드포인트 | 판별 | 근거 |
|---|---|---|
| `POST /api/login` | `Accept`에 `text/html` 포함 → 웹(쿠키), 아니면 앱(JSON 바디에 토큰) | `JwtLoginFilter.java:98-99` |
| `POST /api/tokens/refresh` | `Authorization: Bearer ` 있으면 앱, 없으면 웹 | `RefreshController.java:44,55` |
| `PUT /api/me/password` | `Authorization: Bearer ` 있으면 앱 | `AccountController.java:108-109` |

**실측**: `Accept` 없이 `POST /api/login`을 보내면 **`Set-Cookie`가 하나도 없고** 응답 바디로 `access_token`·`refresh_token`이 그대로 온다. 프론트는 이걸 피하려고 JSON 전용 SPA인데도 **일부러 `Accept: "application/json, text/html"` 을 보낸다**(`frontend/src/context/AuthContext.jsx:49`).

**왜 문제인가**
- **문서가 틀렸다.** `설계/04 §1-4`: *"앱(**Authorization 헤더**)에는 JSON 바디로 토큰을 내리는 이중 경로가 있다."* 로그인에는 Authorization 헤더가 있을 수 없다 — 로그인의 실제 판별자는 `Accept`다. 04만 읽고 Flutter 클라이언트를 짜면 **로그인만 다르게 동작하는 이유**를 못 찾는다.
- **클라이언트가 거짓말을 하도록 강요한다.** SPA가 HTML을 받을 생각이 전혀 없는데 `Accept: text/html`을 붙여야 쿠키를 받는다. 이 한 줄이 지워지면 로그인은 200을 주면서 **쿠키 없이 로그인 실패처럼 보이는** 상태가 된다(에러 없음 → 원인 추적이 어렵다).
- 같은 "웹이냐 앱이냐" 판정이 두 규칙으로 갈려 있다 — **판정이 갈릴 소지**가 구조적으로 남아 있다.

**고치는 비용**: 중간(계약 변경). 최소 조치는 **04 §1-4에 로그인의 판별자가 `Accept`임을 명시**하는 것(비용 거의 0). 근본 조치는 판별자를 하나로 모으는 것인데, 그건 앱이 실제로 붙는 시점의 결정이 맞다.

**안 고치면 언제 터지나**: Flutter가 붙는 이터레이션. 그리고 그 전이라도 누가 `AuthContext`의 fetch 헤더를 정리하다 `Accept` 줄을 지우는 날.

`설계/02 §4`: *"목록 화면의 상태(검색어·필터·정렬·**페이지**)는 컴포넌트 state가 아니라 **주소 쿼리스트링**에 둔다 → 새로고침·뒤로가기·주소 공유가 그대로 복원된다."*
`CommunityListPage.jsx`의 파일 주석도 *"주소가 목록 상태의 단일 출처"* 라고 적는다.

그런데 `searchType`·`keyword`만 주소에 있고 **`page`는 `useState`**다(`frontend/src/pages/CommunityListPage.jsx:25-29`, 주소에 반영하는 코드 없음). 결과: 3페이지에서 새로고침하면 1페이지, 글을 열었다가 뒤로 오면 1페이지. 자료실·보관함은 규칙을 지키고 있어 **같은 제품 안에서 목록 화면 동작이 갈린다.** H2와 함께 손대면 커뮤니티 페이징이 한 번에 정리된다.

### L8. `UnitStudyPage`에 **절대 도달하지 않는 분기**가 있다 [코드추론]

`frontend/src/pages/UnitStudyPage.jsx:571-572`의 `quizSet` memo는 `if (!data || en) return { questions: [] };` 로 시작한다. 따라서 그 아래는 **항상 `en === false`** 인데:
- `expressions: data.expressions ?? []` — 일본어 응답에는 `expressions`가 없으므로 항상 `[]`.
- `q.type.startsWith("EXPRESSION_") ? '/en/library/expressions/...'` (`:588`) — EXPRESSION_* 문항은 위에서 재료가 비어 생성될 수 없다. **도달 불가.**
- `libraryBase`도 이 memo 안에서는 항상 `/library`.

의도는 "영어를 켤 때를 대비한 배선"으로 보이고 09 §5가 켜는 조건을 적어 두었으니 삭제 대상은 아니다. 다만 **읽는 사람은 이 코드를 보고 "영어 퀴즈가 부분적으로 동작한다"고 오해한다.** `en` 가드 옆에 "여기 아래는 일본어 전용 — 영어 켜기는 09 §5" 한 줄이면 해소된다.

### L9. `build.gradle`의 미사용 변수 [실측]

`build.gradle:69` `def querydslDir = "src/main/generated"` 가 정의만 되고 **어디에도 쓰이지 않는다**(`sourceSets`·`annotationProcessorGeneratedSourcesDirectory` 설정 없음). QClass는 실제로 `build/generated/sources/annotationProcessor/`에 생성된다. 옛 설정의 잔해 — 지우면 된다.

### L10. 호출자가 없는 공개 엔드포인트 1개 [실측]

`GET /api/files/paths` — 프론트 전체 검색에서 호출처가 없다. 보일러플레이트 유래라 우선순위는 낮지만, `04 §5` 표에 계약으로 적혀 있으므로 **`/api/bookmarks/summary`처럼 "유지하기로 한 이유"를 한 줄 남기거나 지우거나** 둘 중 하나가 맞다. 지금은 판단이 없다.

## 4. 잘 되어 있는 것 — **지키고 확산할 패턴**

지적만 남기면 다음 사람이 무엇을 건드리면 안 되는지 모른다. 이번 점검에서 **의심하고 들어갔다가 설득당한** 것들이다.

### 4-1. 언어 증설을 "조회 조건 하나"로 끝낸 구조

영어 과정이 붙으면서 테이블도 서비스도 복제되지 않았다.
- `CourseLanguage`가 enum 하나, `course.language` 컬럼 하나. 컨트롤러가 언어를 **고정해서** 서비스에 넘긴다.
- `EnLibraryGrammarController`는 `LibraryGrammarService`를 **그대로** 쓰고 `CourseLanguage.EN`만 넘긴다(파일 전체가 그 일만 한다). 자료실 목록·검색·페이징 로직이 한 벌이다.
- `CourseService.loadUnitStudyBase(courseId, unitNo, language)`가 언어 공통부를 담당하고, 3번째 자리(한자/표현)만 호출자가 채운다.

> 이 덕분에 H1(문법 존재 판정의 언어 누락)이 **한 곳만 고치면 되는 결함**으로 남았다. 복제 구조였다면 같은 버그가 여러 벌 있었을 것이다.

### 4-2. `level_code` 컬럼 승격 — 되돌리지 말 것

`courseNo`에서 레벨을 파생하던 것을 DB 컬럼으로 올린 판단은 **지금 보면 유일하게 성립하는 선택**이다. 라이브에서 확인:
```
GET /api/library/kanji?level=E1    → 400  "지원하지 않는 레벨입니다: E1 (INTRO·N5·N4·N3·N2·N1 중 하나)"
GET /api/en/library/grammar?level=N5 → 400 "지원하지 않는 레벨입니다: N5 (E1·E2·E3·E4·E5 중 하나)"
GET /api/library/kanji?level=INTRO   → 200 + 0건   (유효한 코드, 데이터가 없을 뿐)
```
"선택지에서 뺀 것"과 "파라미터가 거부하는 것"을 구분한 것까지 코드(`CourseLevelCatalog`)와 응답이 일치한다. **허용 목록을 DB에서 읽으므로 코스가 늘면 에러 메시지까지 자동으로 늘어난다.**

### 4-3. 동시 쓰기를 **격리 수준까지 못 박은** 사용자 데이터 계층

`ProgressService`·`BookmarkService`가 쓰기 진입점에서 `users` 행을 `PESSIMISTIC_WRITE`로 잠그고, `@Transactional(isolation = READ_COMMITTED)`를 **명시**한다. 이유가 주석에 정확히 적혀 있다 — *"운영 MySQL 기본값(REPEATABLE READ)에서는 잠금을 얻고 다시 조회해도 먼저 들어간 행을 못 본다. H2는 이미 READ_COMMITTED라 로컬에서는 증상이 드러나지 않는다."*
**로컬에서 재현되지 않는 문제를 미리 막아 둔 것**이고, 취소는 벌크 삭제로 처리해 "이미 사라진 행"이 실패가 되지 않게 했다. 이 계층은 손대지 않는 게 좋다.

### 4-4. 콘텐츠에 FK를 걸지 않고 **읽기 시점 필터**로 갚는 결정

`user_unit_completion`·`user_bookmark`가 콘텐츠에 FK를 걸지 않는 대신, 쓰기에서 404로 막고 읽기에서 조인으로 거른다(`ExistingUnits`, `filterExisting`). 시드 재적재 내성과 사용자 데이터 보존을 동시에 얻는다. `03 §4-1`이 *"⚠️ 읽기 시점 필터는 API만으로 재현할 수 없다 … 통합테스트가 없는 유일한 규칙이며 결함이 아니다"* 까지 미리 적어 둔 것도 좋다 — **다음 감사가 같은 지점을 결함으로 올리지 않게 한다.**

### 4-5. 편집 모드의 3겹 방어

`@ConditionalOnProperty`로 **빈 자체를 등록하지 않고**(꺼진 환경엔 경로가 존재하지 않음 → 403이 아니라 404), `application-prod.yml`이 명시적으로 끄고, `RailwayDeploymentValidator`가 prod에서 켜져 있으면 **기동을 거부**한다. "403으로 막으면 경로의 존재를 알려주게 된다"는 근거까지 `04 §9`에 있다. M5는 이 설계를 부정하는 게 아니라 **기본값의 방향**만 지적한 것이다.

### 4-6. 테스트가 숫자가 아니라 규칙을 보게 만든 `CourseCatalog`

*"코스가 열릴 때마다 여러 파일의 숫자를 찾아 고치는 것은 계약 검증이 아니라 숫자 관리다"* — 이 판단은 옳고, 자료실 총계를 `available()`의 합으로 파생시킨 것도 옳다. `somePreparingCourse()`가 준비중 코스를 **계산으로 찾고**, 하나도 없으면 *"그 테스트를 지워야 한다"* 는 메시지와 함께 실패하게 만든 것은 특히 좋다. **H3은 이 패턴이 나쁘다는 게 아니라 이관이 안 끝났다는 것이다.**

### 4-7. 어휘 병합의 대표 id가 **우연에 기대지 않는다**

과거에 문제가 됐던 지점이라 집중해서 봤다. `findAllRowsInLearningOrder`와 `findGroupRowsByVocabularyIds`가 **같은 `baseQuery()`** 를 쓰고, 그 안에 `orderBy(courseNo, unitNo, sortOrder)`가 한 번만 적혀 있다. 병합 키는 `Arrays.asList(word, kana)`라 **쌍**이고 `null`도 그대로 키가 된다(문자열 이어붙이기의 경계 모호성이 없다). 그래서 "어디서 물어도 같은 대표 id"가 **구조적으로** 성립한다 — 콘텐츠가 바뀌어도 흔들리지 않는다.
