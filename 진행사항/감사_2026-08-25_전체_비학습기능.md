기준일: **2026-08-25** / 담당: qa
방법: **로컬 서버(8083)에 실제 요청을 보내 시나리오로 시험**했다. 화면으로만 확인 가능한 것은 코드 근거로 남기고 **[코드 근거]**로 표시했다.

> **표기 규칙 — 이 문서에서 가장 중요한 약속**
> - **[재현]** = 실제 요청/응답으로 그 자리에서 확인한 사실. 응답 원문을 붙였다.
> - **[코드 근거]** = 파일·줄을 읽고 판단한 것. **실행으로 확인하지 못했다.** 고치기 전에 화면에서 한 번 더 봐야 한다.
> - 두 표기가 없는 문장은 배경 설명이다.
>
> 심각도는 **사용자가 실제로 겪는 피해** 기준이다. 보안 항목이라고 자동으로 올리지 않았다.

# 높음

## H1. 같은 초에 로그인한 두 세션은 **완전히 같은 토큰**을 받는다 — 비밀번호를 바꿔도 상대 기기가 안 끊긴다

**증상** — 기획 §4-4의 핵심 약속이 깨진다: *"비밀번호를 바꾸는 이유의 절반은 '남이 내 계정을 쓰는 것 같아서'인데, 다른 세션이 살아 있으면 그 목적이 달성되지 않는다."* **AC-A-28** 위반.

**원인** — `JwtUtil.java:40-59`. access·refresh 토큰의 클레임이 `sub / token_type / tv / iat / exp`뿐이고 **난수(jti)가 없다.** `iat`·`exp`가 **초 단위**라 같은 초의 두 발급은 **바이트 단위로 동일한 문자열**이 된다. 코드도 이미 그 사실을 알고 있다 — `RefreshRepository.java` 주석: *"같은 초 재로그인(동일 토큰 재발급) 시 token 유니크 충돌(500)을 방지"*.

**[재현] 결정적으로 재현된다**

```bash
# 1. 두 세션을 동시에 로그인 (같은 초)
curl -c x1.txt -X POST /api/login -H 'Accept: text/html' -d '{"username":"user10","password":"1234"}' &
curl -c x2.txt -X POST /api/login -H 'Accept: text/html' -d '{"username":"user10","password":"1234"}' &
wait
```
```
same refresh token? YES
same access token?  YES        ← 두 세션이 같은 토큰을 들고 있다
```
```bash
# 2. 세션1에서 비밀번호 변경
PUT /api/me/password {"currentPassword":"1234","newPassword":"abcd","newPasswordConfirm":"abcd"}  → 200

# 3. 세션2(다른 기기 역할)
GET  /api/users/me        → 401 {"errorCode":"TOKEN_EXPIRED"}     ← 여기까지는 의도대로
POST /api/tokens/refresh  → 200 {"message":"Token refreshed"}     ← ★ 되살아난다
GET  /api/users/me        → 200 {"nickname":"임도윤", ...}          ← 완전히 복귀
```

3번의 401→refresh→재요청은 **프론트가 자동으로 한다**(`frontend/src/lib/http.js:65-94` `authFetch`). 즉 **다른 기기 사용자는 깜빡임조차 못 느끼고 계속 로그인 상태로 남는다.**

**왜 되살아나나**: `AccountService.changePassword`(`:117`)가 `refreshRepository.deleteByUserId`로 refresh 행을 지운 뒤 **같은 초에** 현재 기기용 refresh를 새로 발급한다(`:119` → `issueRefreshToken`). 새 값이 방금 지운 값과 **같은 문자열**이라, 상대 세션의 쿠키가 DB에 다시 존재하게 된다. `RefreshService.rotate`(`:64`)의 `findByToken` 검사가 통과한다.

**같은 원인의 두 번째 증상 [재현]** — 회전(rotation) 재사용 탐지도 같은 창에서 무력화된다. 같은 refresh 쿠키로 5개를 동시 요청하면 **5개 전부 200**이다(설계 의도는 1개만 200, 나머지 `TOKEN_DISCARDED`).

**반증 [재현]** — 두 로그인 사이를 2초 벌리면 토큰이 달라지고, 그때는 계약대로 동작한다(세션2 → `refresh 401 TOKEN_DISCARDED`, 로그인 유지 안 됨). **즉 결함은 "같은 초"라는 조건부다.**

**영향**: 조건부지만 침해 대응 경로(비밀번호 변경)의 보장이 확률적으로 무너진다. 탈퇴(`withdraw`)도 같은 `deleteByUserId` + `tv` 증가 조합을 쓰므로 같은 취약 창을 갖는다 — 다만 탈퇴는 쿠키를 즉시 만료시키고 로그인 자체를 막아 실피해가 작다.

**고치는 비용**: 작음(반나절). `createAccessToken`/`createRefreshToken`에 `jti`(UUID) 클레임 한 줄. 다만 **토큰 형식 변경이라 senior-dev 경유**이고, 유니크 충돌을 피하려고 넣은 기존 방어(`deleteByUserEntity_Username` 선삭제)를 함께 재검토해야 한다.

## H2. 로그인 실패에 **아무 제한이 없다** — 15회 연속 실패 후에도 즉시 정상 로그인된다

**증상** — 잠금·지연·CAPTCHA·IP 제한이 하나도 없다. 비밀번호 최소 길이는 **4자**(`JoinDTO`·`PasswordChangeRequest`)이고 시드 계정은 전부 `1234`다.

**[재현]**

```
POST /api/login {"username":"user4","password":"wrong"} × 15회
→ 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401   (지연·잠금 없음)
POST /api/login {"username":"user4","password":"1234"}
→ 200                                                            (곧바로 성공)
```

15회는 임의로 고른 횟수이고, **응답 시간도 눈에 띄게 늘지 않았다.** 4자리 숫자 비밀번호의 전수 공간은 10,000개다.

**근거**: `SecurityConfig.java`에 rate limit 필터가 없고, `JwtLoginFilter.unsuccessfulAuthentication`(`:118-133`)은 401 JSON만 쓴다. `설계/07_운영_배포.md`·`설계/08_결정기록.md`에 **로그인 시도 제한에 관한 결정 기록이 없다** — 즉 "의도된 수용"으로 닫힌 항목이 아니다(`08 §D`에 없음).

**영향**: 운영 배포된 사이트라면 계정 탈취의 가장 싼 경로다. 아이디는 커뮤니티 API가 `username`으로 그대로 노출한다(→ M8) — 즉 **대상 목록을 만드는 것도 인증 없이 가능하다.**

**고치는 비용**: 중간. 결정이 먼저다(senior-dev). 옵션: ① 실패 카운터 + 지연/잠금 ② IP·계정 단위 rate limit 필터 ③ 비밀번호 최소 길이 상향(가입·변경·시드 동시 변경 → 계약 변경). ①만으로도 피해는 크게 준다.

## H3. 마이페이지 [이어서 학습하기]가 **영어 유닛을 공부한 뒤엔 404**로 간다

**증상** — 진도의 "마지막 위치"는 사이트 전체에 하나인데(기획 §2-1), 영어 과정이 생긴 지금 그 하나에 **영어 코스 id(101~105)** 가 들어간다. 마이페이지는 그 값을 **일본어 주소에 그대로** 끼워 넣는다.

**[재현]**

```bash
# 1. 로그인 후 영어 유닛을 공부한 것과 같은 저장이 일어난다
PUT /api/progress/last-position {"courseId":101,"unitNo":1,"stepKey":"vocab"}   → 200
GET /api/progress
   → "lastPosition":{"courseId":101,"unitNo":1,"stepKey":"vocab", ...}

# 2. 마이페이지가 만드는 링크를 그대로 따라가면
GET /api/courses/101/units/1
   → 404 {"success":false,"message":"존재하지 않는 코스입니다: 101","errorCode":"NOT_FOUND"}
```

**근거**
- 저장: `frontend/src/pages/UnitStudyPage.jsx:657` — `userData.saveLastPosition(data.courseId, ...)`. 과정 구분자를 함께 저장하지 않는다. 영어 화면은 `apiBase = "/api/en/courses"`(`:504`)를 쓰지만 **courseId만 저장**된다.
- 사용: `frontend/src/pages/MyPage.jsx:120` — ``to={`/courses/${lastPosition.courseId}/units/${lastPosition.unitNo}`}``. **코스 존재 여부를 확인하지 않는다.**
- 화면 결과 **[코드 근거]**: `/courses/101/units/1` → `UnitStudyPage`(ja) → `/api/courses/101/units/1` 404 → `NotFoundCard`("찾을 수 없는 페이지예요"). 나갈 링크는 있으므로 완전한 막다른 길은 아니다.

**같은 화면의 두 번째 문제**: `MyPage.jsx:113`은 *"유닛 1 학습 중이었어요"* 만 쓴다. **코스 이름이 없다.** 기획 §4-1은 내 학습 카드에 "완료 유닛 수 · **진행 중인 코스** · 마지막으로 본 유닛"을 요구한다. 모든 코스에 유닛 1이 있으므로 이 문장만으로는 어디였는지 알 수 없다.

**대조 — 홈은 옳게 처리한다 [코드 근거]**: `HomePage.jsx:18`은 `courses.find(item => item.id === lastPosition.courseId)`로 코스를 찾고, 못 찾으면 조용히 [학습 시작하기]로 되돌아간다(기획 §2-6의 "사라진 유닛" 규칙). **같은 규칙이 마이페이지에만 없다.**

**영향**: 영어 과정은 지금 1개 코스·2유닛만 열려 있어 노출은 작지만, 마이페이지의 주 CTA가 깨진 링크가 된다. 영어 유닛이 늘수록 커진다.

**고치는 비용**: 작음(2시간). 마이페이지가 홈과 같은 판정(코스 목록에서 찾기 → 못 찾으면 버튼 숨김)을 쓰면 되고, 그러면 코스 이름 표시(기획 §4-1)도 함께 해결된다. 두 과정 모두 지원하려면 코스 목록 2개를 조회해야 하므로 **계약 확인 필요(senior-dev)**.

## M3. 로그아웃해도 **access 토큰이 30분간 그대로 유효**하다

**[재현]**

```
POST /api/logout           -> 200 {"message":"Logged out successfully"}   (쿠키 만료 헤더 정상)
# 로그아웃 직전에 복사해 둔 쿠키로 다시 요청하면
POST /api/tokens/refresh   -> 401 TOKEN_DISCARDED     <- refresh는 확실히 죽었다
GET  /api/users/me         -> 200 {"nickname":"강예진","id":9, ...}   <- access는 살아 있다
```

**근거**: `CustomLogoutSuccessHandler`는 refresh 행 삭제 + 쿠키 만료만 한다. **`token_version`을 올리지 않는다** — 비밀번호 변경(`AccountService` `user.changePassword`)과 탈퇴(`user.withdraw`)는 올리는데 로그아웃만 안 올린다.

**영향**: 정상 브라우저는 쿠키가 지워지므로 피해가 없다. 피해는 **토큰이 이미 새어 나간 경우**로 한정된다(공용 PC에서 개발자도구로 복사 등). "로그아웃했으니 안전하다"는 기대와 최대 30분 어긋난다.

**고치는 비용**: 작음(`tokenVersion + 1` 한 줄)이지만 **모든 기기가 함께 로그아웃되는 부작용**이 있어 정책 결정이 먼저다(senior-dev). 스테이트리스 JWT의 알려진 트레이드오프라 "수용"도 정당하다 — 다만 `설계/08 §D`에 그 결정이 **아직 없다.**

## M4. 계정당 로그인 세션이 **하나뿐**이다 — 두 번째 기기가 첫 기기를 끊는다

**[재현]**

```
1) 기기 A 로그인 -> 200
2) (2초 뒤) 기기 B 로그인 -> 200
3) A로 GET /api/users/me        -> 200      (access가 아직 안 만료라 당장은 멀쩡)

```

**근거**: `RefreshService.saveRefresh`가 저장 전에 `refreshRepository.deleteByUserEntity_Username(username)`으로 **그 사용자의 refresh를 전부** 지운다. DB에는 계정당 refresh 행이 항상 최대 1개다.

**사용자가 겪는 모습 [코드 근거]**: 휴대폰에서 보다가 PC에서 로그인하면, 휴대폰은 **30분 뒤 access 만료 시점에** `authFetch` → refresh 실패 → `auth:expired` → 조용히 게스트로 강등된다. 안내 문구는 없다.

기획서는 다기기 사용을 전제한다 — **AC-G-13**("같은 계정으로 다른 브라우저에서 로그인하면 완료 유닛과 보관함이 그대로 보인다")과 기획 §4-4("비밀번호를 바꾸면 **다른 기기에서는** 다시 로그인해야 해요")는 두 기기가 동시에 로그인된 상태를 정상으로 본다.

**영향**: AC-G-13 자체는 통과한다(로그인 직후에는 보인다). 깨지는 것은 **유지**다. 두 기기를 번갈아 쓰면 매번 다시 로그인해야 한다.

**고치는 비용**: 작음~중간. 단 **H1을 먼저 고쳐야 한다** — 지금 이 전량 삭제가 "같은 초 동일 토큰"의 유니크 충돌 500을 막는 방어로 쓰이고 있다(`RefreshRepository` 주석). **H1과 묶어서 처리할 것.**

## M6. 첨부 단계만 실패해도 **"작성/수정에 실패했습니다"** — 사용자는 다시 눌러 중복을 만든다

**증상**: 본문 저장(`POST`/`PUT`)은 이미 성공했는데 그 뒤 파일 삭제·업로드가 실패하면 같은 `catch`로 떨어져 **"게시글 작성에 실패했습니다"** 알림만 뜬다. 화면 이동도 없다. 사용자가 다시 누르면 **글이 하나 더 생긴다.**

**근거 [코드 근거]**
- `pages/CommunityWritePage.jsx:46-66` — `callApi(POST)` 성공 → `uploadFiles(...)` → 하나의 `catch`에서 `alert("게시글 작성에 실패했습니다.")`. 이미 받은 `communityId`를 버린다.
- `pages/CommunityEditPage.jsx:97-119` — `PUT` 성공 → 파일 삭제 루프(`:106-111`, 실패 시 `throw`) → 신규 업로드(`:113-115`) → 같은 `catch`에서 `alert("게시글 수정에 실패했습니다.")`. 본문은 이미 바뀌었는데 "실패"라고 말한다.

**[재현] — 중복 생성 자체는 서버에서 확인했다** (같은 제목·본문 5개 동시 POST)
```

GET /api/communities?searchType=title&keyword=중복 제출 테스트 -> "totalElements":5
```
서버에 중복 방지가 없으므로 위 재시도 흐름은 그대로 중복 글이 된다.
(화면 버튼 자체는 `disabled={loading}`이라 **단순 연타는 막힌다** — 이 건은 연타가 아니라 **잘못된 실패 안내로 유도된 재시도**다.)

**영향**: 첨부가 있는 글에서만 발생하지만, 발생하면 사용자가 지워야 할 쓰레기 글이 남는다. 수정의 경우 "실패"를 믿고 다시 고치므로 상태 파악이 어렵다.

**고치는 비용**: 작음. 본문 저장 성공 뒤에는 상세로 이동시키고 첨부 실패는 **별도 문구**로 알린다("글은 저장됐어요. 첨부만 실패했어요").

## M8. 탈퇴해도 **로그인 아이디(`username`)가 공개 API에 그대로 남는다**

**증상**: 기획 §4-5는 *"작성자 이름을 '탈퇴한 회원'으로 바꿔 **개인을 식별할 수 없게 한다**"* 고 약속한다. 닉네임은 바뀌지만 `username`은 안 바뀐다.

**[재현]** — user12로 글·댓글을 쓰고 탈퇴한 뒤 **비로그인**으로 조회

```json
GET /api/communities/1001
{"id":1001,"userId":12,"username":"user12","nickname":"탈퇴한 회원","title":"탈퇴 전에 쓴 글(QA)", ...}

GET /api/communities/1001/comments
{"content":[{"id":1000,"userId":12,"username":"user12","nickname":"탈퇴한 회원", ...}]}
```

**근거**: `AccountService.anonymizedUsername`(`:185-187`)은 **로컬 계정에 `null`을 돌려준다** — username을 남겨야 같은 아이디 재가입이 계속 막히기 때문이고(AC-A-40, [재현] 재가입 시 409 확인), 그 자체는 의도된 설계다. 문제는 **그 값이 공개 응답 DTO에 실려 나간다**는 것이다.

화면은 `post?.nickname || post?.username`(`CommunityDetailPage.jsx:171`)이라 **눈에는 안 보인다.** 개발자도구·API 직접 호출로는 그대로 보인다. 탈퇴 여부와 무관하게 **모든 회원의 로그인 아이디가 인증 없이 공개**된다는 점도 같다(H2의 대상 목록 수집을 쉽게 만든다).

**영향**: 기획의 익명화 약속이 반만 지켜진다. 보안상으로는 H2와 결합할 때 의미가 커진다.

**고치는 비용**: 작음이지만 **계약 변경**이다. 프론트의 소유자 판정(`post.username === user.username`, `CommunityDetailPage.jsx:25`)이 그 값을 쓰고 있어 대체 판정(`isMine` 플래그 등)이 필요하다 → senior-dev.

## M9. 소셜 로그인을 **취소하면 날것의 JSON 401 화면**이 뜬다 — 돌아갈 길이 없다

**[재현]** — 카카오 동의 화면에서 [취소]를 눌렀을 때 오는 것과 같은 콜백

```
GET /login/oauth2/code/kakao?error=access_denied&error_description=user_cancel&state=abc
-> HTTP/1.1 401
   Content-Type: application/json;charset=UTF-8
   {"timestamp":"2026-08-24T23:05:16.886+00:00","status":401,"error":"Unauthorized",
    "message":"No message available","path":"/login/oauth2/code/kakao"}
```

토큰 교환 실패(`?code=bogus`)도 같다. **이건 fetch 응답이 아니라 브라우저의 최상위 이동**이다 — 카카오가 리다이렉트로 보낸 주소이므로 사용자는 흰 화면에 영어 JSON을 보게 되고 **뒤로가기 말고는 나갈 길이 없다.**

**근거**: `SecurityConfig.java:151-154`

```java
.failureHandler((request, response, exception) -> {
    log.error("OAuth2 login failed", exception);
    response.sendError(HttpServletResponse.SC_UNAUTHORIZED);
}));
```

`sendError`라서 Spring 기본 `/error` 본문이 나간다 — 이 프로젝트의 에러 봉투(`success/message/errorCode`)도 아니고 한국어도 아니다. 성공 경로는 반대로 잘 돼 있다(`OAuth2LoginSuccessHandler`가 화면으로 리다이렉트).

**영향**: 소셜 로그인을 시도했다가 마음을 바꾸는 것은 **가장 흔한 이탈 경로**다. 그 사람이 사이트 밖으로 튕겨 나간다.

**고치는 비용**: 매우 작음(30분). `failureHandler`에서 `/login?error=...`로 리다이렉트하고 로그인 화면이 그 파라미터를 문구로 읽으면 된다. 계약 변경 없음.

**고치는 비용**: 매우 작음. ① `readDoc`에서 `lastPosition`의 필수 필드를 검사해 없으면 버린다 ② 400은 [다시 시도] 대신 "기록을 합칠 수 없어요 — [이 브라우저 기록 지우기]"로 바꾼다.

# 수동 확인 필요 (실기기·브라우저로만 확인 가능)

이 감사에서 **확인하지 못했다.** "통과"가 아니다.

- **M1(헤더 닉네임) · M2(로그인 복귀) · L1 · L2(0인 칸 문구)** — 서버 응답과 코드 근거로 판정했다. **화면에서 눈으로 한 번 봐야 한다.**
- **M7 댓글 연타** — 실제 마우스 더블클릭으로 댓글이 2개 달리는지.
- **게스트 저장소 실동작** — `localStorage["jp.guest.v1"]`이 실제로 쓰이고 읽히는지, 브라우저 기록 삭제 후 사라지는지(AC-G-01~06).
- **병합 배너 3선택** — [합치기]/[내 기록 아니에요]/[✕]의 화면 동작과 재로그인 시 재노출(AC-G-07~11).
- **별(☆) 클릭이 행 클릭으로 번지지 않는지**(AC-B-03), 빼기 후 되돌리기 5초 타이머(AC-B-18·19).
- **네트워크 끊김 시나리오** — AC-P-26·27(자동 저장은 조용히, 손 토글은 알림), AC-B-24(별 되돌림).
- **모바일 레이아웃·다크 모드** — 이 감사는 API와 코드만 봤다.

# 확인 못 한 것 (환경 제약)

- **소셜 로그인 완주(카카오·구글)** — 실제 제공자 계정이 필요하다. 시작 리다이렉트(302)와 **실패 콜백(M9)** 까지만 확인했다.
  따라서 **소셜 계정의 마이페이지 분기(AC-A-14~19)** — 비밀번호 변경 메뉴 미노출, 이메일 읽기 전용, 탈퇴 시 `탈퇴합니다` 입력 — 는
  **코드와 플래그(`emailEditable`·`passwordChangeable`)로만 확인했고 실제 소셜 세션으로는 시험하지 못했다.**
- **앱(Flutter)과의 크로스 플랫폼 대조** — 저장소에 앱 코드가 없다(CLAUDE.md "아직 미도입"). `/api/oauth2/providers/{provider}/tokens`도 호출하는 앱이 없어 400(토큰 검증 실패)까지만 확인했다.
- **토큰 자연 만료 후 동작** — access 30분 / refresh 4시간. 시간 경과가 필요해 시험하지 못했다. (강제 무효화 경로는 전부 확인했다.)
- **운영(MySQL) 환경** — 로컬 H2(in-memory) 기준이다. 특히 M5(324KB 본문)의 컬럼 타입 한계는 MySQL에서 다르게 나타날 수 있다.

## 재현 방법

서버를 8083에 띄운 뒤. **웹과 같은 쿠키 흐름을 쓰려면 `Accept`에 `text/html`이 있어야 한다** —
없으면 `JwtLoginFilter`가 앱 요청으로 판단해 토큰을 **바디로만** 준다(`JwtLoginFilter.java:80-98`).

```bash
# 로그인 (웹 = 쿠키 모드). 로컬 시드 계정: gks930620 / 1234
curl -s -c cj.txt -X POST http://localhost:8083/api/login \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/html' \
  -d '{"username":"gks930620","password":"1234"}'

# H1 — 같은 초에 로그인한 두 세션이 같은 토큰인지
curl -s -c x1.txt -X POST ... & curl -s -c x2.txt -X POST ... & wait
grep refresh_token x1.txt; grep refresh_token x2.txt      # 값이 같으면 재현

# H2 — 로그인 실패 반복 (지연·잠금이 생기는지)
for i in $(seq 1 15); do curl -s -o /dev/null -w '%{http_code} ' \
  -X POST http://localhost:8083/api/login \
  -H 'Content-Type: application/json' -d '{"username":"user4","password":"wrong"}'; done

# H3 — 영어 코스가 마지막 위치에 들어간 뒤 일본어 주소로 조회
curl -s -b cj.txt -X PUT http://localhost:8083/api/progress/last-position \
  -H 'Content-Type: application/json' -d '{"courseId":101,"unitNo":1,"stepKey":"vocab"}'
curl -s http://localhost:8083/api/courses/101/units/1        # -> 404

# M5 — 목록 응답 크기
curl -s 'http://localhost:8083/api/communities?page=0&size=10' | wc -c
```

> **QA가 이 서버에 남긴 흔적**: 로컬 H2는 `jdbc:h2:mem:devdb`(인메모리)라 **서버를 재시작하면 전부 사라진다.**
> 재시작 전까지는 다음이 남아 있다 — `user12` **탈퇴 처리됨**(로그인 불가, 글 1001은 "탈퇴한 회원"으로 남음),
> 가입 계정 3개(`qatest3`, `qa test<>`, `한글아이디`), 게시글 1001.
> 그 밖의 테스트 글·진도·보관함·닉네임·비밀번호는 **원상 복구했다.**
