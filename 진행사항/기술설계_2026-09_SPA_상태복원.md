## 0. 무엇이 "안 되는" 것인가 — 원인 셋

| 사용자가 겪는 것 | 실제 원인 | 어디서 |
|---|---|---|
| 목록에서 글을 열었다가 돌아오면 **스켈레톤부터 다시** | 조회 훅 `useApiQuery`에 캐시가 없다 — 마운트마다 재요청, 그동안 `loading=true` | 훅 사용처 11곳 + 직접 fetch 8곳 |
| 돌아오면 **맨 위(또는 엉뚱한 곳)** 에 떨어진다 | SPA는 문서가 하나라 브라우저가 스크롤을 대신 맞추지 않는다. `<BrowserRouter>`에 복원 장치가 없다 | 전 화면 |
| 새로고침하면 **보던 상태가 사라진다** | 일부 상태가 URL이 아니라 컴포넌트 state에만 있다 | 댓글 페이지 1건(§3 전수 표). 나머지는 이미 URL이거나 **의도적으로** 메모리 |

세 원인은 서로 얽혀 있다 — **뒤로가기의 스크롤 복원은 콘텐츠가 그려진 뒤여야** 하는데, 캐시가 있으면 뒤로가기의 첫 렌더가 이미 콘텐츠라 복원이 즉시 맞는다. 그래서 **캐시(§1)를 먼저, 스크롤(§2)을 그 위에** 얹는다(§5 순서).

## 1. 결정 1 — 서버 응답 캐시: `useApiQuery` 확장(stale-while-revalidate). React Query는 도입하지 않는다

### 1-1. 왜 확장인가 (도입하지 않는 이유)

| 기준 | 판단 |
|---|---|
| 규모 | 페이지 27개 · 조회는 **공개 GET**(`callPublicApi`)이 전부. 훅 사용처 11곳. 인증 GET을 훅으로 조회하는 곳은 0곳 |
| 필요한 기능 | "캐시 있으면 즉시 표시 + 뒤에서 재요청 + 결과로 교체" 하나. 재시도·폴링·옵티미스틱·무한스크롤은 이 제품에 없다 |
| 컨벤션 | CLAUDE.md "새 라이브러리 도입은 근거 있을 때만"·컨벤션 §7 "반복되는 fetch/loading/error 패턴은 커스텀 훅으로" — **이미 그 훅이 있다.** 확장으로 안 되는 이유가 없다 |
| 비용 | React Query면 `QueryClientProvider` + 11곳 시그니처 교체 + 테스트 픽스처 전면 수정 + 번들 +~13KB(gz). 얻는 것은 위 한 줄과 같다 |

**08 C-1("캐시를 두지 않는다")과의 관계**: C-1은 **서버의 파생값 캐시**(레벨 계산)에 대한 결정이고, 우려는 "무효화 규칙이라는 새 복잡도"였다.
여기서 두는 캐시는 **"무엇이 참인가"가 아니라 "무엇을 먼저 보여줄까"만 정한다** — 마운트마다 반드시 재요청하므로
낡은 값은 한 왕복 안에 스스로 고쳐지고, 무효화가 필요한 곳은 **"내가 방금 쓴 것"이 보이는 화면**(커뮤니티 쓰기 뒤 목록·댓글)뿐이다.
→ `08 C-23`으로 기록했다. C-1은 그대로 유효하다.

### 1-2. 계약 (테스트: `hooks/useApiQuery.cache.test.jsx` — 기존 `useApiQuery.test.jsx`는 그대로 유효)

```js
useApiQuery(url, { keepPreviousData = false } = {})
  → { data, loading, error, reload }
export function invalidateQueries(prefix)   // prefix로 시작하는 URL 항목 삭제 + 떠 있는 훅은 데이터 유지한 채 재요청
export function clearQueryCache()           // 전부 삭제(재요청 없음)
export const QUERY_CACHE_MAX                // 항목 상한
```

| 항목 | 규칙 |
|---|---|
| 캐시 키 | **요청 URL 문자열 그대로**(쿼리스트링 포함). 모듈 수준 `Map`. `url == null`이면 캐시도 요청도 없음(현행) |
| 히트 | 첫 렌더에서 `data=캐시, loading=false` — 기다리지 않는다. 동시에 **재검증 요청**을 보내고 결과로 `data`를 교체한다. 교체 중에도 `loading=false`(스켈레톤·흐림을 얹지 않는다 — 05 §8) |
| 미스 | 현행과 같다(`loading=true` → 응답) |
| 재검증 실패 | **캐시를 버리고 error를 그대로** 낸다(`data=null`). 지워진 글은 404 카드가 맞다. 잠깐의 통신 실패에 옛 화면을 유지하는 것보다 정직한 쪽을 택했다 — 지금(캐시 없음)과 같은 결과다 |
| in-flight 합류 | 같은 URL 요청이 진행 중이면 새 요청을 만들지 않고 그 Promise에 합류한다(홈·마이페이지·코스 상세가 `/api/courses`·`/api/en/courses`를 겹쳐 부른다. StrictMode 이중 마운트도 흡수) |
| `keepPreviousData` | URL이 바뀌고 새 URL이 **미스**면 `data`는 이전 URL 값을 유지한 채 `loading=true`. 새 URL이 히트면 즉시 그 값. **옵션 없이는 현행대로 이전 데이터를 버린다**(상세 화면이 다른 항목을 잠깐 보여주면 안 된다 — `useApiQuery.test.jsx` 4번) |
| `reload()` | 데이터가 있으면 유지한 채 재요청, 없으면(에러 뒤) `loading=true`로 재요청(현행) |
| `invalidateQueries(prefix)` | `url.startsWith(prefix)`인 항목 삭제 + 그 URL로 떠 있는 훅에 재요청(데이터 유지). 호출 시점: **커뮤니티 글 작성·수정·삭제 뒤 `"/api/communities"`**, **댓글 작성·수정·삭제 뒤 `` `/api/communities/${id}/comments` ``** |
| `clearQueryCache()` | 전부 삭제. **`AuthProvider.login`·`logout`(finally)** 에서 호출 — 지금은 공개 GET만 캐시하지만 인증에 따라 응답이 갈리는 GET이 훗날 훅에 들어와도 남의 화면이 새지 않게 |
| 상한 | `QUERY_CACHE_MAX = 50` 항목(코스 6 + 자료실 몇 페이지 + 상세 몇 개면 충분). 넘으면 **가장 오래된 항목부터** 삭제(Map 삽입 순서). 응답 하나가 커야 수십 KB(자료실 100건)라 최대 수 MB — 문제 없음 |
| 테스트 격리 | `test/setup.js`가 매 테스트 뒤 `clearQueryCache()`·`sessionStorage.clear()`를 부른다(이미 들어 있음) |

### 1-3. 05 §8 "부분 교체·갱신 로딩"과의 관계 — 규칙을 막고 있던 사정을 없앤다

05 §8은 페이지·필터 변경을 **"기존 목록을 유지하고 흐리게(`.list-loading`)"** 로 정했고 자료실 3화면이 그 클래스를 이미 붙이고 있다.
그런데 `useApiQuery`가 URL이 바뀌는 순간 `data`를 `null`로 떨어뜨려 **그 코드는 한 번도 실행된 적이 없다** — 실제로는 매번 스켈레톤이다.
`useLibraryList`가 `keepPreviousData: true`를 켜면 문서대로 동작한다(테스트: `pages/LibraryGrammarPage.pageBlur.test.jsx`).
캐시 히트(뒤로가기·재방문)는 §8 표에 **세 번째 줄**로 추가했다: *즉시 표시, 재요청은 조용히*.

## 2. 결정 2 — 스크롤 복원: `<BrowserRouter>` 유지 + 자체 훅 `useScrollRestoration`

### 2-1. 왜 데이터 라우터 `<ScrollRestoration/>`이 아닌가

- **핵심 난점이 그쪽으로는 안 풀린다.** 뒤로가기의 콘텐츠는 비동기로 온다(스켈레톤 → 데이터). RR의 `<ScrollRestoration/>`은 `navigation.state==='idle'` 직후, 즉 **스켈레톤 높이일 때** 복원해 브라우저가 끝에서 잘라 버린다. loader를 쓰지 않는 이 프로젝트에서는 "콘텐츠 준비"를 라우터에 알릴 길이 없다.
- 전환 비용: `createBrowserRouter` + `RouterProvider`로 바꾸면 `App.jsx` 라우트 표(08 C-20이 고정)·테스트 헬퍼(`MemoryRouter` 기반 60여 파일)가 흔들린다. 얻는 것은 위 문제를 못 푸는 복원기 하나다.
- 자체 훅은 60줄 안팎이고 **"문서가 목표 높이에 닿을 때까지 기다린다"** 를 직접 넣을 수 있다.

### 2-2. 계약 (테스트: `hooks/useScrollRestoration.test.jsx`)

```js
// frontend/src/hooks/useScrollRestoration.js (새 파일)
export function useScrollRestoration()          // Layout에서 한 번만 호출
export const SCROLL_STORAGE_KEY = "jp.scroll.v1" // sessionStorage: { [location.key]: y }
export const SCROLL_RESTORE_TIMEOUT_MS = 3000    // 준비 대기 상한
```

| 상황(`useNavigationType`) | 동작 |
|---|---|
| **PUSH** (링크·페이지 버튼·필터 칩) | `window.scrollTo(0, 0)` — 05 §9 "페이지 이동 시 목록 상단" 그대로 |
| **REPLACE** (검색 디바운스 `?q=`, 보관함 기본 탭 보정, `useRouteNotice`의 state 비우기, 댓글 `?cpage=`) | **아무것도 하지 않는다.** 입력 중인 화면·본문 아래 댓글이 튀면 안 된다 |
| **POP** (뒤로/앞으로) · **첫 마운트**(새로고침 포함 — MemoryRouter/BrowserRouter 모두 첫 항목은 POP) | 저장된 `y`가 있으면 **준비 대기 후** `scrollTo(0, y)`. 없으면 `scrollTo(0, 0)` |
| 저장 | `scroll` 이벤트마다(passive, rAF로 합쳐도 됨) 현재 `location.key`에 `window.scrollY`를 기록. **key는 `useLayoutEffect`에서 갱신**한다 — 새 화면이 짧아 브라우저가 스크롤을 잘라내며 쏘는 `scroll` 이벤트가 **옛 key의 값을 덮어쓰지 않게** |
| 저장소 | `sessionStorage["jp.scroll.v1"]`(JSON, 최대 50 key — 넘으면 오래된 것부터). 새로고침을 견디고 탭을 닫으면 사라진다. RR이 `history.state.key`를 보존하므로 새로고침 뒤 `location.key`가 같다(MemoryRouter 첫 항목 key는 `"default"` — 테스트가 그 값을 쓴다) |
| 준비 대기 | `document.documentElement.scrollHeight - window.innerHeight >= y`가 될 때까지 **rAF마다 확인**(ResizeObserver는 jsdom에 없고, rAF는 있다). 되면 1회 `scrollTo`. `SCROLL_RESTORE_TIMEOUT_MS` 안에 안 되면 **그 시점에 1회 적용하고 끝**(브라우저가 잘라도 지금과 같다). `y === 0`이면 기다리지 않는다 |
| 사용자 개입 | 대기 중 `wheel`·`touchmove`·`keydown`이 오면 **복원을 포기**한다(사용자의 손을 이기지 않는다) |
| 브라우저 자동 복원 | 마운트 시 `history.scrollRestoration = "manual"`(지원 시). 켜 두면 popstate 직후 브라우저가 먼저 잘린 위치로 튀고 우리가 다시 옮겨 두 번 움직인다 |
| 정리 | 언마운트·다음 이동 시 rAF 루프·리스너 해제(테스트의 act 경고 방지) |
| 배선 | `components/Layout.jsx`에서 `useScrollRestoration()` 한 줄. `App.jsx`·`main.jsx`는 그대로 |

### 2-3. `UnitStudyPage`의 스텝 전환 `scrollTo({top:0})`(667행)과의 관계

**별개이고 그대로 둔다.** 스텝 전환은 같은 주소 안의 상태 변화라 라우터 이벤트가 없고, 훅은 관여하지 않는다.
스텝은 URL에 넣지 않으므로(§3 — 05 §9) 충돌할 일도 없다. 훅이 관여하는 것은 유닛 **주소**가 바뀔 때(PUSH → 맨 위, POP → 보던 위치)뿐이다.
단, 유닛 화면의 POP 복원값은 "마지막 스텝을 보던 스크롤"인데 재진입 시 열리는 스텝은 진도 복원(`restoredIndex`)에 따르므로 높이가 다를 수 있다 —
준비 대기가 "닿을 수 있는 만큼"으로 처리한다. 더 정교하게 만들 이유는 없다(스텝 전환마다 어차피 맨 위로 간다).

## 3. 결정 3 — 27개 화면 전수 표: 새로고침·뒤로가기에서 사라지면 안 되는 것

판정 기준(우선순위 순): ① `05 §9`가 이미 정한 것은 그대로(주소 = 검색어·필터·정렬·페이지 / **순간 상태는 주소 금지**) ② 진도 저장이 이미 복원하는 것은 URL로 옮기지 않는다(같은 사실을 두 곳에 두지 않는다 — 08 C-7) ③ **입력 중인 글·퀴즈 진행·되돌리기·대화상자**는 URL 금지(공유 링크에 남으면 안 되고 히스토리를 더럽힌다) ④ 서버 데이터는 §1 캐시가 답이지 URL의 일이 아니다.

`지금` 열: **U** = URL(쿼리·경로) · **S** = 컴포넌트 state · **R** = 라우터 state(`location.state`, 새로고침엔 남고 공유엔 안 남음) · **L** = localStorage · **D** = 서버(진도) · **C** = 서버 응답(캐시 대상)

| # | 화면 | 상태 | 지금 | 어디로 | 근거 | 테스트 |

## 4. 결정 4 — 실력 진단 세션 보존 **제안**(설계만. 코드·테스트·09·기획서는 이 문서가 건드리지 않는다)

> ⛔ **2026-09-20 사용자 판정: 반려.** 진단은 새로고침을 견디지 않는다 — 지금 규칙(기획 A36 *"새로고침하면 사라져요"*) **그대로 둔다.**
> 따라서 **A36 · 09 §3-6 · 화면 문구 두 곳은 고치지 않는다.** 아래 제안은 지우지 않고 남겨 둔다(다시 논의될 수 있다) — 되살리려면 이 판정부터 뒤집어야 한다.

**문제**: 09 §3-6 "새로고침·뒤로가기는 레벨 고르기로 되돌리고 기록도 지운다"는 의도된 규칙(기획 A36)이다.
그런데 사용자의 불만이 정확히 "새로고침하면 사라진다"이고, 2차 개편으로 진단이 **여러 판을 이어 치는 구조**가 되어 잃는 것이 커졌다
(N5→N4→N3 세 판을 치고 결과 표를 보다가 새로고침 한 번이면 전부 사라진다).

**안 — `sessionStorage["jp.diagnosis.session.v1"]`** ("저장"이 아니라 "이 탭이 살아 있는 동안 기억")

| 무엇을 | 값 |
|---|---|
| 저장 | `{ selectedLevelCode, results[](판 기록), phase, activeLevel, questions[](생성된 문항 — 보기 순서·정답 포함), answers[], lastRound }` — 즉 화면 state 전부. 문항까지 저장하는 이유: 재생성하면 다른 문항이 나와 "고른 답"이 무의미해진다 |
| 언제 쓰나 | state가 바뀔 때마다(effect) |
| 언제 지우나 | ① 결과 화면에서 **코스로 나가는 링크**를 누를 때(진단은 지나가는 문 — 05 §15-2) ② 탭을 닫을 때(sessionStorage 성질) ③ 명시적 [처음부터 다시] — **없던 버튼이라 planner 결정 필요**. 지금 규칙은 "지우는 길은 새로고침뿐"(09 §3-2-1)인데 새로고침이 보존하면 지우는 길이 사라진다 |
| 복원 | 마운트 시 저장분이 있으면 그 `phase`로 연다. 코스 목록(`/api/courses`)이 바뀌어 `activeLevel`이 목록에 없으면 저장분을 버린다 |
| A36과의 양립 | 양립하지 않는다 — **A36 개정이 필요**하다: "새로고침해도 진행 중인 판과 판 기록이 남는다(같은 탭). 탭을 닫거나 코스로 나가면 사라진다. 계정에 저장되지 않는다." 화면 문구 두 곳(`결과는 저장되지 않아요.` / `지금까지 친 레벨 기록은 저장되지 않아요. 새로고침하면 사라져요.`)도 "계정에 저장되지 않아요 — 이 탭을 닫으면 사라져요"로. 09 §3-6 마지막 줄·§3-2-1 "기록의 수명"·기획 E19도 함께 |
| 08 F-21과의 관계 | F-21(퀴즈·진단 결과 미저장)은 **서버 저장**을 안 한다는 결정이다. 탭 세션 보존은 서버에 아무것도 남기지 않으므로 F-21을 뒤집지 않는다 |
| 비용 | 진단 화면 파일 하나 + `lib/diagnosisSession.js`(직렬화·복원·유효성) + 테스트. 3차(미응답 필수) 구현이 끝난 뒤 별도 파이프라인 |

> **사용자에게 보여줄 한 단락**: 실력 진단은 지금 "결과를 저장하지 않는다"가 규칙이라 새로고침하면 고른 레벨·친 판의 기록·풀던 답이 전부 사라집니다. 이걸 **브라우저 탭이 살아 있는 동안만 기억하는 방식(sessionStorage)** 으로 바꾸면, 새로고침해도 보던 결과 표와 풀던 문항이 그대로 돌아오고, 탭을 닫거나 결과에서 코스로 나가면 깨끗이 사라집니다. 계정에는 여전히 아무것도 저장되지 않습니다. 대신 "새로고침하면 사라져요"라는 안내 문구와 기획 조건 하나(A36)를 "이 탭을 닫으면 사라져요"로 고쳐야 하고, "처음부터 다시" 하고 싶을 때 누를 버튼을 하나 둘지 정해야 합니다(지금은 새로고침이 그 역할). 진단 3차 작업이 끝난 뒤 별도로 진행하면 됩니다 — 하시겠습니까?
