# 높음

## H1. H2 콘솔이 **운영에서도 켜진 채** 배포된다 — 미인증으로 DB 콘솔 로그인 화면이 열린다

**증상**

`spring.h2.console.enabled: true`가 **기본 `application.yml`에 있고 `application-prod.yml`이 이를 덮지 않는다.**
프로파일 yml은 자기가 선언한 키만 덮으므로, prod로 떠도 이 값은 `true`로 남는다.
SecurityConfig는 `/h2-console/**`를 **무조건 permitAll + CSRF 예외 + frameOptions sameOrigin**으로 열어 둔다.

**재현 / 근거**

- **[재현]** 로컬 8083: `GET /h2-console` → `302 → /h2-console/`, `GET /h2-console/` → **200**
- **[재현]** `src/main/resources/application.yml:40-42`
  ```yaml
  h2:
    console:
      enabled: true   # http://localhost:8083/h2-console
  ```
- **[재현]** `src/main/resources/application-prod.yml` 전문에 `spring.h2.console` 키가 **없다**
  (`grep -n "h2" application-prod.yml`의 히트는 전부 `oaut**h2**`·`code/kakao` 오탐이었다)
- **[재현]** `build.gradle:63` `runtimeOnly 'com.h2database:h2'` → H2는 **런타임 클래스패스**라 bootJar에 들어간다.
  프로파일은 클래스패스를 바꾸지 않으므로 **로컬에서 콘솔이 뜬다는 것 자체가 운영 아티팩트에도 서블릿이 있다는 증거**다.
- **[재현]** `H2ConsoleAutoConfiguration`의 조건은 `@ConditionalOnWebApplication(SERVLET)` +
  `@ConditionalOnClass(JakartaWebServlet)` + `@ConditionalOnProperty(spring.h2.console.enabled)` **셋뿐이다**
  (spring-boot-autoconfigure-3.3.4.jar의 클래스 상수 풀에서 확인). **prod/dev 프로파일 조건이 없다.**
- **[재현]** `SecurityConfig.java:48-55` — permitAll·CSRF 예외·frameOptions sameOrigin
- **[코드판단]** 운영 배포가 아직 없어 실제 운영 URL로는 확인 불가.

**영향**

운영 도메인에 **인증 없이** H2 콘솔 로그인 폼이 노출된다. H2 콘솔은 **임의 JDBC URL 접속**을 허용하는 것이 기능이라,
공격자는 자기 JDBC URL로 접속해 H2 세션을 만들 수 있다(H2 콘솔 노출은 원격코드실행 계열 취약점의 표준 진입점으로 알려져 있다).
운영 MySQL 접속정보를 모르더라도 **내부망 프로빙**과 **콘솔 자체를 통한 코드 실행 시도**가 가능하다.
`X-Frame-Options: SAMEORIGIN`·`nosniff`는 이 경로를 막지 못한다.

> 심각도를 "높음"으로 둔 근거: 방어가 **한 겹도 없다**(인증도, 프로파일 조건도, 네트워크 제한도).
> 다만 **아직 배포 전이라 실피해는 0**이므로 "치명"으로 올리지 않았다.

**고치는 비용**: 매우 작음(30분 이하).
`application-prod.yml`에 `spring.h2.console.enabled: false`를 명시하고,
SecurityConfig의 `/h2-console/**` permitAll·CSRF 예외를 `@Profile`/`@ConditionalOnProperty`로 감싸 **꺼진 환경에는 규칙 자체가 없게** 한다.
(편집 모드가 이미 쓰고 있는 "꺼진 환경엔 빈이 없다" 패턴과 같다 — 같은 문제를 같은 방식으로 푸는 것이 맞다.)

## M1. 10MB 초과 업로드가 **413이 아니라 500**이다 — 컨벤션이 이름까지 짚어 금지한 패턴

**증상**

단일 파일 상한(10MB)을 넘긴 업로드가 `MaxUploadSizeExceededException`을 던지는데
`GlobalExceptionHandler`에 이 핸들러가 없어 **최후의 `Exception` 핸들러가 받아 500**을 준다.

**재현** — 로컬 8083, 12MB 파일 업로드:

```
POST /api/files (files=12MB, refId=0, refType=COMMUNITY, usage=IMAGES)
-> HTTP 500
{"success":false,"message":"서버 내부 오류가 발생했습니다.","errorCode":"INTERNAL_SERVER_ERROR", ...}
```

**근거**

- `src/main/java/com/test/test/common/exception/GlobalExceptionHandler.java` — `@ExceptionHandler` 목록에
  `MaxUploadSizeExceededException`이 없다(405·415는 있다)
- `.claude/skills/code-convention/SKILL.md` §2 — "프레임워크 표준 4xx(400/404/405/**413**)를 500으로 뭉개지 않는다"
- `설계/04_API계약.md` §1-2 에러 코드 표에도 **413이 없다** — 계약에도 구멍이 있다

**영향**

프론트는 500을 "잠시 후 다시 시도"로 그린다. 파일이 큰 것은 **요청을 고쳐야 회복되는 클라이언트 잘못**이라
재시도로 절대 성공하지 않는다 — 이 저장소가 미매핑 404·405·415에서 반복해 없애 온 바로 그 패턴이 여기 한 곳에 남았다.
운영 모니터링에도 서버 장애로 잡힌다.

**고치는 비용**: 작음(1시간). 핸들러 1개 + 계약 표 1행 + 컨트롤러 통합테스트 1건.

| §3 "`course_no` NOT NULL **UNIQUE**" | 실제는 **복합 유니크** `uk_course_language_no(language, course_no)` — 일본어 1(N5)과 영어 1(E1)이 공존해야 하므로 단독 UNIQUE면 시드가 깨진다 |
| 테이블 목록 | `expression` · `expression_example` · `unit_expression` **3개가 통째로 없다**(grep "expression" -> 0건) |
| §5 고정 ID 계약 | 입문·N1이 `PREPARING`·유닛 `—`로 적혀 있다. 실제는 둘 다 AVAILABLE, 합계 유닛 125·문법 295·한자 1,350·어휘 2,016(문서는 90·206·1,000·1,416) |
| §7-1 시드 파일 구성 | N5~N2 4쌍만 있다. 입문·N1·영어 6개 파일이 빠졌다(같은 목록이 `설계/07`에는 **맞게** 적혀 있어 두 문서가 서로 어긋난다) |
| §7-2 ID 대역 | 영어 대역이 없다. 실제 시드는 코스 101~105 / 콘텐츠 9000~9999를 쓴다(`data-course-en-content.sql` 머리 주석) |
| §4 `users` | `token_version`·`withdrawn_at`이 없다. 둘 다 **보안 계약**(토큰 무효화·탈퇴 판정)의 근거 컬럼이다 |

**영향**

ERD는 senior-dev의 산출물이고 콘텐츠 작업자가 **시드를 쓰기 전에 읽는 문서**다.
지금 이 문서대로 새 코스 시드를 쓰면 `level_code`·`language`를 빠뜨려 **INSERT가 NOT NULL 위반으로 실패**한다.
§1의 "레벨 컬럼은 없다"는 더 나쁘다 — 있는 컬럼을 없애는 방향의 리팩터링을 정당화한다.

## M5. OAuth2 `state`가 **브라우저에 결속되지 않는다** — 로그인 CSRF를 막지 못한다

**증상**

커스텀 OAuth2 시작점이 `state`를 UUID로 만들어 **전역 `ConcurrentHashMap`** 에 넣고,
콜백에서 **요청 파라미터의 `state`만으로** 조회한다. 세션도 쿠키도 개입하지 않는다
(세션 정책이 STATELESS라 스프링 기본 구현(HttpSession)을 못 쓴 결과로 보인다).

**근거** — **[코드판단]** (실제 공격은 재현하지 않았다 — 외부 제공자 계정과 실제 인가 코드가 필요하다)

- `jwt/repository/InMemoryAuthorizationRequestRepository.java` — `Map<String, OAuth2AuthorizationRequest>` 전역 필드
- 같은 파일 `loadAuthorizationRequest` — `request.getParameter("state")`로만 조회. **요청자 식별이 없다**
- `jwt/controller/Oauth2LoginController.java` — `String state = UUID.randomUUID().toString();` 후 위 맵에 저장,
  브라우저에는 아무 쿠키도 심지 않는다
- `SecurityConfig` — `.authorizationEndpoint(... authorizationRequestRepository)`로 이 구현이 표준 흐름에도 연결돼 있다

**영향**

`state`의 목적은 "**이 콜백이 내가 시작한 흐름인가**"를 증명하는 것인데, 전역 맵이면 **누가 들고 와도 유효**하다.
공격자가 자기 계정으로 인가 코드를 받아 두고 피해자 브라우저를 `/login/oauth2/code/kakao?code=…&state=…`로 유도하면
피해자 브라우저에 **공격자 계정의 토큰 쿠키가 심긴다**(로그인 CSRF). 이후 피해자가 쌓는 진도·보관함·게시글이 공격자 계정에 남는다.
부수적으로 `removeAuthorizationRequest`가 실제로는 제거하지 않아(주석대로 SuccessHandler가 지운다)
**인증 실패 시 인가요청이 5분간 재사용 가능**하다.

**고치는 비용**: 중간(1일). `state`(또는 그 해시)를 **HttpOnly·SameSite=Lax·짧은 만료 쿠키**에 심고 콜백에서 대조한다.
STATELESS를 유지하면서 표준 동작을 회복하는 정석이 쿠키 기반 `AuthorizationRequestRepository`다.
(파일에 적힌 "다중화 시 Redis 필요" TODO도 같은 수정으로 함께 해소된다 — 지금 구조는 인스턴스가 둘이면 로그인이 깨진다.)

## M6. DB 제약 위반이 전부 **500**이다 — 회원가입에 "조회 후 삽입" 경합이 남아 있다

**증상**

`GlobalExceptionHandler`에 `DataIntegrityViolationException` 핸들러가 없다.
그리고 `JoinService`는 **잠금 없이** `existsByUsername` → `save`를 한다. `users.username`은 UNIQUE다.

**근거**

- **[재현]** `GlobalExceptionHandler.java` — 핸들러 목록에 `DataIntegrityViolationException` 없음
- **[재현]** `jwt/service/JoinService.java` — `existsByUsername(...)` 확인 후 `userRepository.save(...)`
- **[재현]** `jwt/entity/UserEntity.java` — `@Column(unique = true) private String username;`
- **[재현]** 진도·보관함·병합·계정은 `UserRepository.lockForUserDataWrite`로 줄을 세운다 — **회원가입만 그 규칙 밖이다**
- **[코드판단]** 실제 500은 재현하지 못했다. 참고로 같은 사용자 **동시 로그인 6건**은 전부 200이었고
  (`refresh_entity.token` UNIQUE + 같은 초에 발급되면 토큰 문자열이 동일해지는 조합이 의심됐으나) H2에서는 재현되지 않았다.
  MySQL(REPEATABLE READ + 갭 락)에서의 거동은 확인하지 못했다.

**영향**

같은 아이디로 가입 버튼을 더블클릭하면 한쪽이 `DUPLICATE_RESOURCE`(409, 계약 §1-2)가 아니라 **500**이 될 수 있다.
이 저장소는 이미 같은 유형(★ 연타·완료 더블클릭)으로 500을 맞고 잠금을 도입했는데 **가입은 그때 함께 점검되지 않았다.**
더 넓게는, 어떤 제약 위반이든 지금은 전부 500이라 **모니터링에서 클라이언트 잘못과 서버 장애가 구분되지 않는다.**

**고치는 비용**: 작음(2~3시간).
`DataIntegrityViolationException` → 409 `DUPLICATE_RESOURCE` 핸들러 1개(계약에 이미 있는 코드다) +
`JoinService`를 "저장 시도 후 위반이면 409"로 바꾼다. 컨트롤러 통합테스트 1건.

## M7. **웹 쿠키 인증 경로에 백엔드 테스트가 0건**이다 — 실제 사용자가 쓰는 유일한 경로인데 전부 앱(Bearer) 분기만 검증한다

**증상**

`JwtLoginFilter`는 `Accept` 헤더에 `text/html`이 있으면 **쿠키를 심고**, 없으면 **JSON 바디로 토큰을 준다.**
웹은 앞의 분기를 쓴다(`AuthContext.jsx`가 `Accept: "application/json, text/html"`을 보낸다). 그런데 테스트는 **전부 뒤의 분기만** 탄다.

**근거** — **[재현]**

- `grep -rln "text/html" src/test/java` -> **0건** (어떤 테스트도 브라우저 분기를 타지 않는다)
- `grep -rn "MockCookie|\.cookie\(" src/test/java` -> **0건** (쿠키를 심거나 검사하는 테스트가 없다.
  `cookie` 문자열이 나오는 두 곳은 `app.cookie.secure=false` 프로퍼티 선언이다)
- `ApiIntegrationTestSupport.login()`은 `accept(APPLICATION_JSON)`으로 로그인해 `access_token`을 바디에서 꺼낸다
  → 이후 236건 전부가 `Authorization: Bearer`를 쓴다
- 같은 이유로 `RefreshController`·`AccountController#changePassword`의 **웹 분기(Set-Cookie)** 도 미검증이다

**영향**

`Set-Cookie`의 `HttpOnly`·`SameSite=Lax`·`Secure`(운영 true)는 **CSRF를 전면 비활성화한 이 앱의 실질적 방어선**인데,
그 속성이 계약대로 나가는지를 확인하는 테스트가 하나도 없다.
`isBrowser` 판정이나 쿠키 속성이 바뀌어도 **236건이 전부 green**이고, 깨지는 것은 브라우저 사용자뿐이다.
직전 감사가 지적한 "테스트가 로그인부터 해서 비로그인 경로를 못 본" 사각지대와 **같은 형태**다 — 이번엔 축이 인증 방식이다.

**고치는 비용**: 작음(2~3시간). `Accept: text/html`로 로그인해 `Set-Cookie` 3속성을 단언하는 통합테스트 1~2건 +
쿠키만으로 인증되는 요청 1건. senior-dev가 Red로 먼저 쓴다.

**고치는 비용**: 매우 작음. 허용 출처를 환경변수로 빼거나 운영에서 CORS 자체를 끈다(같은 오리진이라 필요 없다).

## L7. 웹/앱 분기가 `Accept` 헤더 **문자열 포함 검사**다

**근거** — `JwtLoginFilter.successfulAuthentication`: `accept.contains("text/html")`이면 쿠키, 아니면 JSON 바디로 토큰.
프론트는 이 분기를 타려고 `AuthContext.jsx`에서 `Accept: "application/json, text/html"`을 **일부러** 보낸다.

**영향**: 지금은 정상 동작한다. 위험은 결합이 **암묵적**이라는 것 —
프론트에서 "쓸데없어 보이는" `text/html`을 지우는 순간, 로그인은 200이지만 쿠키가 안 심기고
브라우저에 **토큰이 JSON 바디로 노출**된다(컨벤션 §7 "토큰을 localStorage에 저장하지 않는다"의 취지와 반대 방향).
그리고 M7 때문에 **어떤 테스트도 이를 잡지 못한다.**

**고치는 비용**: 작음. 분기 기준을 `Authorization: Bearer` 유무(리프레시·비밀번호 변경이 이미 쓰는 기준)로 통일하면
세 경로의 판정 규칙이 하나가 된다. **계약 변경이므로 senior-dev 경유.**

## L8. 통합테스트가 전부 `@Transactional`이라 **지연로딩 회귀를 구조적으로 못 잡는다**

**근거** — **[재현]** `ApiIntegrationTestSupport`에 클래스 레벨 `@Transactional`이 걸려 있고,
`UserDataConcurrencyIntegrationTest`(의도적으로 트랜잭션 밖)를 제외한 **모든 통합테스트가 이를 상속**한다.

테스트 트랜잭션이 열려 있는 동안에는 EntityManager가 스레드에 묶여 있어, 서비스 트랜잭션이 끝난 뒤 DTO가
프록시를 건드려도 **초기화가 성공한다.** 운영은 `open-in-view: false`라 같은 코드가 `LazyInitializationException` → 500이다.

과거 커뮤니티 상세가 정확히 이 방식으로 터졌고(`CommunityDetailContractIntegrationTest` 머리말이 그 사고를 기록한다),
그 회귀 테스트조차 같은 `@Transactional` 안에서 돈다 — **fetch join을 다시 제거해도 그 테스트는 통과할 가능성이 높다.**

**현재 실제 결함은 없다** — 공개 GET 22개를 라이브로 전수 호출해 전부 200이었다(아래 "확인했으나 문제 없음").
따라서 이것은 **결함이 아니라 사각지대**다.

**고치는 비용**: 중간. 전면 변경은 비싸다(모든 테스트가 롤백에 기대 정리를 하고 있다).
현실적인 선택은 **지연로딩이 얽힌 상세 API 몇 개만** 트랜잭션 밖 테스트로 따로 두는 것이다
(`UserDataConcurrencyIntegrationTest`가 이미 그 패턴의 선례다).
