# 09. 학습 도구 동작 규칙 (퀴즈 · 진단 · 음성)

> **이 문서가 원본이다.** 퀴즈 문항 생성, 실력 진단 계단·추천, 음성(TTS) 동작의 규칙은 전부 여기에 있다.
> 코드가 규칙을 인용할 때는 **`설계/09 §x-y`** 를 적는다. 임시 계약 문서(`진행사항/2026-08-18_학습도구_관리자_계약.md`)를 인용하지 않는다 —
> 그 문서는 지워질 문서다.
>
> **왜 05(디자인 시스템)나 04(API 계약)가 아닌가**: 이 규칙들은 **서버와의 약속이 아니고**(퀴즈·진단·음성은 순수 프론트다),
> **색·간격·컴포넌트 재사용 규칙도 아니다**(05의 정의를 흐린다). 성격이 다른 것을 남는 문서에 밀어 넣으면
> 다음 사람이 그 문서의 정의를 못 믿게 된다. 게다가 **앱(Flutter)이 오면 같은 규칙을 다시 구현**해야 하는데,
> 그때 뒤질 곳은 디자인 문서도 API 문서도 아니다. 문서 하나를 늘리는 비용보다 **원본 주소가 흔들리는 비용**이 크다(08 C-18·C-19).
>
> 화면이 이 규칙을 **어떻게 보여주는가**(카드 레이아웃·버튼 프리셋·상태별 UI)는 `설계/05 §15`에 있다. 둘은 교차 참조로 잇는다.

**구현 위치**: `frontend/src/lib/quiz.js` · `frontend/src/lib/diagnosis.js` · `frontend/src/lib/tts.js` · `frontend/src/components/ttsStore.js`
— 전부 **순수 함수 + RNG 주입**(`rng: () => number`, 0 ≤ x < 1)이다. 무작위가 들어가는 규칙을 테스트로 고정할 수 있는 이유가 이것이다.

## 1. 퀴즈 문항 생성

### 1-1. 문항 하나의 모양

```js
{
  id: "kanji-reading-12",        // `${유형}-${대상 id}` — 한 세트 안에서 유일
  type: "KANJI_READING",         // 아래 11종 중 하나 (일본어 8 + 영어 표현 3)
  prompt: { main: "遵", sub: "이 글자의 음독은?" },
  choices: ["ジュン", "シュン", "ソン", "セン"],   // 항상 4개, 전부 서로 다른 문자열
  answerIndex: 2,                                  // 자리는 rng로 섞는다
  evidence: { ... }                                 // 채점 후 근거 — 원본 항목 그대로
}
```

### 1-2. 유형 11종과 생성 조건 (일본어 8 + 영어 표현 3)

> 2026-09-03 정정: 이 절은 "8종"이라 적혀 있었지만 `lib/quiz.js`는 영어 표현 3종(`EXPRESSION_*`)을 이미 만들고
> `lib/quizEn.test.js`가 고정하고 있었다 — 문서가 코드의 3/11을 몰랐다. 영어 **화면**에서 퀴즈를 켜지 않는 것(§5)과
> 생성기가 영어 재료를 **만들 수 있는 것**은 다른 사실이다. 둘 다 여기 적는다.

| type | 재료 조건 (없으면 그 유형을 만들지 않는다) | 오답 풀 |
|---|---|---|
| `KANJI_READING` | `onyomi` 또는 `kunyomi`가 있는 한자. 음/훈은 있는 쪽에서 rng로 고른다 | 다른 한자의 **같은 종류** 읽기 |
| `KANJI_MEANING` | 항상 가능(`meaningKo`는 NOT NULL) | 다른 한자의 `meaningKo` |
| `KANJI_WORD_READING` | `kana`가 있는 예시 단어가 1개 이상 | 다른 예시 단어의 `kana` |
| `VOCAB_MEANING` | 항상 가능 | **같은 `partOfSpeech` 우선**, 3개를 못 채우면 범위 전체에서 보충 |
| `VOCAB_WORD` | 항상 가능(뜻 → 단어, 역방향) | 다른 어휘의 `word` |
| `VOCAB_READING` | **`kana`가 있는 어휘만** — kana 계약(06 §1)이 곧 출제 가능 여부다 | 다른 어휘의 `kana` |
| `GRAMMAR_CLOZE` | 예문 `jp`에 그 문법 표현이 **실제로 들어 있을 때만**(표현 = `name`에서 선행 `〜` 제거). 못 찾으면 그 문법은 `GRAMMAR_MEANING`으로 낸다 | 다른 문법의 `name` |
| `GRAMMAR_MEANING` | 항상 가능(`nameKo`는 NOT NULL) | 다른 문법의 `nameKo` |
| `EXPRESSION_CLOZE` *(영어)* | 예문 `en`에 표현 `text`가 **실제로 들어 있을 때만**(GRAMMAR_CLOZE와 같은 규칙). 못 찾으면 그 표현은 `EXPRESSION_MEANING`/`EXPRESSION_TEXT`로 낸다 | 다른 표현의 `text` |
| `EXPRESSION_MEANING` *(영어)* | 항상 가능(`meaningKo`는 NOT NULL) | 다른 표현의 `meaningKo` |
| `EXPRESSION_TEXT` *(영어)* | 항상 가능(뜻 → 표현, 역방향) | 다른 표현의 `text` |

영어 3종은 유닛 재료의 `expressions[]`(한자 자리)에서 나오며, **일본어 유닛에는 `expressions`가 없으므로 생성되지 않는다.**
화면에서 영어 퀴즈를 켜는 조건은 §5다 — 생성기가 만들 수 있다고 화면이 켜져 있는 것은 아니다.

빈칸(`GRAMMAR_CLOZE`)을 **표현이 예문에 없는데도 만들면** 빈칸이 엉뚱한 자리에 뚫린다. 그래서 "실제로 포함될 때만"이 조건이다.

### 1-3. 오답 풀은 **같은 레벨에서 먼저** 채운다 (2026-08-25 감사 H2)

1. 1순위는 **출제 범위 안**(유닛이면 그 유닛, 자료실이면 그 조건).
2. 모자라면 **호출자가 준 오답 풀**에서 가져온다. 이 풀은 **같은 레벨로 조회한 것**이어야 한다 —
   유닛 학습은 코스의 `levelCode`로 `GET /api/library/{type}?level={코드}`를 부른다.
3. 정답 대상과 같은 id는 언제나 제외한다.

**레벨 필터 없이 앞에서 100개를 자르면** 자료실이 학습 순서로 정렬돼 있어 낮은 레벨만 담긴다.
실제로 N1 유닛의 문제에 입문 인사말(`これをください`)이 보기로 섞였다 — 그건 문제가 아니라 **레벨 맞히기**다.
**조용히 낮은 레벨로 채우지 않는다.**

### 1-4. 보기 4개를 못 채우면 **그 문항을 건너뛴다**

- 보기 4개는 **전부 서로 다른 문자열**이어야 한다. 정답과 같거나 서로 같은 후보는 버리고 다음 후보로 간다.
- 4개를 끝내 못 채우면 **그 문항 하나를 조용히 버린다.** 세트 실패가 아니다 — 화면은 만들어진 문항 수를 그대로 보여준다.
- 대상(한자·어휘·문법) id는 한 세트에서 **1회만** 쓴다. 같은 한자가 두 유형으로 두 번 나오지 않는다.

### 1-5. 재료 어댑터 — lib에 넘기기 전에 응답을 평탄화한다

`lib/quiz.js`가 받는 것은 **평평한 도메인 항목**이다: `{id, word, kana, meaningKo, partOfSpeech}` ·
`{id, letter, meaningKo, onyomi, kunyomi, words[]}` · `{id, name, nameKo, examples[]}`.

| 출처 | 어댑터 |
|---|---|
| `GET /api/library/vocabulary` | 표제어 1행 = 문항 1개. 뜻은 `senses[0].meaningKo`(병합 표제어 — 04 §3-7). `senses`가 비면 **그 항목은 버린다**(정답이 없다) |
| `GET /api/library/kanji` (목록) | 그대로. 단 `words`가 없어 `KANJI_WORD_READING`은 만들 수 없다 |
| `GET /api/library/grammar` (목록) | 그대로. 단 `examples`가 없어 `GRAMMAR_CLOZE`는 만들 수 없다(뜻 유형만) |
| `GET /api/courses/{c}/units/{u}` | 이미 평평하다 — 어댑터 불필요 |

어댑터 없이 응답을 그대로 넘기면 `meaningKo`가 `undefined`가 되어 보기가 비고 세트가 깨진다(3단계 qa 치명 ②).
어댑터는 화면이 아니라 **`lib/quiz.js`가 export하는 함수**이고, 실제 응답 픽스처(`test/apiFixtures.js`)로 검증한다(08 C-9).

## 2. 세트 구성 — 몇 문제를 낼 것인가

### 2-1. 유닛 확인 문제 (최대 10문항)

**확인 문제 스텝은 어휘 다음, 정리 앞이다.** 유닛 스텝 순서는
`문법(2~3) → 회화 → 한자(있을 때) → 어휘 → 확인 문제(일본어만) → 정리` 로 고정이고, **정리가 언제나 마지막 스텝**이다.
[다음 유닛 ›](코스 마지막이면 다음 코스 / 코스 목록)는 **정리에만** 있고, 그 앞 모든 스텝의 전진 버튼은 [다음 ›]다 —
확인 문제 카드(풀기 전·결과)의 전진 버튼도 [다음 ›]이며 **정리로** 간다. 세는 스텝 수 = [다음 ›]로 갈 수 있는 스텝 수.
**문제 풀이는 완료 조건이 아니다** — 건너뛰고 정리에 닿아도 유닛은 완료다(01 §7-1).
(2026-09-03 결정 `진행사항/결정_2026-09_이어서_확인문제.md` §2 — 예전에는 정리 뒤 8번째라 [다음 ›]만으로는 도달할 수 없었다.)
고정 테스트: `frontend/src/pages/UnitStudyPage.stepOrder.test.jsx` (스텝 순서·전진 버튼은 이 파일 한 곳 — 08 C-11).

목표 배분은 **문법 2~3 · 한자 3~4 · 어휘 4**이고, 재료가 모자라면 **만들 수 있는 것부터** 채운다.
**실제 만들어진 문항 수가 세트의 사실이다** — 화면은 그 수를 그대로 보여준다(빈 자리를 메우지 않는다).

**입문 유닛이 6문제인 것은 결함이 아니다** (2026-08-25 판정 M3, 08 C-12 ③):
입문은 문법 2 · 한자 0 · 어휘 15(전부 `kana` 없음)라 **문법 2 + 어휘 4 = 6문항**이 된다.
한자 4문항 자리는 입문이 **한자를 배우지 않아서** 비는 것이고, 그 자리를 어휘로 메우면 6문항 중 어휘가 8이 되어
유형 균형이 깨진다. **문항 수는 목표가 아니라 배운 재료의 결과다. 10은 상한일 뿐이다**(08 §F-13·F-14).
→ 이 결정은 `frontend/src/lib/quiz.introCount.test.js`가 고정하고 있다.

### 2-2. 자료실 퀴즈 (10 / 20문항 선택)

- 들어온 탭의 유형만 낸다(한자 탭 → `KANJI_*` 3유형에서 rng 배분).
- **범위(`totalElements`)가 4개 미만이면 세트를 만들지 않는다** — "이 조건으로는 문제를 낼 수 없어요(4개 이상 필요)" + 자료실 복귀.
  이것이 자료실 목록의 [이 조건으로 문제 풀기] 비활성 근거이기도 하다.

### 2-3. 무작위 창 뽑기와 **꼬리 창 제외** (2026-08-25 감사 A-H3)

자료실 API는 한 번에 최대 100건이다. 범위가 그보다 크면 **무작위 창(page)** 을 뽑아 그 창에서 출제한다 —
늘 앞쪽 100개만 쓰면 "102개 중에서 출제합니다"라는 문장이 거짓이 된다.

**단, 뽑는 창은 4건 이상이 보장되는 창으로 한정한다.**
`q=하` 어휘는 102건·2창이고 마지막 창이 **2건**이라, 그 창을 뽑으면 4개 미만이 되어 **약 50% 확률로 퀴즈가 열리지 않았다.**
조건에 맞는 항목이 `100k+1 ~ 100k+3`이면 언제든 재현된다.

- **"문제를 낼 수 없어요"는 `totalElements < 4`일 때만 나온다** — 뽑은 창의 길이로 판정하지 않는다.
- 무작위 창 뽑기 자체는 유지한다(모집단 편향 회피가 원래 목적이다).

### 2-4. 세트의 수명

- **매 세트 새로 생성**한다. 캐시하지 않는다.
- [틀린 문제만 다시 풀기]는 생성이 아니라 **기존 세트의 부분집합**이다 — 같은 문항·같은 보기 그대로.
- 채점은 **보기 클릭 즉시 클라이언트에서**(정답이 세트 안에 있다). 채점 후 답 변경 불가.
- 유닛 확인 문제의 진행 상태는 **화면 컴포넌트 state**다. 스텝을 오가도 유지되고 유닛을 떠나면 사라진다 —
  저장하지 않는다(퀴즈·진단 결과 미저장, 08 §F-21).

## 3. 실력 진단

### 3-1. 계단 (측정)

- 계단 = **AVAILABLE 코스의 레벨을 낮은 것부터**. 코스명·레벨을 하드코딩하지 않고 `GET /api/courses`에서 계산한다(08 C-6).
- **입문은 계단에 들어가지 않는다** — 단계마다 한자 1문항이 필요한데 입문은 한자가 0자다. 측정할 수 없는 것을 측정하는 척하지 않는다.
- 단계당 **3문항 = 어휘 1 · 한자 1 · 문법 1** 고정. 재료는 `GET /api/library/{type}?level={코드}`로 가져오고 문항 생성은 §1 그대로다.
- **3중 2 통과 → 다음 단계 / 미달 → 즉시 종료.** 최소 3문항, 최대 (계단 수 × 3)문항.
- 진단 중에는 **정오를 표시하지 않는다** — 데이터에는 정답이 있으므로 "보여주지 않는 것"이 규칙이다.

**레벨 표기는 두 가지이고 섞으면 안 된다**(3단계 qa 치명 ①의 뿌리):

| 무엇 | 값 | 쓰는 곳 |
|---|---|---|
| `course.levelLabel` | **표시 문구** — `"JLPT N5"`, 입문은 `"문자"`(N 코드가 아예 없다) | 화면 문구·결과 근거 표 |
| 자료실 `level` 파라미터 | **코드** — `"N5"`. 근거는 **`course.level_code` 컬럼**(응답의 `levelCode`)이지 `levelLabel`도 `courseNo`도 아니다(03 §1 · 04 §3-1 — `courseNo` 파생은 2026-08-20에 폐기됐다, 되돌리지 말 것) | `GET /api/library/**` 필터 |

`stagePlan(courses)`는 단계마다 **`levelCode`와 `levelLabel`을 함께** 준다. 조회에는 코드, 표시에는 문구를 쓴다.
**문자열을 잘라 만들지 않는다** — 입문("문자")처럼 접두 규칙이 통하지 않는 값이 실제로 있다.

### 3-2. 추천 (안내) — 계단과 **다른 목록**을 쓴다 (2026-08-25 감사 H1)

```
통과한 단계 없음              → 입장 가능한 첫 코스 (= AVAILABLE 코스 전체 중 courseNo 최소 — 계단 밖이어도 된다)
레벨 L까지 통과, 다음 단계 있음 → 다음 단계 레벨의 코스
전부 통과                     → 가장 높은 공개 코스 + allPassed
```

- **추천 후보 = AVAILABLE 코스 전체(courseNo 순)** 다. 계단은 측정할 수 있는 레벨만 쓰지만, 계단에 없다고 **추천 대상에서까지 뺄 이유는 없다** —
  1단계에서 떨어진 사람에게 같은 N5를 다시 권하면 히라가나를 모르는 사람이 입문을 건너뛴다. **측정과 안내는 다른 목록이다.**
- 추천은 **준비중 코스를 절대 가리키지 않는다.** 입문이 준비중이면 자동으로 계단 첫 코스로 되돌아간다.
- 반환: `{ recommendedCourseId, stepDownCourseId|null, allPassed, stages: [{levelLabel, correct, total}] }`.
  전부 준비중이면 `null`(배너를 그리지 않는다).
- 결과 화면의 "그 위 코스는 준비 중" 안내는 **실제로 PREPARING 코스가 있을 때만** 그린다 —
  없는 것을 약속하지 않는다(08 C-12 ②). 재료 로딩 실패 시의 대체 경로도 **같은 첫 코스**를 가리킨다.

**단일 기준 테스트**: 추천은 `frontend/src/lib/diagnosis.recommend.test.js` 하나, 측정(계단·문항·통과 임계값)은 `diagnosis.test.js`다(08 C-11).

## 4. 음성 (TTS)

| # | 규칙 |
|---|---|
| 1 | **읽을 텍스트 = `kana ?? 원문`** — kana 계약(06 §1)이 곧 발음 계약이다. `speechTextOf({jp, kana})` 하나로 통일 |
| 2 | **노출 게이트** — `speechSynthesis.getVoices()`에 `lang`이 `ja`로 시작하는 음성이 하나도 없으면 **버튼·속도 칩을 렌더하지 않는다**(안내도 없다). `voiceschanged`까지 기다린 뒤 판정한다(크롬은 목록이 비동기다) |
| 3 | **단일 재생** — 새 재생은 항상 `cancel()` 후 시작. 같은 버튼 재클릭 = 정지. 화면·스텝 이탈 시 cancel |
| 4 | **속도 2단계** — 보통 `1.0` / 느리게 `0.7`. 저장 키 **`jp.tts.v1`**, 로그인 무관 **전역 저장**. 변경은 **다음 재생부터**(재생 중인 utterance는 건드리지 않는다) |
| 5 | **재생 실패**(음성은 있는데 utterance error) — 그 자리 안내 1회, 같은 화면에서 반복 노출 금지 |
| 6 | **utterance 설정** — `lang="ja-JP"`, 첫 번째 ja 보이스 명시 지정. 화자 선택은 없다 |
| 7 | **회화 [전체 재생]** — 줄 배열을 순차 재생, `onend`마다 다음 줄 + 현재 줄 인덱스 콜백(강조는 화면 몫). 개별 버튼이 끼어들면 전체 재생을 취소한다 |

- 한자 글자 단독·활용표에는 버튼을 붙이지 않는다.
- 속도 칩은 **자료실 목록에는 두지 않는다**(2026-08-25 판정 L5): 속도가 전역 저장이라 다른 화면에서 바꾼 값이 목록에도 적용되고,
  목록은 훑는 화면이라 설정 칩이 행 밀도를 흐린다. 필요하다는 판단은 designer의 몫이다.
- **테스트 한계**: 실제 발화·목소리 품질은 jsdom에서 검증할 수 없다. 테스트가 덮는 것은 ①텍스트 선택 ②게이트 ③단일 재생 호출 순서 ④속도 저장까지다.
  실기기 확인은 qa 시나리오(기기 2종 이상)의 몫이다.

## 5. 영어 과정에는 퀴즈·음성을 켜지 않는다

영어 유닛에는 **확인 문제 스텝이 없고 `.tts-*` 요소도 하나도 없다.** 자료실도 같다(퀴즈 진입 버튼 없음).
근거와 되돌리는 조건은 **08 C-14**(뼈대 과정에는 학습 도구를 먼저 켜지 않는다)에 있고,
화면 쪽 표현은 `설계/05 §16`이 함께 본다.

**켜는 이터레이션의 선행 조건 셋**(하나라도 빠지면 2026-08-25 감사 상태로 되돌아간다):
① `QuizRunner`가 `latin`을 받아 `.jp` 조판과 음성 요소를 끈다 ② `Evidence`에 `EXPRESSION_*` 분기를 넣는다(없으면 빈 회색 상자가 3~4문항 나온다)
③ 영어는 ja 보이스가 아니라 en 보이스로 읽는다.

## 7. 코드가 인용할 절 — 인용 지도

임시 계약 문서가 사라지면서 코드 주석 약 50곳이 **가장 가까운 `설계/05 §15-*`로 임시 이관**돼 있다.
