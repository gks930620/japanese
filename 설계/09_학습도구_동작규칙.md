# 09. 학습 도구 동작 규칙 (퀴즈 · 진단 · 음성)

> **이 문서가 원본이다.** 퀴즈 문항 생성, 실력 진단 레벨·추천, 음성(TTS) 동작의 규칙은 전부 여기에 있다.
> 코드가 규칙을 인용할 때는 **`설계/09 §x-y`** 를 적는다. 임시 계약 문서(`진행사항/2026-08-18_학습도구_관리자_계약.md`)를 인용하지 않는다 —
> 그 문서는 지워질 문서다.
>
> **왜 05(디자인 시스템)나 04(API 계약)가 아닌가**: 이 규칙들은 **서버와의 약속이 아니고**(퀴즈·진단·음성은 순수 프론트다),
> **색·간격·컴포넌트 재사용 규칙도 아니다**(05의 정의를 흐린다). 성격이 다른 것을 남는 문서에 밀어 넣으면
> 다음 사람이 그 문서의 정의를 못 믿게 된다. 게다가 **앱(Flutter)이 오면 같은 규칙을 다시 구현**해야 하는데,
> 그때 뒤질 곳은 디자인 문서도 API 문서도 아니다. 문서 하나를 늘리는 비용보다 **원본 주소가 흔들리는 비용**이 크다(08 C-18·C-19).
>
> 화면이 이 규칙을 **어떻게 보여주는가**(카드 레이아웃·버튼 프리셋·상태별 UI)는 `설계/05 §15`에 있다. 둘은 교차 참조로 잇는다.

**구현 위치**: `frontend/src/lib/quiz.js` · `frontend/src/lib/diagnosis.js` · `frontend/src/lib/tts.js` · `frontend/src/components/ttsStore.js`
— 전부 **순수 함수 + RNG 주입**(`rng: () => number`, 0 ≤ x < 1)이다. 무작위가 들어가는 규칙을 테스트로 고정할 수 있는 이유가 이것이다.

## 1. 퀴즈 문항 생성

### 1-1. 문항 하나의 모양

```js
{
  id: "kanji-reading-12",        // `${유형}-${대상 id}` — 한 세트 안에서 유일
  type: "KANJI_READING",         // 아래 11종 중 하나 (일본어 8 + 영어 표현 3)
  prompt: { main: "遵", sub: "이 글자의 음독은?" },
  choices: ["ジュン", "シュン", "ソン", "セン"],   // 항상 4개, 전부 서로 다른 문자열
  answerIndex: 2,                                  // 자리는 rng로 섞는다
  evidence: { ... }                                 // 채점 후 근거 — 원본 항목 그대로
}
```

### 1-2. 유형 11종과 생성 조건 (일본어 8 + 영어 표현 3)

> 2026-09-03 정정: 이 절은 "8종"이라 적혀 있었지만 `lib/quiz.js`는 영어 표현 3종(`EXPRESSION_*`)을 이미 만들고
> `lib/quizEn.test.js`가 고정하고 있었다 — 문서가 코드의 3/11을 몰랐다. 영어 **화면**에서 퀴즈를 켜지 않는 것(§5)과
> 생성기가 영어 재료를 **만들 수 있는 것**은 다른 사실이다. 둘 다 여기 적는다.

| type | 재료 조건 (없으면 그 유형을 만들지 않는다) | 오답 풀 |
|---|---|---|
| `KANJI_READING` | `onyomi` 또는 `kunyomi`가 있는 한자. 음/훈은 있는 쪽에서 rng로 고른다 | 다른 한자의 **같은 종류** 읽기 |
| `KANJI_MEANING` | 항상 가능(`meaningKo`는 NOT NULL) | 다른 한자의 `meaningKo` |
| `KANJI_WORD_READING` | `kana`가 있는 예시 단어가 1개 이상 | 다른 예시 단어의 `kana` |
| `VOCAB_MEANING` | 항상 가능 | **같은 `partOfSpeech` 우선**, 3개를 못 채우면 범위 전체에서 보충 |
| `VOCAB_WORD` | 항상 가능(뜻 → 단어, 역방향) | 다른 어휘의 `word` |
| `VOCAB_READING` | **`kana`가 있는 어휘만** — kana 계약(06 §1)이 곧 출제 가능 여부다 | 다른 어휘의 `kana` |
| `GRAMMAR_CLOZE` | 예문 `jp`에 그 문법 표현이 **실제로 들어 있을 때만**(표현 = `name`에서 선행 `〜` 제거). 못 찾으면 그 문법은 `GRAMMAR_MEANING`으로 낸다 | 다른 문법의 `name` |
| `GRAMMAR_MEANING` | 항상 가능(`nameKo`는 NOT NULL) | 다른 문법의 `nameKo` |
| `SENTENCE_MEANING` *(진단 전용)* | 문법에 예문이 1건 이상. 지문 = 예문(`jp`/`kana`), 정답 = 그 예문의 `meaningKo` | **같은 레벨 다른 문법** 예문의 `meaningKo`(§1-3 그대로) |
| `EXPRESSION_CLOZE` *(영어)* | 예문 `en`에 표현 `text`가 **실제로 들어 있을 때만**(GRAMMAR_CLOZE와 같은 규칙). 못 찾으면 그 표현은 `EXPRESSION_MEANING`/`EXPRESSION_TEXT`로 낸다 | 다른 표현의 `text` |
| `EXPRESSION_MEANING` *(영어)* | 항상 가능(`meaningKo`는 NOT NULL) | 다른 표현의 `meaningKo` |
| `EXPRESSION_TEXT` *(영어)* | 항상 가능(뜻 → 표현, 역방향) | 다른 표현의 `text` |

`SENTENCE_MEANING`은 **진단에서만** 쓴다(§3-3). 유닛·자료실 퀴즈는 "문장" 축이 없다 — 유닛은 회화 스텝이 그 자리를 이미 맡고 있고,
자료실은 문법·한자·어휘 **세 탭의 사전 뷰**라 문장이라는 탭이 없다. 유형을 늘리면 두 화면의 세트 구성을 다시 정의해야 한다.

영어 3종은 유닛 재료의 `expressions[]`(한자 자리)에서 나오며, **일본어 유닛에는 `expressions`가 없으므로 생성되지 않는다.**
화면에서 영어 퀴즈를 켜는 조건은 §5다 — 생성기가 만들 수 있다고 화면이 켜져 있는 것은 아니다.

빈칸(`GRAMMAR_CLOZE`)을 **표현이 예문에 없는데도 만들면** 빈칸이 엉뚱한 자리에 뚫린다. 그래서 "실제로 포함될 때만"이 조건이다.

### 1-3. 오답 풀은 **같은 레벨에서 먼저** 채운다 (2026-08-25 감사 H2)

1. 1순위는 **출제 범위 안**(유닛이면 그 유닛, 자료실이면 그 조건).
2. 모자라면 **호출자가 준 오답 풀**에서 가져온다. 이 풀은 **같은 레벨로 조회한 것**이어야 한다 —
   유닛 학습은 코스의 `levelCode`로 `GET /api/library/{type}?level={코드}`를 부른다.
3. 정답 대상과 같은 id는 언제나 제외한다.

**레벨 필터 없이 앞에서 100개를 자르면** 자료실이 학습 순서로 정렬돼 있어 낮은 레벨만 담긴다.
실제로 N1 유닛의 문제에 입문 인사말(`これをください`)이 보기로 섞였다 — 그건 문제가 아니라 **레벨 맞히기**다.
**조용히 낮은 레벨로 채우지 않는다.**

### 1-3-1. `VOCAB_MEANING`은 **같은 품사에서 먼저** 채운다

뜻 고르기(`VOCAB_MEANING`)의 오답은 §1-3의 레벨 규칙 **안에서** 한 단계 더 좁힌다:
**정답과 품사가 같은 어휘를 먼저** 쓰고, 3개를 못 채울 때만 나머지 품사에서 보충한다.

이유는 §1-3과 같다 — 품사가 섞이면 뜻을 몰라도 **말투로 답이 보인다**
("먹다 / 책 / 조용한 / 그리고" 중에서 동사 하나만 고르면 된다).
품사를 맞춰 두면 후보 넷이 같은 자리에 놓여 **뜻을 알아야** 고를 수 있다.

> 다른 유형(`VOCAB_WORD`·`VOCAB_READING`)에는 이 규칙이 없다 —
> 그쪽 보기는 뜻이 아니라 표기·읽기라 품사가 단서가 되지 않는다.

고정 테스트: `frontend/src/lib/quizDistractors.test.js`
구현: `frontend/src/lib/quiz.js`의 `vocabQuestion` (`candidates: [samePos, rest]` — 앞 배열부터 소진한다)

### 1-4. 보기 4개를 못 채우면 **그 문항을 건너뛴다**

- 보기 4개는 **전부 서로 다른 문자열**이어야 한다. 정답과 같거나 서로 같은 후보는 버리고 다음 후보로 간다.
- 4개를 끝내 못 채우면 **그 문항 하나를 조용히 버린다.** 세트 실패가 아니다 — 화면은 만들어진 문항 수를 그대로 보여준다.
- 대상(한자·어휘·문법) id는 한 세트에서 **1회만** 쓴다. 같은 한자가 두 유형으로 두 번 나오지 않는다.

> ⚠️ **[모르겠어요]는 진단 전용이다**(§3-5). 여기서 말하는 "보기 4개"는 **정답 후보 4개**이고,
> 진단은 그 위에 성격이 다른 다섯 번째 버튼을 **얹는다**. 유닛 확인 문제·자료실 퀴즈의 보기는 **4개 그대로**다 —
> 그쪽은 **즉시 채점**이라 "모름"을 고르는 순간 오답 연출이 떠서 학습 흐름을 끊는다.
> 고정 테스트: `lib/diagnosis.test.js`의 "적용 범위는 진단뿐".

### 1-5. 재료 어댑터 — lib에 넘기기 전에 응답을 평탄화한다

`lib/quiz.js`가 받는 것은 **평평한 도메인 항목**이다: `{id, word, kana, meaningKo, partOfSpeech}` ·
`{id, letter, meaningKo, onyomi, kunyomi, words[]}` · `{id, name, nameKo, examples[]}`.

| 출처 | 어댑터 |
|---|---|
| `GET /api/library/vocabulary` | 표제어 1행 = 문항 1개. 뜻은 `senses[0].meaningKo`(병합 표제어 — 04 §3-7). `senses`가 비면 **그 항목은 버린다**(정답이 없다) |
| `GET /api/library/kanji` (목록) | 그대로. 단 `words`가 없어 `KANJI_WORD_READING`은 만들 수 없다 |
| `GET /api/library/grammar` (목록) | 그대로. **2026-09-10부터 `examples`가 목록에 실린다**(04 §3-5 · 08 B-12) → `GRAMMAR_CLOZE`·`SENTENCE_MEANING`을 목록 재료만으로 만들 수 있다 |
| `GET /api/courses/{c}/units/{u}` | 이미 평평하다 — 어댑터 불필요 |

어댑터 없이 응답을 그대로 넘기면 `meaningKo`가 `undefined`가 되어 보기가 비고 세트가 깨진다(3단계 qa 치명 ②).
어댑터는 화면이 아니라 **`lib/quiz.js`가 export하는 함수**이고, 실제 응답 픽스처(`test/apiFixtures.js`)로 검증한다(08 C-9).

## 2. 세트 구성 — 몇 문제를 낼 것인가

### 2-1. 유닛 확인 문제 (최대 10문항)

**확인 문제 스텝은 어휘 다음, 정리 앞이다.** 유닛 스텝 순서는
`문법(2~3) → 회화 → 한자(있을 때) → 어휘 → 확인 문제(일본어만) → 정리` 로 고정이고, **정리가 언제나 마지막 스텝**이다.
[다음 유닛 ›](코스 마지막이면 다음 코스 / 코스 목록)는 **정리에만** 있고, 그 앞 모든 스텝의 전진 버튼은 [다음 ›]다 —
확인 문제 카드(풀기 전·결과)의 전진 버튼도 [다음 ›]이며 **정리로** 간다. 세는 스텝 수 = [다음 ›]로 갈 수 있는 스텝 수.
**문제 풀이는 완료 조건이 아니다** — 건너뛰고 정리에 닿아도 유닛은 완료다(01 §7-1).
(2026-09-03 결정 `진행사항/결정_2026-09_이어서_확인문제.md` §2 — 예전에는 정리 뒤 8번째라 [다음 ›]만으로는 도달할 수 없었다.)
고정 테스트: `frontend/src/pages/UnitStudyPage.stepOrder.test.jsx` (스텝 순서·전진 버튼은 이 파일 한 곳 — 08 C-11).

목표 배분은 **문법 2~3 · 한자 3~4 · 어휘 4**이고, 재료가 모자라면 **만들 수 있는 것부터** 채운다.
**실제 만들어진 문항 수가 세트의 사실이다** — 화면은 그 수를 그대로 보여준다(빈 자리를 메우지 않는다).

**입문 유닛이 6문제인 것은 결함이 아니다** (2026-08-25 판정 M3, 08 C-12 ③):
입문은 문법 2 · 한자 0 · 어휘 15(전부 `kana` 없음)라 **문법 2 + 어휘 4 = 6문항**이 된다.
한자 4문항 자리는 입문이 **한자를 배우지 않아서** 비는 것이고, 그 자리를 어휘로 메우면 6문항 중 어휘가 8이 되어
유형 균형이 깨진다. **문항 수는 목표가 아니라 배운 재료의 결과다. 10은 상한일 뿐이다**(08 §F-14).
(예전에는 여기에 F-13도 함께 인용돼 있었지만, F-13은 **진단**의 통과 기준이고 2026-09-10에 뒤집혔다 — 유닛 확인 문제와는 무관하다.)
→ 이 결정은 `frontend/src/lib/quiz.introCount.test.js`가 고정하고 있다.

### 2-2. 자료실 퀴즈 (10 / 20문항 선택)

- 들어온 탭의 유형만 낸다(한자 탭 → `KANJI_*` 3유형에서 rng 배분).
- **범위(`totalElements`)가 4개 미만이면 세트를 만들지 않는다** — "이 조건으로는 문제를 낼 수 없어요(4개 이상 필요)" + 자료실 복귀.
  이것이 자료실 목록의 [이 조건으로 문제 풀기] 비활성 근거이기도 하다.

**출제 범위 = 목록이 걸고 있던 조건 그대로다** (2026-09-21 QA 보통 결함 판정 — `hasRules`가 주소에서 사라졌다)

| 조건 | 출제 주소로 넘기나 | 이유 |
|---|---|---|
| `q` · `level` · `pos` · **`hasRules`** | **넘긴다** | **모집단을 좁힌다** — 목록이 보여준 개수가 곧 출제 범위다 |
| `sort` · `page` | 넘기지 않는다 | 같은 모집단을 **보는 순서·자리**일 뿐 범위를 바꾸지 않는다 |

활용표 유무(`hasRules`)를 예외로 두지 않는 이유는 둘이다.
① [이 조건으로 문제 풀기]는 `.result-bar`의 **결과 개수·적용 칩과 같은 줄**에 서서 *"이 개수·이 조건이 곧 출제 범위"* 를
배치로 약속한다(05 §15-1). 조건이 하나라도 떨어지면 §2-3이 지키려던 **"N개 중에서 출제합니다"가 다시 거짓**이 된다 —
N4 문법은 활용표 조건 하나로 **21 ↔ 47**이 갈린다.
② 문법 문항은 `name`·`nameKo`·예문으로 만들어진다(§1-2) — **활용표는 출제에 쓰이지 않는다.**
즉 활용표 없는 문법을 빼야 할 출제상의 이유가 없고, 조건을 떨어뜨릴 근거도 없다.

- 좁힌 범위가 4개 미만이 되면 **위의 비활성 규칙이 그대로 받는다** — 이 경우를 위한 새 규칙을 만들지 않는다.
- 범위 문장(§2-3 "…N개 중에서 출제합니다")의 접두에는 **레벨·품사·검색어만** 적는다. 문장이 보증하는 것은 **개수**이고,
  활용표 조건은 그 개수에 이미 반영돼 있다.
- 고정 테스트: `frontend/src/components/library/QuizEntry.test.jsx` — **무엇이 넘어가고 무엇이 안 넘어가는가는 여기 한 곳**이다(08 C-11).
  (버튼의 자리·비활성·0건 미렌더는 `pages/LibraryQuizPage.test.jsx`.)

### 2-3. 무작위 창 뽑기와 **꼬리 창 제외** (2026-08-25 감사 A-H3)

자료실 API는 한 번에 최대 100건이다. 범위가 그보다 크면 **무작위 창(page)** 을 뽑아 그 창에서 출제한다 —
늘 앞쪽 100개만 쓰면 "102개 중에서 출제합니다"라는 문장이 거짓이 된다.

**단, 뽑는 창은 4건 이상이 보장되는 창으로 한정한다.**
`q=하` 어휘는 102건·2창이고 마지막 창이 **2건**이라, 그 창을 뽑으면 4개 미만이 되어 **약 50% 확률로 퀴즈가 열리지 않았다.**
조건에 맞는 항목이 `100k+1 ~ 100k+3`이면 언제든 재현된다.

- **"문제를 낼 수 없어요"는 `totalElements < 4`일 때만 나온다** — 뽑은 창의 길이로 판정하지 않는다.
- 무작위 창 뽑기 자체는 유지한다(모집단 편향 회피가 원래 목적이다).

### 2-4. 세트의 수명

- **매 세트 새로 생성**한다. 캐시하지 않는다.
- [틀린 문제만 다시 풀기]는 생성이 아니라 **기존 세트의 부분집합**이다 — 같은 문항·같은 보기 그대로.
- 채점은 **보기 클릭 즉시 클라이언트에서**(정답이 세트 안에 있다). 채점 후 답 변경 불가.
- 유닛 확인 문제의 진행 상태는 **화면 컴포넌트 state**다. 스텝을 오가도 유지되고 유닛을 떠나면 사라진다 —
  저장하지 않는다(퀴즈·진단 결과 미저장, 08 §F-21).

## 3. 실력 진단

### 3-1. 레벨 선택 (측정 단위 = **한 판**)

> ⚠️ **2026-09-14 전면 개정 — 계단이 사라졌다.** 기획 `진행사항/기획_2026-09_진단개편.md`(요구 8~13)로 측정 모델이 바뀌었다.
> 예전 규칙("가장 낮은 레벨부터 자동으로 올라가고, 통과하면 다음 단계, 미달이면 즉시 종료")은 **더 이상 유효하지 않다.**
> 뒤집은 근거: *"N2쯤 하는 사람에게 입문·N5·N4·N3을 먼저 풀라고 요구하는 것은 측정이 아니라 통행세다."*
> (2026-09-10 개정분 — 6문항·표기 규칙·[모르겠어요]·통과선 — 은 **전부 그대로 살아 있다**.)

- **한 번의 검사 단위는 "한 판" = 레벨 하나**다. 사용자가 **레벨을 골라** 6문항을 풀고 제출하면,
  **통과든 미달이든 결과 화면에서 멈춘다.** 이어서 칠지는 매번 사용자가 버튼으로 정한다(§3-2-1).
  기억할 문장은 하나다: **"제출하면 항상 결과 화면이다."**
- **레벨 목록 = AVAILABLE 코스의 레벨을 낮은 것부터.** 코스명·레벨을 하드코딩하지 않고 `GET /api/courses`에서 계산한다(08 C-6).
  `stagePlan(courses)`가 주는 배열이 **그대로 선택지**다 — 이름(`STAGE_LEVEL_CODES`·`stagePlan`)은 계단 시절 그대로 두되,
  **뜻은 "자동으로 훑을 순서"가 아니라 "고를 수 있는 레벨"** 이다.
  → `STAGE_LEVEL_CODES = ["INTRO","N5","N4","N3","N2","N1"]`. 준비중 레벨은 목록에 없다.
- ★ **기본 선택값은 언제나 목록의 가장 낮은 레벨**이다. 되돌아온 사용자에게도 같다.
  이것이 이 개편의 안전장치다 — **"내 레벨을 모르는 사람"의 동선이 예전과 완전히 같다**(추가 클릭 0회).
  고르는 비용은 지름길을 쓰는 사람만 낸다.
- **입문도 레벨이다**(2026-09-10). 빠져 있던 유일한 근거가 "단계마다 한자 1문항이 필요한데 입문은 한자 0자"였는데,
  개편으로 **한자 낱자 문항 자체가 진단에서 빠졌다**(§3-3).
- 한 판은 **6문항**이고 구성은 §3-3에 있다. 재료는 `GET /api/library/{type}?level={코드}`로 가져오고 문항 생성 규칙은 §1 그대로다.
  **재료는 어휘·문법 둘뿐**이다 — 한자 자료실은 부르지 않는다.
- **통과 = 정답 ≥ `ceil(그 판의 실제 문항 수 × 2/3)`**(6→4, 5→4, 4→3, 3→2). 개수가 아니라 **비율**로 적는 이유:
  재료가 모자라 5문항이 나온 판에서도 기준이 흔들리지 않아야 한다(§3-6).
- **최소 3문항** — 3문항 미만으로밖에 못 만든 판은 **측정하지 않는다**(§3-6). 그 레벨은 결과 표에 행을 만들지 않는다.
- **화면이 약속하는 총량은 없다.** 한 번에 치는 것은 한 레벨뿐이라 "최대 n단계"·"3분" 같은 문구를 쓰지 않는다.
- 진단 중에는 **정오를 표시하지 않는다** — 데이터에는 정답이 있으므로 "보여주지 않는 것"이 규칙이다.
  문항별 정오를 보여주면 사용자가 자기 답을 되짚어 **진단이 학습 화면**이 되고, 판정에 대한 항의 지점이 생긴다("4개 맞은 것 같은데?").
  근거는 결과 표의 판별 정답 수(`4 / 6`)가 이미 준다. **갈래별 정답 수도 같은 이유로 결과에 넣지 않는다**(§3-3).
- **화면 문구에서 "단계"라는 낱말을 쓰지 않는다** — 가리킬 대상이 없어졌다. 화면은 "레벨", 문서·주석의 내부 용어는 "한 판"이다.

**레벨 표기는 두 가지이고 섞으면 안 된다**(3단계 qa 치명 ①의 뿌리):

| 무엇 | 값 | 쓰는 곳 |
|---|---|---|
| `course.levelLabel` | **표시 문구** — `"JLPT N5"`, 입문은 `"문자"`(N 코드가 아예 없다) | 화면 문구·선택지·결과 표 |
| `course.title` | **코스 이름** — `"왕초보"`·`"입문"` | 선택지 문구 `{title}({levelLabel})` · 코스 버튼 |
| 자료실 `level` 파라미터 | **코드** — `"N5"`. 근거는 **`course.level_code` 컬럼**(응답의 `levelCode`)이지 `levelLabel`도 `courseNo`도 아니다(03 §1 · 04 §3-1) | `GET /api/library/**` 필터 |

`stagePlan(courses)`는 레벨마다 **`levelCode`·`levelLabel`·`title`·`courseId`를 함께** 준다. 조회에는 코드, 표시에는 문구를 쓴다.
**문자열을 잘라 만들지 않는다** — 입문("문자")처럼 접두 규칙이 통하지 않는 값이 실제로 있다.

### 3-2. 추천 (안내) — **통과한 레벨**로 정한다, 레벨 목록과 **다른 목록**을 쓴다

> ⚠️ **2026-09-14 재정의.** 예전 계산은 *"맨 아래부터 **연속으로** 몇 개 통과했나"*(`passedCount`)였다.
> 계단이 **항상 맨 아래에서 시작한다**는 전제 위에서만 맞는 식이고, 레벨을 고르게 하는 순간 **조용히 틀린다** —
> `N2를 골라 통과 → 연속 통과 1 → N5 코스 추천`. 화면은 멀쩡해 보이므로 **테스트로만 잡힌다.**
> **"연속"이라는 개념 자체가 없어졌다**: 판은 서로 독립이고 순서·횟수는 판정에 쓰지 않는다.

```
통과한 레벨이 하나라도 있으면
    → 그중 **가장 높은** 레벨의 **바로 위** 레벨 코스
    → 위가 없으면(가장 높은 레벨을 통과) allPassed + 가장 높은 공개 코스
통과한 레벨이 하나도 없으면
    → 미달한 레벨 중 **가장 낮은** 것의 **바로 아래** 레벨 코스
    → 더 내려갈 곳이 없으면 **입장 가능한 첫 코스**
```

| 친 판 | 통과 레벨 | 추천 | 왜 |
|---|---|---|---|
| N2 통과 | N2 | **N1 코스** | N2는 충분하니 그 위부터 |
| N2 미달 | 없음 | **N3 코스** | 미달한 가장 낮은 레벨의 한 칸 아래 |
| N2 미달 → N3 통과 | N3 | **N2 코스** | N3는 충분하고 N2는 부족하다 |
| N2 통과 → N1 미달 | N2 | **N1 코스** | N1이 부족하니 N1 코스 |
| 입문 미달 | 없음 | **입문 코스**(첫 코스) | 더 내려갈 곳이 없다 |
| N1 통과 | N1 | **가장 높은 공개 코스** + `allPassed` | 한 판만 쳐도 성립한다 |
| N2 통과 + N3 미달(모순) | N2 | **N1 코스** | **통과가 이긴다** — 추천은 "할 수 있는 것"에서 출발한다 |

- **"바로 위/아래 레벨"은 레벨 목록에서 한 칸**이다. 코스 번호에서 파생하지 않는다(08 C-9) — 준비중 레벨은 건너뛴다.
- **추천 후보 = AVAILABLE 코스 전체(courseNo 순)** 다. 레벨 목록은 "재료로 측정할 수 있는 레벨", 추천은 "보낼 수 있는 코스"라
  성격이 다르고, 재료 부족으로 측정할 수 없는 레벨은 언제든 생긴다(§3-6). **측정과 안내는 다른 목록이다.**
- 추천은 **준비중 코스를 절대 가리키지 않는다.**
- `allPassed`의 뜻: ~~계단을 전부 통과~~ → **가장 높은 레벨을 통과.** 한 판만 쳐도 성립할 수 있다.
- 반환: `{ recommendedCourseId, allPassed }`. 전부 준비중이면 `null`(배너를 그리지 않는다).
  **`stepDownCourseId`는 없앴다** — 결과 화면의 보조 동선이 코스 링크가 아니라 **레벨 검사 시작 버튼**이 됐다(§3-2-1).
  남겨 두면 "한 단계 아래 코스"와 "아래 레벨 도전"이라는 두 벌의 계산이 공존한다(08 C-11).
- 결과 화면의 "그 위 코스는 준비 중" 안내는 **실제로 PREPARING 코스가 있을 때만** 그린다(08 C-12 ②).

**단일 기준 테스트**: 추천은 `frontend/src/lib/diagnosis.recommend.test.js` **하나**다(08 C-11).

### 3-2-1. 판 기록과 이어가기 — **추천과 다른 계산이다**

★ 두 계산을 하나로 합치지 말 것. **추천은 "지금까지 친 전부"** 에서, **이어가기 버튼은 "방금 친 한 판"** 에서 나온다.
한 판만 쳤을 때는 같은 곳을 가리키지만 여러 판을 치면 갈린다.

**판 기록** `recordLevelResult(results, result)` — 결과 표의 재료다.

- **레벨당 한 행**이다. 같은 레벨을 다시 치면 **나중 결과로 덮어쓴다**(행이 늘지 않는다).
  덮어쓰는 이유: ① `N2 통과`와 `N2 —`가 나란히 서면 표가 스스로 모순된다 ② 문항은 매번 새로 뽑히므로 다시 친 사람은 두 번째를 자기 실력이라고 생각한다 ③ 추천 계산에 "어느 것이 진짜인가"라는 분기가 생기지 않는다.
- **레벨 순(낮은 것부터)으로 정렬**한다. **친 순서가 아니다** — 진단이 대답하는 질문은 "나는 사다리 어디쯤인가"이고,
  시간 순서는 판정에 쓰이지 않는 정보다. **"몇 번 쳤는지"를 화면에 표시하지 않는다.**
- **행이 하나뿐인 첫 판에서도 표를 그린다** — 근거가 언제나 같은 자리에 있어야 한다.
- 측정하지 않은 판(3문항 미만·호출 실패)은 **행을 만들지 않는다**(§3-6).

**이어가기** `nextLevelOffer({ plan, results, levelCode, passed })` → `{ level, status }`

| 방금 친 판의 한 칸 위(통과)/아래(미달)가 | `status` | 화면 |
|---|---|---|
| 목록에 없다(끝에 닿았다) | `END_OF_LIST` | 버튼 없음 + *"가장 높은 레벨까지 확인했어요…"* / *"여기가 가장 낮은 레벨이에요."* |
| 있고, 아직 안 쳤거나 **쳐서 미달했다** | `OFFER` | 주 버튼 `{levelLabel} 도전하기 ›` / `{levelLabel} 확인하기 ›` |
| 있고, **이미 통과했다** | `ALREADY_PASSED` | 버튼 없음 + *"아래 레벨은 이미 충분했어요 — 여기부터 공부하면 돼요."* |

- 마지막 줄이 이 규칙의 이유다: `N2 통과 → N1 미달`인 사람에게 아래는 **방금 통과한 N2**이고,
  **이미 증명한 것을 다시 확인하라고 권하는 것**이 이 개편이 없애려던 귀찮음 그 자체다.
  그 자리에서는 **코스 시작하기가 주 버튼**을 물려받는다 — 실제로 그 사람이 할 일은 N1 코스를 공부하는 것이다.
- **미달했던 레벨은 다시 제안한다.** 다시 도전하는 것은 의미가 있다.
- **없는 버튼은 자리도 만들지 않는다**(비활성 버튼 없음 — "왜 안 눌리지"라는 질문을 만든다).
- **기록의 수명**: [다른 레벨 고르기]로 되돌아가도 기록은 **유지**된다. 지우는 길은 **새로고침뿐**이고,
  그 사실은 결과 화면의 *"새로고침하면 사라져요"* 한 줄이 이미 말한다 — 초기화 버튼을 새로 만들지 않는다.

**단일 기준 테스트**: `frontend/src/lib/diagnosis.rounds.test.js` **하나**다.

### 3-3. 한 판의 구성 — **6문항**, 갈래 `어휘` · `문법` · `어법` · `문장`

| 레벨 | 단어 | 문법 | 문장 | 계 |
|---|---|---|---|---|
| 입문 · N5 · N4 · N3 | `VOCAB_MEANING` **3** | `GRAMMAR_MEANING` **2** | `SENTENCE_MEANING` **1** | **6** |
| N2 · N1 | `VOCAB_READING` **3** | `GRAMMAR_CLOZE` **3** | — (빈칸 지문이 문장을 겸한다) | **6** |

- **한자 낱자 문항(`KANJI_*`)은 진단에서 쓰지 않는다.** 낱자에 kana를 붙이면 문항이 소멸하고(읽기를 묻는데 읽기를 적어 주는 꼴),
  낱자는 문맥이 없어 후리가나 개념이 성립하지 않는다. 한자는 사라지지 않는다 — **N4부터 단어·문장 지문 안에 kana 줄과 함께** 나온다.
- **유형이 레벨에 따라 갈리는 것은 표기 규칙의 결과다**(§3-4): 입문~N3은 보기가 한국어라 "뜻" 유형만 성립하고,
  N2~N1은 보기가 일본어라 "읽기·빈칸"만 성립한다(일→일 뜻풀이 데이터가 없다). 결과적으로 앞 구간은 **이해도**, 뒤 구간은 **읽기·용법**을 잰다.
- **화면 순서는 단어 → 문법 → 문장 고정**이다. 섞으면 판마다 배치가 달라져 6장을 훑는 눈이 매번 새로 적응해야 한다.
- **같은 대상은 한 판에서 한 번만** 쓴다(§1-4). 문장 문항의 문법과 문법 문항의 문법도 서로 달라야 한다.
- **문장 문항을 못 만들면 그 한 자리만 단어로 채운다.** 단어는 어느 레벨에서도 재료가 가장 많다.
  그 밖의 빈자리는 **메우지 않는다** — 만들어진 수가 그 판의 사실이다(§2-1과 같은 원칙).

**갈래 — 위 구성에 이름을 붙인 것이다**(2026-09-14 · 기획 D18). **문항 수·유형·순서는 하나도 바뀌지 않았다.**
사용자 요구(*"문법, 어법, 단어어휘가 잘 나뉘어져 있으면 좋겠어"*)의 핵심은 새 분류 체계가 아니라 **이미 있는 묶음을 눈에 보이게 하라**는 것이다.

| 문항 유형 | 갈래 | 무엇을 재나 |
|---|---|---|
| `VOCAB_MEANING` · `VOCAB_READING` | **어휘** | 낱말의 뜻을 아는가 / 낱말을 읽을 수 있는가 |
| `GRAMMAR_MEANING` | **문법** | **규칙 자체**를 아는가(지식) |
| `GRAMMAR_CLOZE` | **어법** | **문장 안에서** 맞는 표현을 고를 수 있는가(쓰임) |
| `SENTENCE_MEANING` | **문장** | 문장 전체를 읽어 낼 수 있는가 |

| 레벨 | 어휘 | 문법 | 어법 | 문장 | 계 |
|---|---:|---:|---:|---:|---:|
| 입문 · N5 · N4 · N3 | **3** | **2** | 0 | **1** | 6 |
| N2 · N1 | **3** | 0 | **3** | 0 | 6 |
| 입문~N3에서 **문장을 못 만들었을 때** | **4** | **2** | 0 | 0 | 6 |

- **화면 순서는 `어휘 → 문법 → 어법 → 문장` 고정**(`QUESTION_GROUP_ORDER`). 레벨이 바뀌어도 순서가 바뀌지 않는다.
- ★ **0문항인 갈래는 머리글째로 렌더하지 않는다.** N2·N1에 `문법`·`문장` 머리글이 없는 것은 **정상 경로**이고,
  재료 부족으로 어느 갈래가 0이 된 경우도 **완전히 같은 규칙**이다(예외를 두지 않는다).
  근거: 빈 머리글은 "여기 있어야 할 것이 없다"는 **결함 신호**로 읽힌다. 사과 문구·"준비 중" 표시도 만들지 않는다.
- **머리글에 개수를 붙이지 않는다**(~~`어휘 3문항`~~). 6장이 한 화면에 다 보이므로 보면 안다(05 §19-6).
- **문항 번호는 갈래와 무관하게 화면 전체에서 1부터 이어진다**(`1.`~`6.`). 갈래마다 1로 되돌리지 않는다 —
  `1.`이 세 번 나오면 미응답 안내(*"아직 2문항을 고르지 않았어요"*)와 대조할 때 헷갈린다.
- **결과 화면에는 갈래별 정답 수를 넣지 않는다.** 갈래별 점수는 사실상 **문항별 정오**이고(§3-1이 닫아 둔 문이 열린다),
  판정의 단위는 레벨이다. 판정에 쓰지 않는 숫자를 화면에 두지 않는다(05 §19-6).
- **부수 효과**: N2·N1 빈칸 문항은 `legend`에 들어가는 값이 질문이 아니라 **예문의 한국어 뜻**(힌트)이라
  "무엇을 묻는지"를 말해 주지 않았다. **`어법` 머리글이 그 자리를 메운다** — 문항 생성 규칙은 그대로 둔 채 고쳐진 결함이다.

`groupQuestions(questions)` → `[{ title, items: [{ question, number }] }]` — 빈 갈래는 **배열에 없고**, `number`는 전체 통번호다.
번호를 화면에서 따로 세지 않는 이유: 묶음과 번호가 두 곳에서 계산되면 어긋난다.

**어디에 무엇을 두나**(구현 경계 — 규칙이 두 벌이 되지 않게):

| 파일 | 맡는 것 |
|---|---|
| `lib/quiz.js` | **문항 한 개를 만드는 규칙**(§1). `SENTENCE_MEANING` 생성기도 여기 — 유형 표가 여기 있으므로 생성도 여기다. **보기는 언제나 4개**다 |
| `lib/diagnosisScript.js` | **표기 규칙**(§3-4) — 문자 판별·생성 조건·표시 방식뿐. 문항을 만들지 않는다 |
| `lib/diagnosis.js` | **한 판의 구성**(어느 유형을 몇 개)과 **갈래 묶기**, 표기 규칙으로 재료 거르기·지문 만들기, **[모르겠어요] 얹기**, 채점·통과 판정, 레벨 목록·판 기록·이어가기·추천 |

`buildStageQuestions({ levelCode, vocabItems, grammarItems, rng })` → 최대 6문항.
문항 하나의 모양은 §1-1에 `prompt.kana`(병기 줄, 없으면 `null`)와 다섯 번째 보기가 더해진 것이다:
`choices`는 5개이고 `choices[4] === "모르겠어요"`, `answerIndex`는 **항상 0~3**이다.
채점은 `countCorrect(questions, answers)` — `answers[i]`가 4(모름)면 오답이다.
`null`(미응답)도 오답으로 다루지만 **화면에서는 도달할 수 없다**(§3-6 — 미응답이 있으면 제출되지 않는다).
안전망으로 남긴다(2026-09-20 senior-dev) — lib은 화면의 제출 조건에 기대지 않는다.

### 3-4. 레벨별 표기 규칙 — **생성 조건**과 **표시 방식**은 다른 것이다

**생성 조건** = "이 항목을 지문으로 쓸 수 있나"(못 쓰면 다른 항목을 뽑는다).
**표시 방식** = "뽑은 항목을 화면에 어떻게 적나".

| 레벨 | 가타카나 | kana 모드 | 보기 언어 |
|---|---|---|---|
| **입문 · N5** | **금지**(한 자라도 있으면 지문 후보에서 제외) | `REPLACE` — 한자를 kana로 **치환해 한 줄만**(`学生` → `がくせい`) | 한국어 |
| **N4** | **금지** | `BOTH` — 원문 줄 + **kana 줄 병기** | 한국어 |
| **N3** | 허용 | `BOTH` | 한국어 |
| **N2 · N1** | 허용 | `NONE` — **kana 줄을 그리지 않는다** | 일본어 |

- **한자가 있는데 `kana`가 없는 항목은 제외**한다(`REPLACE`는 치환할 재료가 없고, `BOTH`는 병기할 줄이 없다).
  `NONE`(N2·N1)에서는 kana 줄을 안 그리므로 제외하지 않는다.
- **표시**: `REPLACE` = 한자가 있으면 `kana`, 없으면 원문 / `BOTH` = 원문 + (한자가 있을 때만) kana 줄 / `NONE` = 원문만.
  **kana 줄은 원문 아래**다(2026-09-11 — designer 결정). 위에 두면 루비처럼 보이는데 실제로는 줄 단위 병기라 기대가 어긋나고, 원문이 아래로 밀린다.
  한자가 없으면 kana 줄을 **얹지 않는다** — 같은 글자를 두 줄 적으면 줄만 늘고 읽히는 것은 없다(05 §19-6).
- **문법 이름은 예외다**: `grammar_point.name`에는 **읽는 법 데이터가 없다**. 그래서
  ① `REPLACE` 레벨(입문·N5)에서는 **한자가 든 이름을 지문에서 뺀다**(N5 문법 44개 중 한자 없는 **18개**만 지문 후보다)
  ② `BOTH` 레벨(N4·N3)에서는 **kana 줄 없이 그대로** 보여준다. 가타카나 규칙은 이름에도 그대로 적용된다.
- ★ **규칙을 적용하는 자리는 "화면에 일본어로 나오는 곳"뿐이다.**
  입문~N3은 보기가 전부 한국어이므로 **지문만 검사하고 오답 풀은 거르지 않는다.**
  여기를 같이 거르면 N5 어휘 후보가 20% 줄어드는 것이 **오답 풀까지 20% 줄어드는 일**이 되어,
  "보기 4개를 못 채워 버려지는 문항"(§1-4)이 늘어난다. N2~N1은 보기도 일본어이므로 지문과 보기 양쪽에 적용한다.
- **[모르겠어요]는 이 규칙의 대상이 아니다** — 보기가 아니라 포기 버튼이고, 어느 레벨에서나 한국어다.
- 왜 kana 줄의 경계가 N3 / N2인가: 후리가나를 N2까지 끌고 가면 **읽기 문항이 성립하지 않는다**(정답을 지문 위에 적어 주는 꼴).
  N2~N1은 제품 전체가 시험대비 톤이라 kana를 떼는 지점이 여기다.

**구현 계약**(`frontend/src/lib/diagnosisScript.js` — 순수 함수, 고정 테스트 `diagnosisScript.test.js` **한 곳**):

| 함수 | 반환 |
|---|---|
| `hasKanji` · `hasKatakana` · `hasJapanese` · `hasHangul` | 문자 종류 판별(빈 값·null은 `false`). 가타카나는 `[ァ-ヺ]` — `「」`·`〜`·`。`는 기호이지 가타카나가 아니다 |
| `levelScript(levelCode)` | `{ katakanaAllowed, kanaMode: "REPLACE"\|"BOTH"\|"NONE", choiceLang: "KO"\|"JA" }`. **모르는 코드는 가장 엄격한 규칙**(입문·N5)을 준다 — 규칙 밖 문자가 새는 것보다 문항이 줄어드는 편이 싸다 |
| `canUseAsPrompt(levelCode, {text, kana})` | 단어·문장 지문으로 쓸 수 있나 |
| `canUseAsNamePrompt(levelCode, {name})` | 문법 이름을 지문으로 쓸 수 있나(읽는 법 없음 전제) |
| `renderPrompt(levelCode, {text, kana})` | `{ main, kana }` — `kana`는 병기 줄(없으면 `null`) |

**제약(데이터)**: 후리가나는 **글자 위 루비가 아니라 줄 병기**다. 데이터는 단어/문장 **전체의 읽는 법**만 갖고
어느 한자가 어느 음절에 대응하는지는 없다 → `<ruby>`를 쓸 수 없다. 글자별 루비를 원하면 한자별 읽기 데이터를 새로 만들어야 한다(콘텐츠 별건).

### 3-5. [모르겠어요] — **다섯 번째 보기**, 채점은 오답과 같다

- **보기 = 정답 1 + 오답 3 + 모름 1 = 5개.** §1-4의 "보기 4개"는 **정답 후보 4개** 규칙으로 그대로 살아 있고, 모름은 그 위에 얹히는 **다른 성격의 버튼**이다.
- **오답을 2개로 줄여 4개를 맞추지 않는다.** 줄이면 찍기 정답률이 1/4 → 1/3으로 **올라가**, 이 보기를 넣은 목적(찍기를 걷어내 측정을 정확하게)이 뒤집힌다.
- **자리는 언제나 맨 아래 고정**이고 **rng 셔플 대상이 아니다.** 매번 위치가 바뀌면 "포기"를 누르려다 오답을 누른다. 정답은 항상 앞 4자리 안에 있다.
- **채점은 오답과 동일**하다. 정답 수에 들어가지 않고, **별도 통계를 만들지 않는다**(판정에 안 쓰는 숫자를 화면에 두지 않는다 — 05 §19-6).
- **미응답은 제출되지 않는다**(§3-6). [모르겠어요]를 고른 문항은 **답한 문항**이다 — 남은 수를 셀 때 빠지고,
  전부 [모르겠어요]여도 제출된다(0/n 미달). 문구는 `모르겠어요` 하나이고 다섯 보기는 **전부 서로 다른 문자열**이어야 한다
  (오답 후보에 같은 값이 있으면 그 후보를 쓰지 않는다).
- **적용 범위는 진단뿐이다** — §1-4의 경고 참조.

### 3-6. 제출 단위 · 재료가 모자랄 때

**제출은 페이지 단위다.** 한 레벨 = 한 화면 6문항 → 버튼 하나로 제출(**미응답 0일 때만** — 아래) → 채점(화면에 안 보인다) → **언제나 결과 화면**.

- ★ **통과든 미달이든 결과 화면에서 멈춘다**(2026-09-14). 자동 진행은 **어느 방향으로도 없다** —
  통과했다고 다음 레벨 문항이 뜨지 않고, 미달했다고 아래 레벨로 내려가지도 않는다.
  왜 통과에도 멈추나: 자동으로 올라가면 **사용자는 자기가 어디까지 통과했는지 모른 채 다음 문제를 만난다.**
  왜 미달에도 멈추나: 자동으로 내려가면 **떨어진 사람에게 묻지도 않고 더 쉬운 문제를 들이민다** —
  N2에서 미달한 사람이 원하는 것이 항상 "N3 검사"는 아니다.
- **제출 버튼 라벨은 하나다**(`제출하고 결과 보기 ›`). 다음 판이 있는지로 갈리던 라벨은 폐기됐다.
- **제출과 결과 사이에 로딩이 없다** — 채점은 화면 안에서 끝나고 부를 재료가 없다.
  스켈레톤이 나오는 자리는 **[시작하기]·[도전하기]·[확인하기]를 누른 뒤**다.
- **제출 전에는 몇 번이든 답을 바꿀 수 있다.** §2-4의 "채점 후 답 변경 불가"와 충돌하지 않는다 —
  그쪽은 **보기를 누른 순간 채점되는** 즉시 채점 퀴즈의 규칙이고, 진단은 **제출 시점에 채점**한다.
- ★ **미응답이 있으면 제출되지 않는다**(2026-09-16). [모르겠어요]가 보기로 있으므로 빈칸은 의도가 아니라 실수다 —
  실수를 오답으로 채점하면 진단이 실력이 아니라 실수를 잰다.
  (1차의 *"붙잡으면 [모르겠어요]를 넣은 의미가 없다"* 는 거꾸로였다 — [모르겠어요]가 **있기 때문에** 어느 문항에서도 잡히지 않는다. 나가는 길이 문항마다 한 번 클릭으로 있다.)
  막는 방법은 비활성이 아니다: 누르면 **번호가 가장 작은 미응답 문항으로 이동·초점**하고, **미응답 문항마다 안내 한 줄**이 붙는다
  (**제출을 시도한 뒤에만** — 시도 전에는 DOM에 없다. 답을 고르면 그 문항의 줄은 즉시 사라진다).
  제출 버튼 위 한 줄은 **남은 수**를 말한다(시도 전에도 보이고, 0이면 없다). 확인 모달은 여전히 없다.
  - 문구는 둘로 고정한다 — 버튼 위 `아직 {n}문항을 고르지 않았어요 — 모두 고르면 제출할 수 있어요.` / 문항 안 `답을 골라 주세요 — 모르면 [모르겠어요]를 고르면 돼요.`
    **"모름으로 처리"** 라는 말은 화면 어디에도 없다.
  - **[모르겠어요]는 답이다**(§3-5). 미응답을 [모르겠어요]로 자동 채우지 않고, 분모에서 빼지도 않는다.
  - 막힌 시도는 **흔적을 남기지 않는다** — 판 기록·채점·추천 어느 것도 일어나지 않는다. 3~5문항 판도 **만들어진 문항 전부**에 답해야 제출된다.
  - "이동"은 스크롤과 초점이다. 이미 보이는 자리면 초점만 옮긴다. 자동으로 무엇을 고르거나 바꾸지 않고, 다 채웠다고 자동 제출하지도 않는다.
- **제출한 판으로는 돌아갈 수 없다.** 같은 레벨을 **다시 칠 수는 있고**(§3-2-1), 그때 문항은 새로 뽑힌다(같은 문항이 다시 나올 수 있고 막지 않는다).
- **연타는 첫 클릭만 처리한다.** 막는 방법은 `disabled`가 아니라 **화면 전환**이다:
  제출하면 그 자리에서 `phase`가 `result`로 바뀌어 **문항 화면이 통째로 언마운트된다** — 누를 버튼도 고를 보기도 사라진다.
  그 위에 `useRef` 가드가 **같은 틱의 두 번째 클릭**을 막는다. → **보기·버튼에 `disabled`를 넣지 않는다.**
  **막힌 제출**(미응답 있음)은 화면 전환도 가드도 일으키지 않는다 — 잠금은 실제 제출에만 딸려 있다.
  ★ 순서: **누름 → 미응답 검사 → (있음) 이동·표시 / (없음) 가드 → 채점 → 전환.** 가드가 검사보다 먼저 켜지면 막힌 첫 클릭이 그 다음 정상 제출을 막는다.
  막힌 상태에서 다시 누르면 같은 일이 반복된다(그 시점의 첫 미응답으로) — 버튼도 보기도 그대로 살아 있고, 이미 고른 답을 바꿀 수 있다.
- **새로고침·뒤로가기는 레벨 고르기 화면으로 되돌리고 쌓인 판정 기록도 함께 지운다.** 진행 상태를 저장하지 않는다.

**재료가 모자랄 때.**

| 상황 | 결과 |
|---|---|
| 한 판이 **3~5문항**만 만들어짐 | 그대로 진행한다. 진행 줄이 그 수를 말하고, 통과선은 `ceil(수 × 2/3)`다. **사과 문구·경고 띠는 없다** |
| 한 판이 **3문항 미만** | 그 판은 **측정하지 않는다.** 통과·미달이 실력이 아니라 운이 되기 때문이다 |

**"3문항 미만이면 없는 것으로 친다"는 `buildStageQuestions`가 강제한다** — 2문항이 만들어져도 **빈 배열을 돌려준다**.
그래서 화면은 `length === 0` 하나만 보면 되고, 판정이 화면과 lib 두 곳에 생기지 않는다(08 C-11).

**문항 화면을 못 띄우면 언제나 같은 실패 카드다**(2026-09-14 — "첫 단계 / 2단계 이후" 갈림은 폐기됐다. 고르는 모델에 "첫 단계"가 없다).

- 재료 부족이든 호출 실패든 **같은 카드 한 벌**이다. 재료 부족과 호출 실패를 **화면에서 구별해 주지 않는다** —
  사용자가 할 수 있는 일이 같다(05 §19-6). [다시 시도]의 뜻만 실제로 다르다.
- **말없이 결과 화면으로 되돌리지 않는다.** 사용자는 **자기가 방금 누른 버튼의 결과**를 기다린다 —
  아무 말 없이 이전 화면이 다시 뜨면 **"아무 일도 안 일어났다"** 로 읽힌다.
- 문구가 **어느 레벨에서 막혔는지 말한다**: *"{title}({levelLabel}) 레벨은 문제를 준비하지 못했어요."*
  그 정보가 사용자의 다음 선택(다른 레벨 고르기)에 직접 쓰인다.
- 버튼은 **지금까지 친 판이 있느냐**로 주 버튼만 갈린다:

| 지금까지 친 판 | 주(primary) | 보조 | 약(ghost) |
|---|---|---|---|
| **없다** | `일단 {첫 코스 title}부터 시작하기` | `다른 레벨 고르기` | `다시 시도` |
| **있다** | `지금까지 결과 보기` | `다른 레벨 고르기` | `다시 시도` |

- **[다시 시도]는 언제나 같은 레벨을 다시 부른다**(처음으로 되돌아가지 않는다).
- **실패한 레벨은 결과 표에 행을 만들지 않는다** — 측정하지 않았기 때문이다. 앞서 친 판의 결과는 그대로 남는다.
- **고를 레벨이 하나도 없으면**(AVAILABLE 코스 0개인데 주소로 직접 들어옴) 실패 카드가 아니라 레벨 고르기 화면 자리에 한 줄이다:
  *"지금은 확인할 수 있는 레벨이 없어요."* 선택지도 [시작하기]도 **[다시 시도]도 두지 않는다** —
  다시 불러도 같은 결과이고, 나가는 길은 GNB가 이미 준다. (2026-09-14 senior-dev 판정:
  화면정의 초안은 이 상황도 실패 카드로 보냈지만, *"문제를 준비하지 못했어요"* 는 **사실이 아니다** — 문제가 아니라 코스가 없다.)

### 3-7. 화면 계약 (웹 DOM)

조판·색·간격은 `설계/05 §15-2`가 정한다. 여기 적는 것은 **테스트가 의존하는 구조**다 — 셋(웹·앱·qa)이 같은 것을 가리키게 하기 위한 최소 약속이다.

| 요소 | 계약 |
|---|---|
| 레벨 선택 | `<fieldset class="diag-levels">` + `<legend>`(그룹 이름) + 같은 `name`의 `<input type="radio">`. 한 줄의 문구는 **`{title}({levelLabel})`**, **기본 선택 = 첫 줄** |
| 지난 결과 표시 | 이미 친 레벨의 라벨 안 마지막 자식 `<span class="diag-level-mark">` = **`{정답 수} / {문항 수}`**. 안 친 레벨에는 **없다**. 판정 낱말(통과/미달)을 쓰지 않는다 |
| 갈래 묶음 | `<section class="diag-group">` + 머리글 `<h2 class="diag-group-title">`. **중첩 `<fieldset>`으로 만들지 않는다**(문항마다 이미 fieldset/legend가 있어 낭독기가 그룹을 두 겹으로 읽는다). **빈 갈래는 DOM에 없다** |
| 문항 카드 | `<fieldset class="diag-question" role="radiogroup">` 최대 6장. 번호·질문은 `<legend>`, 번호는 **화면 전체 통번호**. **역할이 `radiogroup`인 이유**(2026-09-20 senior-dev 확정, designer 권고): ARIA 1.2에서 `aria-invalid`는 `radiogroup`에는 허용되고 fieldset의 기본 역할 `group`에는 허용되지 않는다. 같은 `name`의 라디오 다섯 개를 담은 묶음이라 뜻도 맞다. 이름은 여전히 `legend`에서 온다(HTML-AAM은 요소 기준이다 — 역할을 바꿔도 번호·질문이 읽힌다) |
| 지문 | `.quiz-prompt` · kana 병기 줄은 **바로 아래** `.quiz-prompt-sub`(있을 때만 렌더한다 — 빈 줄을 만들지 않는다) |
| 보기 | 한 문항당 같은 `name`을 가진 `<input type="radio">` **5개**. 마지막이 `모르겠어요` |
| 제출 | 화면에 **버튼 하나**. 라벨은 **언제나** `제출하고 결과 보기 ›`. **`disabled`는 어느 순간에도 없다**(막혀도 그대로 살아 있다) |
| 남은 수 줄 | 제출 버튼 **위** `.quiz-note` — `아직 {n}문항을 고르지 않았어요 — 모두 고르면 제출할 수 있어요.` 미응답 1개 이상이면 **시도 전에도** 있고, 0이면 **없다**. 제출 버튼이 이 줄을 **`aria-describedby`** 로 가리킨다(줄이 없으면 접근 가능한 설명도 비어 있다) |
| 미응답 안내 | 제출을 시도한 뒤, 미응답 문항 카드 **안** — `<legend>` **바로 다음 자식** `<p class="diag-question-help" id="…">답을 골라 주세요 — 모르면 [모르겠어요]를 고르면 돼요.</p>`(지문 위. `.quiz-note`가 **아니다** — 급·색은 05 §15-2). 그 카드는 **`aria-invalid="true"`** 이고 이 줄의 id를 **`aria-describedby`** 로 가리킨다(라디오 다섯 개마다 붙이지 않는다). 답하면 요소·두 속성을 **함께 뗀다** — `"false"`로 바꾸지 않는다(줄과 1:1). 시도 전에는 DOM에 없다 |
| 막힘 시 이동·초점 | 스크롤은 **fieldset**에 `scrollIntoView({ block: "start" })` — `behavior`를 넘기지 않는다(넘기면 킷의 `prefers-reduced-motion` 처리를 우회한다. 즉시 이동이 규칙). 초점은 **번호가 가장 작은 미응답 문항의 첫 라디오**에 `focus({ preventScroll: true })` — 초점 호출이 라디오 기준으로 다시 스크롤해 안내 줄을 밀어내지 않게. fieldset이 아니라 라디오에 초점을 두는 이유: 화살표 한 번이 곧 답이어야 한다 — Tab으로 거슬러 오르지 않는다. 낭독은 legend(번호·질문) → 카드 설명(안내 줄) → 라디오 순으로 따라온다. sticky GNB 밑에 묻히지 않게 하는 `scroll-margin-top`은 05 §15-2·화면정의 §4-2 ⑥. `role="status"` 라이브 영역은 쓰지 않는다 |
| 진행 줄 | `{levelLabel} 레벨 · {n}문항`. **"단계"라는 낱말을 쓰지 않고**, 전체 분모도 쓰지 않는다(한 번에 치는 것은 한 레벨뿐이다) |
| 결과 머리글 | 캡션 `진단 결과 · {title}({levelLabel})` + `.diag-headline` = **`이 레벨은 충분해요`** / **`이 레벨은 아직 조금 어려워요`** |
| 결과 표 | 지금까지 친 레벨만 행, **레벨 순**, 레벨당 **한 행**, 행이 하나여도 그린다. **3열** — `레벨` / `정답 수 / 문항 수`(한 칸에 `4 / 6`) / `판정`. 레벨 칸은 행 머리(`<th scope="row">`) |
| 판정 낱말 | `통과` / `—`. **"미달"·"불합격"을 화면에 쓰지 않는다** — 진단이지 시험이 아니다(벌주지 않는다) |
| 결과 버튼 | primary 하나 고정. 이어가기(`{levelLabel} 도전하기 ›` / `{levelLabel} 확인하기 ›`) → `{title} 코스 시작하기` → ghost `다른 레벨 고르기`. **없는 버튼은 자리도 만들지 않는다** |
| 추천 한 줄 | 표 아래 `지금 시작한다면 {title}({levelLabel}) 코스가 좋아요.` · 마지막 줄 `지금까지 친 레벨 기록은 저장되지 않아요. 새로고침하면 사라져요.` |
| 없어야 하는 것 | 정답 표시·근거 박스·"맞은 개수"·**갈래별 정답 수**가 **DOM에 없다**(CSS로 숨기는 것이 아니다). `.quiz-verdict`·`.quiz-evidence`도 없다. **`모름으로 처리` 문구**·`[disabled]`·확인 모달(`role=dialog`)도 없다(2026-09-16). **"정답 표시" = 문항의 정답을 드러내는 것**이다 — 결과 표의 열 제목 `정답 수 / 문항 수`는 판별 집계라 여기 걸리지 않는다(2026-09-15 정정: 테스트의 `/정답/` 정규식이 이 열 제목까지 잡아 명세와 어긋났다. 테스트를 좁혔고 명세는 그대로다) |

**왜 버튼이 아니라 라디오인가**: 제출 전까지 **답을 바꿀 수 있어야** 하고(§3-6), 다섯 중 하나를 고르는 것이 곧 라디오의 의미다.
즉시 채점 퀴즈(`QuizRunner`)의 보기가 `<button>`인 것은 **누르는 순간 채점이 끝나기 때문**이다 — 같은 모양이라고 같은 요소를 쓰지 않는다.
**레벨 선택도 같은 라디오**를 쓴다: 레벨마다 시작 버튼을 두면 화면의 주 버튼이 여섯이 되고(05 §3-2), 오조작을 되돌릴 곳이 없다.

**결과 표를 3열로 두는 이유**: `정답 수`와 `문항 수`를 열로 가르면 **분모만 들어 있는 열**이 하나 생긴다.
`4 / 6`은 한 칸에서 한 번에 읽히고, 분모는 행마다 다를 수 있어(3~6문항 — §3-6) **정답 수 옆에 붙어 있어야 의미가 산다.**
