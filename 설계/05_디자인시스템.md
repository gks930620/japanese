## 1. 한 줄 원칙

> **밝고 반듯하게.** 흰 바탕과 1px 선으로 구조를 만들고, 강조는 인디고 하나로 끝낸다.

정보량이 많아도 답답하지 않은 화면이 목표다. 이 사이트는 문법·한자·어휘가 끝없이 나열되는 학습 도구라
**장식이 아니라 위계**가 읽혀야 한다. 아래 모든 규칙은 이 문장을 지키는 방법일 뿐이다.

## 2. 네 가지 원칙

| # | 원칙 | 내용 |
|---|---|---|
| ① | **흰 바탕 + 1px 선으로 구조를 만든다** | 카드·패널·표의 경계는 `--border` 1px이다. **그림자는 hover에만 잠깐**(`--sh-2`). 상시 그림자로 면을 띄우지 않는다 |
| ② | **강조색은 인디고 하나** | `--point` 단색. **그라디언트를 쓰지 않는다.** 오렌지 `--point-2`는 "새로 생긴 것 / 여기부터" 표시에만 **아주 조금**(§3) |
| ③ | **흰 화면이 길어지면 연보라 면으로 끊는다** | `--hero-bg`. 히어로·구획 나눔이 이 면의 자리다. **`backdrop-filter`(유리)는 어디에도 쓰지 않는다** — 킷이 쓰지 않는 표현이다 |
| ④ | **크기 차이로 읽는 순서를 만든다** | 제목은 크고 굵게(`--w-heavy` 800 + `--display-tracking`), 본문은 `--t-md`(15px). 색을 늘리는 대신 **급간**으로 위계를 만든다 |

보조 규칙:

- **모양은 라운드 사각이다.** 버튼·입력은 `--r`(10px), 카드는 `--r-lg`(16px), 작은 타일은 `--r-sm`(8px).
  **알약(`--r-pill`)은 배지·진도 막대·아바타처럼 "값을 담은 조각"에만** 쓴다. 버튼을 알약으로 만들지 않는다.
  *(Halo 시절의 "버튼·칩·배지는 전부 알약, 예외 없다"는 폐기됐다.)*
- **면이 겹치면 안쪽을 낮춘다.** 카드 안 박스는 `--surface-alt`, 페이지 배경은 `--bg`.
  선 위에 선을 겹치지 않는다 — 카드 안 표의 바깥 테두리는 지운다.
- **의미색(`--ok`/`--warn`/`--err`)은 상태 표시용이다.** 버튼 배경에 쓰지 않는다(파괴적 동작 `.k-btn--danger`만 예외).
- **큰 제목은 자간을 좁힌다** (`--display-tracking` = -.035em).
- **`#hex`를 쓰고 싶어지면 토큰이 하나 부족한 것이다.** 하드코딩 대신 `frontend/src/styles/project-tokens.css`에
  `:root` + `:root[data-theme="dark"]` **두 벌**로 토큰을 추가한다(킷 `클래스-목록.md` §11-3).
  **킷 파일(`base`·`components`·`tokens`·`extras`)은 한 줄도 고치지 않는다** — 다음 킷 교체 때 사라진다.
  이 프로젝트가 실제로 추가한 토큰은 **`--font-jp`(일본어 폰트 스택) 하나뿐**이다.
  *(Halo 시절의 `--dim`은 킷의 `--overlay`로 대체됐다.)*
- 허용된 예외는 둘뿐이고 **둘 다 코드 주석에 사유가 적혀 있어야 한다**:
  카카오 브랜드 색(브랜드 가이드 고정값, 테마 종속 아님)과 `.tts-btn`의 28px 고정폭(§15-3, 3줄 병기 줄 높이를 지키는 값).

## 3. 강조 예산 — 이 프로젝트의 적용 규칙

> Halo 시절엔 "그라디언트 예산"이었다. Lets에는 그라디언트가 없으므로 **세는 대상이 바뀌었다.**
> 예산이라는 장치 자체는 남는다 — 그것이 **정보 위계를 강제하는 방법**이기 때문이다.

### 3-1. 세는 것은 세 가지다

| 강조 수단 | 무엇 | 예산 |
|---|---|---|
| **A. 주 버튼** `.k-btn--primary` | 인디고 면 버튼 | **화면당 1개** |
| **B. 인디고 강조 면** `--point`/`--point-soft` 배경 | 활성 메뉴 밑줄·활성 탭·선택 칩·아바타 글리프·페이지네이션 현재·진도 막대 채움 | **화면당 6개 이하** |
| **C. 오렌지** `--point-2` | "새로 생긴 것 / 여기부터" 알약 배지 | **화면당 0~1개** |

**세지 않는 것**: `--border` 1px 선, hover 그림자, 의미색 상태 표시(정답·오류·완료), `--hero-bg` 연보라 면.
이것들은 초점이 아니라 구조·상태다.

### 3-2. 예산 규칙 (확정)

- **화면당 `.k-btn--primary`는 1개.** 어느 상태에서도 동시에 둘이 되지 않는다 — 상태가 전환되며 **라벨만 바뀐다**
  (퀴즈: 문제 풀기 → 다음 문제 → 다음 유닛). 같은 화면에 진행 버튼이 두 벌 생기면 그 화면은 잘못 설계된 것이다.
- **오렌지는 화면에 하나다.** 코스 목록의 "여기부터" 1장, 유닛 목록의 "여기부터" 1행. 둘이 같은 화면에 있으면 하나를 지운다.
  **오렌지를 반복 요소·상태색·버튼에 쓰지 않는다.**
- **반복 요소에 강조 면을 깔지 않는다.** 한자 타일 60개·문법 행 20개·어휘 표 행 50개·레벨 배지·태그·품사 라벨·적용 칩·결과 개수 — 전부 금지.
  **선택된 칩은 예외**다(선택은 상태이지 장식이 아니다) — `--point-soft`, `aria-pressed="true"`.
- **히어로 위 CTA는 `.k-btn--primary` 그대로.** 연보라 면(`--hero-bg`) 위 인디고 버튼은 대비가 충분하다.
  *(Halo의 "히어로 위엔 primary 금지 → 흰 알약" 규칙은 그라디언트 위 그라디언트를 피하려던 것이라 근거째 사라졌다.)*

GNB가 기본으로 소비하는 몫: 활성 메뉴 밑줄 **1개**(홈처럼 활성 메뉴가 없으면 0).
로고는 킷이 `--point` 글자색으로 칠하므로 **면이 아니라 글자다 — 세지 않는다.**

| 화면 | B(인디고 면) 내역 | 합계 |
|---|---|---:|
| 코스 목록 | 활성 메뉴 1 · 진도 막대 n(반복 아님, 카드당 1) | 1 + 진도 |
| 유닛 학습 | 활성 메뉴 1 · 현재 스텝 칩 1 · 아바타 1 | 3 |
| 자료실 목록 | 활성 메뉴 1 · 아바타 1 · 활성 탭 1 · 선택 칩 n · 현재 페이지 1 | 4 + 선택 칩 |
| 실력 진단 | (**GNB 활성 메뉴 없음** — 진단은 메뉴가 아니다) · 고른 레벨·고른 보기 면 n은 **세지 않는다**(선택은 상태다 — §3-2, §15-2) | 0 |
| 편집 모드 띠 · 편집 패널 · 저장 결과 | 0 (`--warn-soft` 띠 · `.k-btn--danger` · ghost만) | +0 |

**퀴즈·실력 진단·음성·편집 모드·영어 과정이 새로 들인 강조는 여전히 0개다**(§15·§16).
진도·보관함도 0이다 — 진도 막대 채움은 `--point` 단색이고 ★는 텍스트 글리프다.

### 3-3. 예산이 실제로 설계를 바꾼 선례

코스가 4개 AVAILABLE이 되자 코스 목록의 강조가 7개로 늘어 예산을 넘겼다.
→ **"첫 AVAILABLE 코스 1장만 강조"**로 바꿨고, 그 판정을 하드코딩하지 않고
**AVAILABLE 중 `courseNo` 최솟값**으로 계산하게 만들었다(`lib/courses.js`).
코스가 더 늘어나도 자동으로 유지된다.
**킷이 바뀌어도 이 결정은 살아 있다** — 강조 수단만 그라디언트 배지에서 오렌지 알약 배지(`.k-badge--pill`)로 바뀌었다.

> 예산은 장식 규칙이 아니라 **정보 위계를 강제하는 장치**다. 예산을 넘겼다는 건 "무엇이 제일 중요한지"를 정하지 않았다는 뜻이다.

## 4. 토큰 (단일 출처: `design_kits_lets/tokens.css`)

**값은 이 문서가 아니라 킷의 토큰 파일이 정한다.** 여기엔 어떤 토큰이 무슨 용도인지만 적는다.
전체 목록은 `design_kits_lets/tokens.css`를 직접 본다.

| 분류 | 토큰 | 용도 |
|---|---|---|
| 강조 | `--point` `--point-hover` `--point-soft` `--point-text` `--on-point` | 링크·아이콘·포커스 / hover / 연한 강조 면 / soft 면 위 글자 / `--point` 면 위 글자 |
| 오렌지 | `--point-2` | **"새로 생긴 것 / 여기부터" 알약 배지 전용**(§3-1 C) |
| 면 | `--bg` `--bg-sunken` `--surface` `--surface-alt` `--surface-hover` | 페이지 / 가라앉은 면 / 카드·패널 / **카드 안 박스·입력·표 헤더** / hover |
| 선 | `--border` `--border-strong` | 카드·표 구분선 / 입력 테두리 |
| 텍스트 | `--text` `--muted` `--muted2` | 본문 / 보조 / 라벨·캡션 |
| 의미색 | `--ok` `--ok-soft` `--ok-text` · `--warn` `--warn-soft` `--warn-text` · `--err` `--err-soft` `--err-text` | 면/글자 쌍이 이미 있다 — **`color-mix()`로 계산하지 않는다** |
| 섹션 면 | `--hero-bg` `--hero-fg` | **연보라 면**(원칙 ③). 히어로·구획 나눔 |
| 반경 | `--r-sm`(8) `--r`(10) `--r-lg`(16) `--r-pill`(999) | 작은 타일 / 버튼·입력 / 카드 / 배지·막대·아바타 |
| 간격 | `--sp-1`…`--sp-10` (4·8·12·16·20·24·32·40) | 여백은 전부 이 계단에서 고른다 |
| 타이포 | `--t-xs`…`--t-3xl` · `--w-normal`…`--w-heavy` · `--lh` `--lh-tight` `--lh-relaxed` · `--font` `--font-mono` | 본문은 `--t-md`(15px) / `--lh`(1.65) |
| 그림자 | `--sh-1` `--sh-2` `--sh-3` `--sh-point` | 거의 안 쓴다 / **hover 전용** / 모달 / 포커스 링 |
| 그 밖 | `--overlay` `--focus` `--nav-h` `--content-max`(1200) `--touch`(46) `--dur` `--ease` | `--overlay`는 확인 대화상자 딤(§12-1) |
| **프로젝트 확장** | `--font-jp` | **일본어 전용 폰트 스택.** 킷에 대응이 없는 유일한 값 → `frontend/src/styles/project-tokens.css` |

킷 `base.css`의 전역 규칙: 리셋, `box-sizing`, body 폰트 `--font`/`--t-md`/`--lh`, 포커스 링.
**웹폰트 다운로드 없음(시스템 폰트만)** 정책은 유지한다 — `--font`의 Pretendard는 있으면 쓰고 없으면 폴백된다.
**배경 메시(radial-gradient)는 사라졌다.** Lets의 바탕은 흰색이고, 화면을 끊는 건 `--hero-bg` 면이다.

CSS 로드 순서(고정):

```
design_kits_lets/base.css → components.css → tokens.css → extras.css
→ frontend/src/styles/project-tokens.css   (프로젝트 토큰만)
→ frontend/src/styles.css                  (도메인 스타일만)
```

- `mobile.css`는 **로드하지 않는다** — 앱형 셸(앱바·탭바·FAB)을 쓰지 않는다(§12).
- `styles.css`는 킷 `.k-*` 위에 **여백·크기·도메인 규칙만 얹는다.** 같은 것을 다시 정의하지 않는다.
  퀴즈·진단·음성·편집·영어 블록은 이 파일 맨 아래에 있고, **그 값의 근거는 §15·§16이다**.

## 5. 다크 모드 — `data-theme` 방식

- `<html data-theme="dark">`만 바꾸면 킷의 `:root[data-theme="dark"]` 토큰 한 벌이 덮어써지고 전 화면이 따라온다.
  **컴포넌트 CSS는 손대지 않는다.** Lets는 라이트·다크 두 모드를 모두 지원하고 **기본은 라이트**다.
- `document.documentElement.style.colorScheme`도 함께 세팅해야 스크롤바·`<select>` 같은 브라우저 기본 UI까지 어두워진다(자주 빠뜨린다).
- 설정값 3종: `"light" | "dark" | "system"`, `localStorage` 저장, 초기값 `system`.
  `system`은 **계산해서 `light`/`dark`를 명시**한다 — 킷의 `prefers-color-scheme` 폴백에 맡기지 않는다(둘이 어긋나면 원인을 찾기 어렵다).
- FOUC 방지: `index.html`의 `<head>` 인라인 스크립트가 **CSS 로드 전에** `data-theme`을 선적용한다.
- 구현: `frontend/src/lib/theme.js`.

다크에서 자주 나는 사고 3가지:

- **`input`/`select`/`textarea`에 `.k-input`/`.k-select`/`.k-textarea`를 안 붙이면 그 요소만 흰 배경으로 남는다.** 가장 흔한 사고다.
- **하드코딩이 한 곳이라도 남으면 그 요소만 라이트로 남는다** — `#hex`·`rgb()`·`color-mix()`를 전수로 없앤다.
- 라이트에서 `--border`로 보이던 경계가 다크에서 배경과 붙어 **면이 사라져 보인다** → 안쪽 면을 `--surface-alt`로 한 단 낮춘다.

## 6. 3줄 병기 (일본어 문장 표기의 표준형)

컴포넌트: `.jp-sentence` / `frontend/src/components/JpSentence.jsx`

```
ここは 教室です。        ① 원문      --t-xl(22px) / var(--text)   / --font-jp
ここは きょうしつです。   ② 가나 읽기  --t-md(15px) / var(--muted)  / --font-jp
여기는 교실입니다.        ③ 한국어 뜻  --t-sm(13.5px) / var(--muted2) / 본문 폰트
```

**세 줄의 크기 차이가 이 컴포넌트의 전부다**(원칙 ④). 본문이 커지거나 작아지면 세 값을 함께 다시 잡는다 —
급간이 눌리면 "원문 / 읽기 / 뜻"이 한 덩어리로 보인다.

규칙:

- **적용 범위는 "문장 단위 콘텐츠 전부"** — 문법 예문, 회화 대사, 정리 스텝 요약 예문, 자료실 문법 상세.
- **가나 줄 생략**: 원문에 한자가 없어 읽기가 원문과 같으면(`kana === null`) ② 줄을 아예 렌더링하지 않는다.
  표 형태에서는 읽기 열에 `─`를 넣는다(유닛 어휘표·자료실 어휘표 공통).
- **문장이 아닌 단위에는 쓰지 않는다.** 한자는 음독/훈독 별도 필드(`.kv-row` 나열), 어휘는 3열 표(단어/읽기/뜻).
  단 한자의 **예시 단어**는 3줄 스택(`.kanji-word`)이고, 유닛 학습과 자료실 상세가 이걸 공유한다.
- 반응형: ≤768px에서 원문 22px → **19px**.
- **라틴 문장은 같은 컴포넌트 + `latin` 클래스**로 자형만 되돌린다(`font-family: inherit`) — 영어 과정이 쓴다(§16-4).
  영어 데이터는 `kana`가 항상 null이라 위 "가나 줄 생략" 규칙이 그대로 걸려 **자동으로 2줄 병기**가 된다. 영어용 표기 컴포넌트를 새로 만들지 않는다.

탈락한 대안 — 다시 제안하지 말 것:

| 대안 | 왜 안 되나 |
|---|---|
| 후리가나 루비 | 어절 세그먼트 데이터가 필요해 제작비가 오르고, 8~9px로 작아져 왕초보에게 안 읽히며, 줄 높이가 흔들리고 복사 시 텍스트가 섞인다 |
| 로마자 병기 | 히라가나 읽기 습관 형성을 방해한다 — N5 학습 목표와 정면으로 충돌 |

## 7. 컴포넌트 재사용 규칙

> **새 화면은 새 디자인 언어를 만드는 일이 아니라 기존 컴포넌트를 재조합하는 일이다.**

0. **먼저 킷에서 찾는다** — `design_kits_lets/클래스-목록.md`. 대개 있다. 없을 때만 도메인 컴포넌트를 만든다.
1. **같은 내용은 같은 컴포넌트로.**
   자료실 문법 상세와 유닛 학습 문법 스텝은 같은 내용이므로 `GrammarBody`를 공유한다.
   두 벌로 두면 계약이 바뀔 때 한쪽만 갱신돼 "같은 콘텐츠" 감각이 깨진다.
2. **공통 부품을 자료실별로 복제하지 않는다** (`.lv-badge`·`.applied-chip`·`.empty-block`).
3. **기존 컴포넌트를 확장하는 것이 신규 화면을 만드는 것보다 낫다.**
   예: 자료실용 404를 새로 만들지 않고 `NotFoundCard`에 prop 2개(`to`, `label`)를 추가했다(기존 호출부는 기본값으로 그대로 동작).
4. **커뮤니티에서 쓰던 것을 그대로 쓴다** — `Pagination`, 검색 입력, 정렬 셀렉트. 자료실용 변형을 만들지 않는다.
5. **반복 요소는 크기를 낮춘다**: 유닛 문법 명칭 20px → 목록 17px, 한자 배지 72px → 타일 40px, 카드 `--r-lg` → 타일 `--r`.
6. **타일에는 카드 표현을 얹지 않는다** — hover 부상(`transform`+`--sh-2`)은 "누를 수 있는 카드"의 신호다.
   타일 60개가 전부 떠오르면 신호가 아니라 소음이다. 타일은 `--border` 1px + `--surface-alt`로 조용히 둔다.

### 7-1. 층 구조 — 킷 클래스는 `ui/` 안에만 있다

킷 규약: **"React라면 클래스를 그대로 쓰지 말고 얇게 감싼다. 감싸되 스타일은 만들지 않는다."**

```
components/ui/   ← 킷 어댑터. .k-* 조립만. CSS 0줄, style={{}} 0개
components/      ← 도메인 컴포넌트. ui/를 조립 + 도메인 클래스
pages/           ← 도메인 컴포넌트를 쓴다. .k-* 를 직접 쓰지 않는 것이 원칙
```

- **감싸는 것(`components/ui/`)**: `Button` `Card`(+head/body/foot) `Chip` `Alert` `Badge`
  `Field`(+`Label`/`Input`/`Select`/`Textarea`/`Help`) `Empty` `Skeleton` `Bar` `Stat` `Table` `Modal`.
- **감싸지 않는 것**: 셸(`.k-shell` `.k-topnav` `.k-main` `.k-footer` `.k-hero` `.k-page-title`) — **`Layout` 한 곳에만 나온다**.
  유틸(`.k-flex` `.k-stack` `.k-grid` `.k-spacer` `.k-muted` `.k-mono` `.k-section`) — `className`으로 직접 쓴다.
- **활성·선택·비활성은 클래스가 아니라 속성이다**: `aria-current="page"` / `aria-selected` / `aria-pressed` / `disabled`.
  `.active`·`.on`·`.sel` 같은 클래스를 새로 만들지 않는다.
- `ui/` 안에 `style={{ color: … }}`가 한 줄이라도 생기면 **그 순간부터 킷 교체가 안 된다.**

## 8. 상태별 UI 규칙 (새 목록 화면마다 다시 적용)

### 로딩은 2종으로 구분한다

| 상황 | 처리 |
|---|---|
| **첫 로딩** | 스켈레톤. **개수는 한 화면분만** (한자 타일 12, 문법 행 6, 어휘 행 10). 60개를 다 깔면 화면 전체가 맥동한다 |
| **갱신 로딩** (페이지·필터·검색) | **기존 목록을 유지하고 흐리게** (`.list-loading` — opacity .45 + pointer-events:none). 스켈레톤으로 갈아끼우면 스크롤이 튄다. 조회 훅이 이전 데이터를 유지해야 성립한다(`useLibraryList`가 `keepPreviousData`를 켠다 — 02 §4) |
| **재방문·뒤로가기** (같은 주소를 다시 마운트) | **즉시 표시.** 조회 훅의 캐시가 첫 렌더를 채우고 재요청은 뒤에서 조용히 한다 — 스켈레톤도 흐림도 얹지 않는다(08 C-23). 재요청 결과는 그 자리에서 갈아끼운다(부분 교체) |

- 검색 디바운스(300ms) 중에는 로딩 표시를 걸지 않는다.
- **스켈레톤에 스피너를 쓰지 않는다** — 자리를 미리 잡아 레이아웃 점프를 막는 것이 목적이다.

### 부분 교체 원칙

목록 화면이 0건이거나 오류일 때 **탭·검색창·필터바·적용 칩은 절대 사라지지 않는다.**
교체되는 것은 목록 영역과 페이지네이션뿐이다 — 사용자가 조건을 고쳐 빠져나갈 수 있어야 한다.
(전체 교체는 상세 화면에서만.)

### 빈 블록 금지

활용표가 없으면 표 자리와 제목까지 통째로 렌더링하지 않는다. 예시 단어 0개면 소제목째, 예문 0개면 블록째 없앤다.
**"없음"이라고 적힌 빈 상자를 남기지 않는다.**

**열 단위로도 적용한다** — `─`만 늘어선 열은 정보가 아니라 잡음이다.

| 대상 | 규칙 |
|---|---|
| **유닛 어휘 표** | 그 유닛의 어휘가 읽기(`kana`)/발음(`ipa`·`koApprox`) **전량 null이면 그 열을 헤더째 빼고 한 열 줄인다**(입문 유닛·영어 유닛이 여기 걸린다) |
| **자료실 어휘 목록** | **적용하지 않는다.** 여러 코스가 섞인 목록에서 열을 감추면 값이 있는 다른 행의 읽기까지 사라진다 |
| 한 행이라도 값이 있을 때 | 열을 유지하고 없는 행만 `─`(§6) |

스텝·블록도 같다: 유닛의 한자가 0자면, 표현이 0개면 **그 스텝 자체를 만들지 않는다**. "아직 없어요" 안내를 만들지 않는다(§12).

### 끝은 두 종류다 — 축하와 "여기까지 열렸다"를 같은 자리에 섞지 않는다 (2026-09-21)

**"다음이 없다"는 "끝냈다"가 아니다.** 유닛을 앞에서부터 채워 나가는 코스에서는 **열린 마지막 유닛**도
다음이 없다 — 거기에 완주 축하를 띄우면 코스 상세의 "채우는 중이에요"와 **정면으로 모순되는 안내**가 된다
(2026-09-21 결함 2). 판정 근거는 화면이 지어내지 않고 **응답의 `coursePlannedUnits`** 를 읽는다(설계/04 §2-3-A).

| 상태 | 정리 스텝의 자리 | 진행 버튼 |
|---|---|---|
| **완주 + 다음 코스 있음** | 축하 `k-alert--ok` | 다음 코스 |
| **완주 + 다음 코스가 준비중** | 축하 `k-alert--ok` — 앞 두 문장은 그대로 두고 **뒤에 자료실 한 문장만 덧붙인다** | 코스 목록 |
| **열린 데까지의 끝** (아직 채우는 중) | `.more-units-coming` — **중립 톤**. 축하하지 않는다 | **그 코스의 유닛 목록**(남은 열린 유닛으로 돌아가는 것이 유일하게 참인 행선지다) |

- 두 자리는 **동시에 뜨지 않는다**(§2-4 "진입 안내 줄은 한 번에 하나만"과 같은 판단).
- **2번과 3번은 다른 상태다.** 2번은 *이 코스는 끝났고 다음 코스가 없을 뿐*이라 축하가 사실이고,
  3번은 *이 코스가 아직 안 끝났다*라 축하가 거짓이다. 둘 다 "기다려야 한다"는 점만 같다.
- **기다리게 만드는 화면은 지금 할 수 있는 것을 준다**(§12) — 2·3번 모두 자료실로 보낸다.
  빈 약속이 아니다: 방금 배운 표현·어휘가 그대로 검색된다. 다만 문구는 **"배운 것"**까지만 말한다 —
  이 계약은 언어 중립이라 같은 문장이 일본어에도 쓰이고, "표현과 어휘"라고 쓰면 일본어(한자·문법)에서 거짓이 된다.

- **낱말은 planner가 정한다.** 화면이 정하는 것은 *무엇을 구분하는가*와 *어디에 서는가*까지다.

### 0건 문구는 3분기

| 상황 | 문구 | 버튼 |
|---|---|---|
| 검색어 있음 | `'{검색어}' 검색 결과가 없어요` (작은따옴표 인용 — 오타를 스스로 발견하게) | [검색·필터 초기화] |
| 필터만 | `조건에 맞는 항목이 없어요` + 걸린 조건 되읽기 | [필터 초기화] |
| **조건이 하나도 없는데 0건** (자료실이 아직 비었다) | `아직 준비 중이에요` + 왜 비었는지 한 줄 | 콘텐츠로 가는 링크(예: [영어 코스 보기]) |

세 번째는 **사용자가 고칠 수 있는 게 없는 상태**라 "초기화"를 권하면 거짓 안내가 된다.
조건 0건과 구조적 0건은 반드시 다른 문구여야 한다.

**필터 칩 줄에 없는 조건이 적용 칩에는 있는 상태가 정상이다** — 주소로 들어온 값(예: 한자 자료실의 `?level=INTRO`)은
칩 목록에 선택지가 없어도 **적용 칩에 띄워 해제할 수 있게** 한다. 조용히 지우면 사용자는 왜 0건인지 알 수 없다.

### 그 밖

- **문구에 숫자를 고정하지 않는다.** "1,415개", "총 1,000자" 같은 하드코딩 금지 — 전부 API 값을 쓴다.
- 범위 밖 페이지 번호는 **조용히 1페이지**로. 경고·토스트 없음.
- 로딩 실패는 "불러오지 못했어요" + [다시 시도]. 화면이 빈 채 방치되지 않는다.

### 진도·보관함이 화면에 얹힐 때 (2026-08-14 확정)

| 규칙 | 내용 |
|---|---|
| **진도 0이면 막대를 그리지 않는다** | 빈 막대를 깔면 "안 한 일"이 강조된다. 준비중 코스도 막대 없음 |
| **진도 때문에 에러 화면을 만들지 않는다** | 진도·보관함 조회가 실패하면 **진도 없는 화면과 똑같이** 그린다(부가 정보이지 본문이 아니다). 단 **보관함 화면의 목록 실패는 예외** — 그건 본문이라 [다시 시도] 카드를 보여준다 |

| **저장 표시를 만들지 않는다** | 자동 저장(스텝 이동·진입)에 스피너·토스트가 없다. 실패해도 조용하다. **손으로 누른 것(완료 토글·★)만** 실패를 인라인 한 줄로 알리고 표시를 되돌린다 |

## 9. 주소(URL)가 목록 상태의 단일 출처

- 검색어·필터·정렬·페이지는 **쿼리스트링**에 둔다. 컴포넌트 state에 이중으로 두면 뒤로가기가 어긋난다.
  `useSearchParams` 한 곳에서 읽고 쓴다(검색 입력만 디바운스용 로컬 state, 300ms 후 `replace`).
- **기본값은 주소에서 생략한다** (`page=1`, 기본 정렬, 빈 `q`).
- 상세 → "목록으로"는 **직전 목록 주소를 그대로 복원**한다(브라우저 뒤로가기와 결과가 같아야 한다).
- **순간 상태는 주소에 넣지 않는다** — 어휘 아코디언 펼침, 유닛 학습 스텝(진도 저장이 복원한다), 퀴즈·진단 진행, 입력 중인 폼, 되돌리기 자리표시자, 대화상자.
- 필터·검색이 바뀌면 1페이지로 복귀하고, 페이지 이동 시 목록 상단으로 스크롤을 리셋한다.
- **상세 화면 안의 하위 목록 페이지**(글의 댓글 `?cpage=`)도 주소에 두되 **replace**로 쓴다 — 장소가 아니라 하위 목록이라 히스토리를 쌓지 않고, 스크롤 규칙(아래)에도 걸리지 않아 본문 위로 튀지 않는다. 0-base, 0은 생략.
- **스크롤 규칙은 셋뿐이고 한 곳(`Layout`의 `useScrollRestoration`)에서만 지킨다**: 새 주소(PUSH)는 **맨 위**, 뒤로/앞으로·새로고침(POP)은 **보던 위치**(콘텐츠가 그 높이에 닿은 뒤에 옮긴다), replace는 **그대로**. 화면이 `scrollTo`를 직접 부르는 것은 같은 주소 안의 상태 전환(유닛 스텝)뿐이다.
- **페이지당 개수는 어떤 화면 폭에서도 바뀌지 않는다** (한자 60·문법 20·어휘 50).
  기기마다 다르면 **주소를 공유했을 때 다른 목록**이 나온다.

> **새 화면에서 "이 상태를 어디에 둘까"를 정하는 순서** (2026-09-20 전수 점검에서 쓴 기준 — 27화면을 이 순서로 판정했다)
>
> 1. **위 규칙이 이미 정한 것은 그대로** — 검색어·필터·정렬·페이지는 주소, 순간 상태는 주소 금지.
> 2. **진도 저장이 이미 복원하는 것은 주소로 옮기지 않는다** — 같은 사실을 두 곳에 두지 않는다(08 C-7). 유닛 학습 스텝이 이 경우다.
> 3. **입력 중인 글 · 퀴즈·진단 진행 · 되돌리기 · 대화상자는 주소 금지** — 공유 링크에 남으면 안 되고 히스토리를 더럽힌다.
> 4. **서버 데이터는 주소의 일이 아니다** — `useApiQuery` 캐시가 답이다(02 §4 · 08 C-23).
>
> 순서가 중요하다: 2·3을 건너뛰고 "복원되면 좋으니 주소에 넣자"로 가면 **같은 사실이 두 곳에 생기거나**(2) **공유하면 안 되는 것이 링크에 실린다**(3).

한 줄에 3개 이상 서던 자리는 `--sm`으로 낮추거나 줄을 나눈다.

가로 스크롤 정책 — **목적에 따라 갈린다**:

  정보는 사라지지 않고 `.vocab-meta` 줄로 내려간다.

## 11. 접근성

- **탭 줄은 `role="tablist"`가 아니라 일반 내비게이션 링크(`<Link>`)다.** 주소가 바뀌는 페이지 이동이므로
  새 탭 열기·주소 복사가 되어야 한다.
- 어휘 표의 확장 행: `<tr>` 안에 `<button>`을 넣지 않고 **행 자체에 `role="button"` + `aria-expanded` + `tabIndex=0`**
  (Enter/Space 토글). 확장된 내용은 `aria-hidden` 처리하지 않는다(스크린리더가 읽어야 한다).
- 새 탭 링크: `target="_blank" rel="noopener noreferrer"` + **`aria-label`에 "(새 탭에서 열림)"** + 시각 예고 글리프 `.ext-mark ↗`.
- **포커스 링은 킷이 준다**(`--sh-point` / `--focus`). 우리가 다시 정의하지 않고, `outline: none`으로 지우지도 않는다.
  Tab으로 모든 버튼·링크에 링이 보여야 한다.
- **상태는 클래스가 아니라 속성으로 표시한다**: 현재 위치 `aria-current="page"`, 선택 `aria-pressed`,
  탭 선택 `aria-selected`, 비활성 `disabled`, 오류 `aria-invalid="true"`.
  접근성과 스타일을 한 번에 얻는 것이 킷 계약의 설계다.
- **모든 `<table>`은 `.k-tablewrap` 안에 넣는다** — 없으면 좁은 화면에서 페이지가 가로로 터진다.

| **정렬을 칩으로** | 정렬은 택일이라 복수 선택 언어(칩)와 섞이면 오해된다 → 정렬은 셀렉트, 필터는 칩 |
| **없는 기능에 대한 사과 문구** | "획수 정보는 아직 없어요" 같은 안내는 결핍을 부각한다. 확장은 자리를 비워 두는 게 아니라 **구조로 확보**한다 — 한자 상세는 `.kv-row` 나열이라 나중에 행 2개만 추가하면 되고, 자료실 탭도 `.k-tabs` 기반이라 4번째 탭이 붙어도 안 깨진다 |

### 12-1. 유일한 예외 — 확인 대화상자 `.confirm-dialog` (2026-08-14 개정, senior-dev 승인)

**개정한 이유(2026-08-14, Halo 시절)**: 원래 금지의 근거는 "모달 = 반투명 유리 → 원칙 ③(blur는 헤더에만)과 충돌"이었다.
**blur를 쓰지 않는 대화상자는 그 근거에 걸리지 않는다.** 근거가 닿지 않는 곳까지 금지가 뻗어 있었던 것이다.
그리고 되돌릴 수 없는 삭제(보관함 전체 비우기·학습 기록 초기화·브라우저 기록 지우기·회원 탈퇴)를 인라인 확인으로 처리하면,
사용자는 "되돌릴 수 없다"는 사실을 **누른 뒤에** 알게 된다.

**Lets 전환 후에도 이 예외는 그대로다.** 근거가 "유리"에서 "학습을 중단시키지 않는다"로 바뀌었을 뿐,
되돌릴 수 없는 삭제만 확인받는다는 결론은 같다. 킷이 `.k-modal`을 제공한다고 해서 쓰임이 넓어지지 않는다.

| ① | **컴포넌트는 `components/ConfirmDialog.jsx` 하나뿐이다.** 화면마다 다른 대화상자를 만들지 않는다 |
| ② | **`backdrop-filter` 금지.** 딤은 불투명도만 있는 단색(킷의 `--overlay`)이다. 패널은 `--surface` **불투명** |
| ③ | **강조 0개.** 확인 버튼은 `.k-btn--primary`가 아니라 `.k-btn--danger`다 — 파괴적 동작을 주 버튼으로 만들면 "권장 행동"으로 읽힌다 |
| ④ | **되돌릴 수 없는 파괴적 동작에만.** 되돌릴 수 있는 것(별 빼기 등)은 대화상자가 아니라 **되돌리기 한 줄**로 처리한다 |
| ⑤ | **`<dialog>` + `showModal()`** 을 쓴다 — ESC 닫기·포커스 트랩·`aria-modal`이 공짜다. div로 흉내 내지 않는다 |
| ⑥ | **기본 포커스는 취소, 취소가 오른쪽.** 실수로 누르기 쉬운 자리에 파괴적 동작을 두지 않는다 |
| ⑦ | **본문의 숫자는 실제 값**이다("한자 34개를 모두 뺄까요?"). 하드코딩 금지 |

**여전히 금지인 것** (이 예외가 열어 준 것이 아니다):

- 정보를 보여 주는 모달, 입력 폼 모달, 바텀시트, 오버레이 내비게이션·검색, 이미지 라이트박스
- 토스트·인라인 안내로 될 일을 대화상자로 올리는 것 (학습·열람을 중단시키지 않는다는 기획 원칙)
- 대화상자 안의 강조 면·유리(blur)·2단 스크롤
- 대화상자로 **취소 가능한** 동작을 확인받는 것 (④의 반대)

> 이 예외를 더 넓히려면(예: 폼 모달) **여기 적힌 근거부터 반박해야 한다**(`08_결정기록.md` 서문 규칙).

**폼 모달 금지가 실제로 어떻게 풀렸나**: 관리자 편집은 모달 대신 **원본 블록 바로 아래 인라인 펼침**으로 만들었다(§15-4).
금지가 기능을 막은 게 아니라 더 나은 배치(변경 전 값을 보면서 고치기)를 강제했다. 폼이 필요해지면 **먼저 인라인을 시도한다.**

## 13. 이 디자인이 *아닌 것* (탈락 시안)

새 화면을 구상할 때 가장 빨리 방향을 잡아주는 목록이다.

| 탈락 시안 | 왜 안 되나 |
|---|---|
| **Halo (그라디언트 + 유리 + 그림자)** | **2026-09-03 교체됨.** 학습 화면은 문법·한자·어휘가 끝없이 나열되는 곳이라 화려함이 정보를 이긴다. 그라디언트 예산을 매 화면 세는 비용도 컸다 |
| Blueprint (다크 + 모노 + 고밀도) | 기본은 밝고 반듯하게. **다크는 옵션이지 정체성이 아니다** |
| Paper (크림 + 명조) | **세리프를 쓰지 않는다** |
| Brutalist (굵은 테두리 + 원색) | **굵은 테두리·원색 금지.** 선은 1px `--border`다 |
| Console (초고밀도) | **빽빽하게 채우지 않는다.** 여백이 재료다 |
| Warm (따뜻한 파스텔) | **색온도는 차가운 쪽**(인디고·연보라) |
| Bento (비균일 타일) | **균일한 카드 그리드**를 유지한다 |

한 줄로: **밝고 · 차갑고 · 반듯하고 · 균일하고 · 1px 선으로 구조를 만드는** 쪽.

> Lets 킷 자체의 "피할 곳"도 지킨다: **고밀도 관리자 표 · 감성 브랜드 랜딩 · 처음부터 어두운 화면.**
> 새 화면이 이 셋 중 하나로 흘러가면 킷을 벗어난 것이다.

## 15. 학습 도구 화면 규칙 (퀴즈 · 실력 진단 · 음성 · 편집 모드)

> 아래 네 도구는 **얹히는 기능**이다. 넷 다 새 강조를 0개 들여왔고, 기존 컴포넌트 위에 여백·상태만 얹었다.
> 새 화면에 이 도구를 붙일 때 여기 적힌 것 말고 새 언어를 만들지 않는다.
> ⚠️ **여기는 보여주는 방식만 적는다.** 문항을 어떻게 만들고(유형 11종·오답 풀·보기 구성·레벨별 표기 규칙), 진단 계단·추천을 어떻게 판정하고, 음성이 어떻게 동작하는가는 **`설계/09_학습도구_동작규칙.md`이 원본**이다. 생성 규칙과 화면 규칙을 두 곳에 적지 않는다(08 C-11).


### 15-1. **즉시 채점** 퀴즈는 한 벌뿐 — `QuizRunner`

> ⚠️ **2026-09-10 정정.** 예전 이 절은 *"진입이 셋(유닛 확인 문제 · 자료실 퀴즈 · 실력 진단)이지만 카드는 하나다"* 라고 적었다.
> **진단이 페이지 단위 제출로 개편되면서 거짓이 됐다**(09 §3-6·§3-7). 진단은 이제 `QuizRunner`를 쓰지 않는다.

**`QuizRunner`를 쓰는 곳은 둘이다 — 유닛 확인 문제 · 자료실 퀴즈.** 이 둘의 차이는 프리셋뿐이다.
시작 → 문제 → 결과는 **한 주소 안의 상태 전환**이다(라우트를 쪼개지 않는다 — 결과는 저장되지 않으므로 되돌아갈 주소가 없다).

| | 유닛 확인 문제 | 자료실 퀴즈 |
|---|---|---|
| 문항 수 | 유닛이 정한 상한 고정 | 칩으로 택일(기본 10) |
| 결과 primary | 다음 유닛(마지막이면 코스 완료 분기) | 자료실로 돌아가기(조건 복원) |

**실력 진단은 이 카드를 쓰지 않는다**(§15-2). 겉이 닮았다고 같은 컴포넌트가 아니다 — **상호작용 모델이 다르다.**
`QuizRunner`는 **한 문항씩 넘기며 보기를 누르는 순간 채점**하고, 진단은 **6문항을 한 화면에 늘어놓고 라디오로 고른 뒤 한 번에 제출**한다.

**무엇을 공유하고 무엇이 갈리나** (진단이 여기서 가져다 쓰는 것과, 절대 가져가지 않는 것)

| | 공유한다 — 같은 클래스·같은 값 | 갈린다 |
|---|---|---|
| 카드 | `.quiz-card`(640px 중앙) — 진단의 **네 상태 전부**가 이것 한 장이다 | 진단 레벨 화면은 그 **안에** `.diag-group` 2~3장 → `.diag-question`(`<fieldset>`) **6장**을 담는다. 퀴즈는 카드 안이 한 문항이다 |
| 진행 줄 | `.quiz-progress`(`--muted` `--t-sm` `tabular-nums`) | 문구가 다르다 — 퀴즈는 `{현재}/{전체} · 맞은 개수`, 진단은 `{레벨} · {n}문항`(분모 없음) |
| 지문 | `.quiz-prompt` · `.quiz-prompt-sub` | 진단은 `.quiz-prompt.glyph`(64px 낱자)를 **쓰지 않는다** — 한자 낱자 문항이 진단에서 빠졌다(09 §3-3) |
| 보기 | `.quiz-choices`/`.quiz-choice` — 세로 스택 · 폭 100% 좌정렬 · 알약 · 면 `--surface-inset` · 반복 요소라 **강조 면 금지** | **요소가 다르다**: 퀴즈는 `<button>`, 진단은 `<label>` + `<input type="radio">`(09 §3-7). **클래스는 같고 선택자가 갈린다** — 정오 클래스(`.correct`/`.wrong`)·hover 그림자·`:disabled`는 버튼 쪽 규칙이다 |
| 버튼 줄 | `.quiz-result-actions` | 진단 레벨 화면은 이 줄에 **버튼 하나**(제출)만 둔다. 진단 결과 화면은 셋까지 서되 **primary는 하나**다(§15-2) |
| 저장 안 됨 한 줄 | `.quiz-note` | 없음 — 진단 결과·시작 화면도 같은 한 줄을 쓴다 |
| 결과 카드 | `.k-stat` 면 낮추기 · `.k-tablewrap`/`.k-table` · 새 탭 링크 | 없음 |
| 채점 시점 | — | 퀴즈 = **누르는 순간**, 진단 = **제출 버튼** |
| 정오 표현 | — | `.quiz-choice.correct/.wrong` · `.quiz-verdict` · `.quiz-evidence` · "맞은 개수"는 **진단 DOM에 아예 없다**(09 §3-7) |
| 연출 | **정오 연출 금지 · 색만으로 정오를 전달하지 않는다** — 두 화면 공통 | 없음 |

**합치지 않는 이유**: 한 컴포넌트에 두 모델을 담으면 `mode` prop이 **요소 종류(button/radio)와 채점 시점까지** 갈라 놓는다.
그 시점부터 한쪽 화면을 고치면 다른 쪽이 조용히 깨진다. 같은 값을 공유하는 길은 **컴포넌트가 아니라 클래스·토큰**이다(위 표의 왼쪽 열).

**카드 규칙** *(아래는 `QuizRunner` — 유닛 확인 문제 · 자료실 퀴즈 — 의 규칙이다. 진단은 §15-2)*

- `.quiz-card` = 기성 `.k-card` + **폭 640px 중앙**. 읽는 면은 `--surface` 불투명.
- 진행 줄 `.quiz-progress`: "{현재} / {전체} · 맞은 개수 {n}", `--muted` `--t-sm`, **`tabular-nums`**
  (3/10 → 4/10에서 숫자 폭이 흔들리면 줄이 떨린다).
- 지문 `.quiz-prompt`: 문장형은 `.jp-sentence` 원문과 같은 급(`--t-xl`, ≤768px 19px),
  **한자 1~2자는 `.glyph`로 64px**(≤768px 48px) 가운데 정렬. 빈칸은 `＿＿` 글리프 — 새 장식을 만들지 않는다.
- **보기는 세로 스택**(`.quiz-choice`, 폭 100% 좌정렬, `--r`). 4개는 **반복 요소라 강조 면 금지**.
  hover는 글자색 `--point`(칩과 같은 문법).
- **채점 후 상태**: 정답 `--ok-soft`+`--ok-text`, 고른 오답은 `--err-soft`+`--err-text`
  (`.k-alert--err`와 **같은 식**. 순수 `--err`는 틴트 위에서 채도가 튄다).
  **`color-mix()`로 틴트를 계산하지 않는다 — 킷이 `-soft`/`-text` 쌍을 이미 준다.**
  나머지는 `disabled` + opacity .55. **정오 규칙은 `:disabled` 뒤에 와서 opacity를 되돌린다.**
- **색만으로 정오를 전달하지 않는다** — `.quiz-verdict`(`role="status"`) 한 줄이 "정답/오답"을 글자로 말한다.
- **정오 연출 금지.** 흔들림·번쩍임·효과음 없음. transition은 `color`·`box-shadow`뿐 — 조용한 90%다.
- 근거 `.quiz-evidence`: `--surface-alt` 박스(`--r`). 내부는 전부 기성(`.kv-row`·`.kanji-word`·`.jp-sentence`)이고
  **여백만 맞춘다**. 자료실 링크는 여기 넣지 않는다(결과 화면의 몫).
- 결과: 점수는 기성 `.k-stat`을 **카드 안에서** 쓰되 면을 `--surface-alt`로 낮추고 **테두리를 끈다**
  (surface 위 surface는 평평해 보이고, 카드 속 카드는 카드가 아니다 — §7-6과 같은 판단. 선 위에 선을 겹치지 않는다 — §2 보조규칙).
  정오 목록 `.quiz-result-row`는 행 구분선 `--border` 1px.
- **결과의 자료실 링크는 진입과 무관하게 전부 새 탭**(`.ext-mark ↗`). 같은 탭으로 나가면 결과 상태가 소멸한다.
- 버튼 줄 `.quiz-result-actions` 하나를 시작·문제·결과·에러·0문항 카드가 **전부 공유**한다. ≤768px에서 세로 100%.
- 카드 안의 `.k-stat`·표·근거 박스는 **hover 부상을 쓰지 않는다**(`--sh-2`/`--card-hover-shadow` 금지) — 누를 수 있는 것이 아니다.
- **"결과는 저장되지 않아요" 한 줄**(`.quiz-note`, `--t-sm` **`--muted`**)은 결과 화면에 항상 있다.
  (2026-09-10 정정: 이 줄은 `--muted2`로 적혀 있었으나 코드는 `--muted`였고, **`--muted`가 맞다** — §19-2의 보조 텍스트 최소선.)

**시작 화면 — 어느 레벨부터 볼지 고른다** *(2026-09-14 신규)*

> 와이어프레임·탈락 시안 비교는 **`진행사항/화면정의_2026-09_진단.md` §1-1·§3-1**. 여기는 그 형태를 고른 **규칙**이다.

**판단 기준**: 이 개편의 동기는 *"고르는 수고 < 처음부터 푸는 수고"* 다.
**고르는 일 자체가 새로운 귀찮음이 되면 이 개편은 실패한다** — 그래서 기준은 "한눈에 다 보이는가 / 몇 번 눌러야 하는가" 둘이다.
접히는 선택지(셀렉트·아코디언)는 이 기준에서 탈락한다.

- **형태는 세로 알약 스택**이다 — `.quiz-choices` / `.quiz-choice` + 라디오. 다음 화면의 보기와 **같은 부품**이라
  진단 전체가 한 벌로 읽히고(§7-1 — 비슷한 버튼을 또 발명하지 않는다), **새 CSS가 사실상 0**이다.
  세로 한 줄이라 "낮은 것 → 높은 것"이라는 순서가 배치로 읽힌다(격자로 놓으면 Z자로 꺾여 그 정보가 사라진다 — §19-5).
- **고른 뒤 [시작하기]다. 누르는 즉시 시작하지 않는다.** 진단은 한 주소 안의 상태 전환이라 레벨 화면에서 **뒤로 갈 곳이 없다** —
  즉시 시작은 오조작을 새로고침으로만 되돌리게 만든다. 고르기와 시작을 나누면 **커밋 지점이 눈에 보인다.**
  비용은 탭 한 번이고, 이 개편이 없애려는 수고는 *"30문항을 먼저 푸는 것"* 이지 탭 한 번이 아니다.
  덤으로 §3-2("화면당 주 버튼 1개, 상태가 바뀌며 라벨만 바뀐다")가 시작 → 제출 → 결과 내내 그대로 유지된다 — 6개 버튼은 그 규칙을 깬다.
- **기본 선택 = 목록의 첫 줄**(가장 낮은 레벨). *"모르겠으면 어디부터"* 의 답은 안내 문구가 아니라 **기본값**이 한다(§19-6).
  덕분에 **아무것도 안 고른 상태가 없어** [시작하기]가 `disabled`가 되는 일이 없다 — 비활성 버튼은 "왜 안 되지"를 만든다(제출 버튼과 같은 판단).
- 한 줄의 글은 **`{title}({levelLabel})` 한 줄**이다 — 결과 화면의 추천 줄·판정표와 **같은 표기**를 쓴다(§7-1).
  둘 다 **API 값**이고 코드(`N5`)를 노출하지 않는다(§16-2). 레벨만 적으면 "문자"처럼 N 코드가 없는 값이 무엇인지 안 읽힌다.
  한 줄을 제목·부제 두 줄로 쪼개지 않는다 — 알약 안에 2단 조판을 넣으면 다음 화면의 보기와 모양이 갈린다.
- 목록은 **입장 가능한 레벨만**이다(`stagePlan` — 1~6줄, 가변). **준비중 레벨 줄을 만들지 않는다**:
  고를 수 없는 줄은 고르는 수고만 늘리고, "아직 준비 중"은 §12가 금지한 사과 문구다. 준비중 코스 안내는 코스 목록의 몫이다.

- ⚠️ **레벨 목록을 면으로 묶지 않는다** — 아래 "갈래를 면으로 묶지 않는다"와 **같은 근거**다(면 계층이 이미 세 겹이라 흰 알약이 묻힌다).

- **이미 친 레벨**은 그 줄 오른쪽 끝에 판정 한 낱말을 붙인다 — 알약 본문보다 **한 급 낮춘 3단 라벨**이라 레벨 이름보다 먼저 읽히지 않는다.
  시작 화면에 판정표를 다시 얹지 않는다 — **목록 자체가 기록이다**(§19-6). 배지·면·색·아이콘을 쓰지 않는다(§12 레벨 배지 색 구분 금지와 같은 계열).

  `--muted`로 낮추면 읽어야 할 규칙이 각주처럼 보인다. 3단으로 내려가는 것은 "결과는 저장되지 않아요" 한 줄뿐이다.
- 제목 줄은 `.step-caption`("실력 진단") + `.step-title` 두 줄이다 — **유닛 학습 스텝과 같은 조판**이고, 진단만의 제목 스타일을 만들지 않는다.
- **"3분이면 알 수 있어요"는 여전히 없다.** 소요 시간을 약속하지 않는다.
  ⚠️ 이건 **이 화면만의 규칙이 아니다** — 진단으로 보내는 **유입 배너에도 그대로 적용된다**(위 "진입 배너" 항목의 두 줄).
- ⚠️ **지운 문장**: *"낮은 레벨부터 최대 {n}단계까지 올라갑니다."* — 계단 모델의 문장이라 한 판 모델에서 **거짓**이 됐다.
  `{n}`(최대 단계 수)을 화면 어디에도 쓰지 않는다.
- ⚠️ **"레벨마다 6문항"은 상한이지 약속이 아니다.** 재료가 모자라면 3~5문항이 나온다(09 §3-6).
  **시작 화면은 6을 말해도 되고, 사실을 말하는 쪽은 레벨 화면의 진행 줄이다** — 그래서 진행 줄이 **만들어진 수**를 그대로 적는 것이 중요하다.

**레벨 화면 — 6문항이 한 화면에, 갈래로 묶여서** *(2026-09-14 개정 — 갈래 묶음 추가. 예전 이름은 "단계 화면")*

- **카드는 한 장이다.** 6문항은 `.quiz-card` **안**의 갈래 묶음(`.diag-group` 2~3장) → `<fieldset>` 6장이고,

- **레벨 화면에는 제목 줄(`.step-caption`/`.step-title`)이 없다.** 맨 위는 진행 줄이다 —
  시작·결과·실패 카드가 "실력 진단"이라고 이미 말했고, 문제를 푸는 화면에서 제목은 6문항을 아래로 미는 군더더기다(§19-6).

  페이지 `--bg`(흰) → 카드 `--surface-alt`(회색) → **보기 알약 `--surface-inset`(흰)**.
  여기서 문항 블록을 한 겹 더 칠하면 흰 알약이 그 면에 **묻혀 사라진다** — §19-7이 말한 조용한 실종이다.
- 그래서 **구별은 선과 여백이 한다.** 이것은 §19-3("면은 색으로 구별한다")을 어기는 것이 아니다 —
  그 규칙은 **페이지 위의 카드**를 가르는 규칙이고, 여기는 **같은 판 위에 놓인 순서**를 가르는 일이다.
  순서는 선으로 가르는 것이 맞다(자료실 행 목록과 같은 문법).
  ⚠️ **2026-09-14 정정 — 선이 붙는 자리가 바뀌었다.** 예전에는 `.diag-question` **사이마다** 선이 있었다.
  갈래 묶음이 들어오면서 **선은 갈래 사이로 옮겨 갔고, 문항 사이에는 여백만 남는다**(바로 아래).
- `<fieldset>`·`<legend>`의 **브라우저 기본 테두리·여백·좌우 패딩을 전부 끈다.** 끄지 않으면 문항마다 회색 판 위에 이중 테두리가 생긴다.
- 위계는 세 단이다(§19-2):

| 단 | 문항 카드에서 | 값 |
|---|---|---|
| 1 제목 | **지문** — 읽어야 하는 일본어 | `.quiz-prompt` `--t-xl` · `--text` · `--tracking-tight` |
| 2 내용 | **보기 5개** | `.quiz-choice` `--t-md` · `--text` · `--w-bold`(기존 값 그대로) |
| 3 라벨 | **갈래 제목**(문항 바깥) | `.diag-group-title` `--t-md` · `--w-bold` · **`--text`** — legend보다 한 급 크고 한 급 진하다(아래 "갈래 묶음") |
| 3 라벨 | `<legend>`(번호·질문) | `--t-sm` · `--w-bold` · `--muted` — 라벨이라 굵기를 준다(§19-2 3단) |
| 3 라벨 | 진행 줄 `.quiz-progress` · 미응답 줄 | `--t-sm` · `--muted`, **굵기 없음**(문장이지 라벨이 아니다) |
| 3 라벨 | kana 병기 줄 | `.quiz-prompt-sub` `--t-md` · `--muted`(기존 값 그대로 — 일본어라 `--t-sm`까지 줄이면 획이 뭉갠다) |

- **지문을 `--w-heavy`로 올리지 않는다.** 일본어 자형은 큰 크기에서 굵히면 획이 뭉쳐 오히려 안 읽힌다 —
  위계는 **크기**(`--t-xl` vs `--t-md`)가 이미 만든다. 보기 알약의 `--w-bold`는 강조가 아니라 **누를 수 있다는 표시**이고 `.quiz-choice`와 같은 값이다.
- `<legend>`는 fieldset의 **첫 자식**이어야 하므로 질문 줄이 지문 **위**에 온다(기획 §4-2 와이어프레임은 지문→질문 순이었다).
  DOM 계약(09 §3-7)을 따르고, 읽는 순서로도 "무엇을 묻는지"가 먼저인 편이 낫다. 형식은 **`{번호}. {질문}`** 한 줄이다.
- **번호는 "1"이지 "1/6"이 아니다**(§19-6 — 6장이 다 보이는데 분모를 여섯 번 반복하지 않는다).
  **번호 원판·배지를 만들지 않는다** — 코스 목록에서 이미 뺀 장식이다(§19-4).
- 일본어가 나오는 줄(지문·kana 줄·N2~N1의 보기)에는 기성 유틸 **`.jp`** 를 붙인다 — 진단이 자형 규칙을 새로 정의하지 않는다.
- **kana 병기 줄**은 `.quiz-prompt-sub`(`--t-md` `--muted`)로 **원문 아래**다.
  기획 §9-2 ②는 "원문 위"라 적었지만, 우리 데이터는 글자 위 루비가 **불가능**하고(09 §3-4 제약) 줄 병기다 —
  위에 얹으면 읽는 법이 본문보다 먼저 읽혀 **원문이 밀린다**. 기성 보조 줄을 그대로 쓰는 편이 낫다.
- **`.quiz-prompt.glyph`(64px)를 쓰지 않는다** — 한자 낱자 문항이 진단에서 빠졌다(09 §3-3). 진단 지문은 언제나 단어·문장이다.

**갈래 묶음 — 6문항을 단어·문법·문장으로 나눠 보여준다** *(2026-09-14 신규)*

> 요구: *"테스트별로 문법, 어법, 단어어휘가 잘 나뉘어져 있으면 좋겠어."*
> 순서는 이미 **단어 → 문법 → 문장 고정**이다(09 §3-3). **없는 것은 순서가 아니라 구분이다.**
> 갈래의 정의와 이름 문구는 기획·09가 정한다. 여기는 **묶음의 시각적 위계와 상태**만 정한다.

**계층을 어떻게 만드나 — 선을 옮긴다** *(⚠️ 이것이 이 개편의 핵심 판단이다)*

구분 장치를 **더하면** 두 겹이 된다: 문항 사이 1px 선과 갈래 사이 1px 선이 같은 굵기라 **묶음이 안 읽힌다.**
그래서 더하지 않고 **옮겼다.**

| 경계 | 이전 | 지금 | 뜻 |
|---|---|---|---|
| **같은 갈래 안** 문항 사이 | `--border` 1px + `--sp-6` | **`--sp-6` 여백만 (선 없음)** | 한 무리다 — 가르지 않는다 |
| **갈래와 갈래 사이** | (없음) | **`--border` 1px + 위아래 `--sp-8`** + 갈래 제목 | 여기서 종류가 바뀐다 |

- **근접성이 묶음을 만든다.** 같은 갈래 문항끼리는 붙어 있어야 한 무리로 읽힌다 — 그 사이에 선을 그으면 **떼어 놓는 일**이다.
  선이 5개에서 2개로 줄어드는 것은 덤이다(§19-6 덜어내기). 남은 선은 **뜻이 하나뿐**이다: *"여기서 갈래가 바뀐다."*
- **선의 굵기·색을 새로 만들지 않는다.** 갈래 선도 `--border` 1px 그대로다 — 위계는 **선의 유무**가 만든다(있다/없다는 굵기 차보다 강한 신호다).
  `--border-strong`으로 두 단계 선을 만들지 않는다: 640px 한 단에 굵기가 다른 선이 섞이면 표처럼 보인다(§13 "고밀도 관리자 표" 회피).
- 여백도 `--sp-6` → `--sp-8` **한 급만** 올린다. 선이 이미 "있다/없다"로 갈라 주므로 **여백까지 크게 벌릴 필요가 없다** — 벌릴수록 카드만 길어진다.

**⚠️ 갈래를 면으로 묶지 않는다** *(가장 하고 싶어지는 일이고, 가장 하면 안 되는 일이다)*

면 계층이 이미 **세 겹**이다 — 페이지 `--bg`(흰) → 카드 `--card-bg`=`--surface-alt`(회색) → 보기 알약 `--surface-inset`(카드 안에서 `--surface` = 흰).
**네 번째 면을 만들지 않는다.** 이유는 셋이고, 셋 다 이 화면 밖에도 적용된다:

- 남은 중립 면은 `--surface-alt`와 **눈으로 구별되지 않으면서** 그 위 흰 알약의 대비만 깎는다 — 얻는 것 없이 잃는다(§19-7 조용한 실종).
- `--point-soft`는 **"고른 것"이라는 뜻을 이미 갖고 있다**(§19-3 — 면 색은 역할당 하나씩).
- `--surface-inset`은 **상속으로 계산되는 토큰**이라(§19-7-1) 중간에 면을 끼우면 그 안 알약을 **직접 다시 칠해야** 하고,
  그 순간 면 계층이 구조에서 절차로 되돌아간다 — §19-7-1이 없애려던 바로 그 상태다.
  *(실제 토큰 값 대조는 `진행사항/화면정의_2026-09_진단.md` §3-3.)*

**그래서 갈래는 선 + 여백 + 이름표로 묶는다.** 테두리 상자·아이콘·번호 원판·갈래별 색도 같은 이유로 없다(§19-4 — 수단 하나).

**갈래 제목의 위계 — legend와 지문 사이에 낀다**

| 줄 | 값 | 왜 |
|---|---|---|
| 지문(1단) | `.quiz-prompt` `--t-xl` · `--text` · 기본 굵기 | 읽어야 하는 일본어. **가장 크다** |
| **갈래 제목** | `.diag-group-title` **`--t-md` · `--w-bold` · `--text`** | 아래 참조 |
| 문항 `<legend>`(3단) | `--t-sm` · `--w-bold` · `--muted` | 번호·질문 |

- **legend와는 두 축이 동시에 갈린다**: 크기 한 급(15 vs 13.5)과 명도 한 급(`--text` vs `--muted`).
  한 축만 바꾸면(예: 같은 `--t-sm`에 색만 진하게) 흑백·저대비 화면에서 구별이 사라진다.
- **지문과는 크기가 압도적으로 갈린다**(22 vs 15). 갈래 제목을 `--t-lg`(17)로 올리면 지문과 경쟁하므로 올리지 않는다.
- 갈래 제목이 `--w-bold`인데 지문이 기본 굵기인 것은 §19-2("굵기는 1단에만")의 위반이 아니다 —
  **이 화면은 지문을 굵히지 않기로 이미 정했고**(일본어 자형은 크게 굵히면 획이 뭉갠다), 그래서 굵기 축이 비어 3단 라벨들이 쓰고 있다.
  갈래 제목은 `<legend>`와 **같은 계열의 라벨**이지 새 1단이 아니다. 위계는 크기와 명도가 만든다.
- `.step-caption`(`--muted` + `--label-tracking`)을 재사용하지 않는다 — `--muted`면 legend와 명도가 같아져 **둘이 구별되지 않는다.**
- 요소는 `<section class="diag-group">` + `<h2 class="diag-group-title">`이다. 중첩 `<fieldset>`으로 만들지 않는다 —
  문항마다 이미 fieldset/legend가 있어 낭독기가 그룹을 두 겹으로 읽는다. 제목이면 제목 요소를 쓴다.

**문항 번호는 전체 통번호다 (1~6). 갈래마다 1로 되돌리지 않는다**

- 진행 줄이 *"· 6문항"* 이라고 말하는데 갈래별로 다시 세면 **화면 어디에도 6이라는 수가 없다** — 말과 화면이 어긋난다.
  같은 번호("2번")가 세 번 나오면 미응답 줄의 *"아직 2문항을 고르지 않았어요"* 가 **가리킬 것을 잃는다.**
- 갈래는 제목과 묶음이 이미 말하고 있다 — 번호까지 갈래를 말하면 같은 말을 두 번 한다(§19-6).
  형식은 그대로 **`{번호}. {질문}`** 한 줄이고, 원판·배지를 만들지 않는다(§19-4).

**빈 갈래는 제목째 없다** *(§8 빈 블록 금지)*

- **문항이 0개인 갈래는 블록째 렌더링하지 않는다.** 제목만 덩그러니 남기지 않는다(§8 — 예문 0개면 블록째 없앤다).
  "문장 (0문항)"·"이 레벨에는 문장 문항이 없어요" 같은 안내를 만들지 않는다(§12 사과 문구 금지).
  N2·N1은 문장 갈래가 애초에 없으므로 **갈래가 2개인 화면이 정상**이다.
- **갈래가 하나만 남아도 제목은 그린다.** 제목은 구분 장치가 아니라 **이름표**이고, 그 문항들이 무엇인지는 여전히 새 정보다.
  화면 구조가 레벨마다 달라지지 않는 편이 낫다.
- **갈래 선은 "렌더된 갈래 사이"에만 생긴다.** 빈 갈래를 건너뛰고 선을 남기면 **첫 갈래 위에 선이 뜬다** — 선은 인접 선택자로 긋는다.
- 갈래별 정답 수·정답률을 **결과 화면에 만들지 않는다.** 2~3문항짜리 갈래 점수는 사실상 문항별 정오 노출이고(09 §3-1 위반),
  판정에 쓰지 않는 숫자를 화면에 두지 않는다(§19-6). 판정표에 갈래 열도 만들지 않는다.

**6장이 같아 보이는 것이 규칙이다** *(§19의 핵심 긴장 — 구별되되 튀지 않게)*

- **구별은 구조가 한다**: 문항 사이 `--sp-6` 여백 + 번호 라벨, 갈래 사이 구분선 + 갈래 제목. **강조 수단은 0개다.**
- 유형(단어·문법·문장)에 따라 **면·테두리·아이콘·번호 색을 바꾸지 않는다**(§19-4). 6장은 여백·글자 크기·보기 개수가 전부 같다.
  **갈래 구분은 문항 바깥에서만 한다** — 갈래가 달라도 문항 블록 자체는 똑같이 생긴다.
- 구분선은 **갈래 사이에 하나씩**이다. 선을 긋고 그 안에 또 테두리 상자를 만들지 않는다(선 위에 선 금지 — §2 보조규칙).
- 문항 사이에 팁·격려 문구·광고를 넣지 않는다. 6장 사이에 다른 것이 끼면 리듬이 끊겨 "한 벌"로 안 읽힌다.
- 문항 블록에 **hover 부상(`--sh-2` / `--card-hover-shadow`)을 주지 않는다** — 문항은 누를 수 있는 것이 아니다(§15-1과 같은 판단).
- **6장이 세로로 길다는 것을 화면 장치로 덮지 않는다** — 접기·탭·"다음 3문항" 더 보기를 만들지 않는다.
  한 화면에서 다 보고 한 번에 제출한다는 것이 이 개편의 요구 자체다(기획 A3). 스크롤은 문제가 아니다.
- **막힌 문항의 안내 줄(2026-09-20)은 이 규칙의 예외가 아니라 상태다.** "같아 보인다"는 장식이 한 장만 튀지 않는다는 뜻이고,
  미응답 문항은 **전부 같은 줄**을, 답한 문항은 **전부 없음**을 갖는다 — 같은 상태는 같게 보인다. 블록의 면·테두리·번호·보기는 그대로다(아래 "막힌 문항 안내 줄").

**보기 — 라디오 5개**

- `.quiz-choices` 안에 `<label class="quiz-choice">` + `<input type="radio" name="{문항 id}">` + `<span>보기</span>`.
  한 문항의 다섯 개가 같은 `name`이다(09 §3-7).
- **알약을 새로 디자인하지 않는다** — 클래스가 `.quiz-choice` 그대로다(폭 100% 좌정렬, `--r-pill`, `--t-md` `--w-bold`,
  면 `--surface-inset`, `--bw solid --border`, 세로 스택 10px). 학습 퀴즈와 진단의 보기가 서로 다르게 생기면 같은 제품으로 안 보인다.
- ⚠️ **같은 클래스를 두 요소가 쓰므로, 버튼 전용 규칙은 버튼에만 닿게 한다.** `.quiz-choice.correct`/`.wrong`·`:disabled` opacity·hover 그림자는
  `QuizRunner`의 것이다. 라벨 쪽에는 `:has(input[type="radio"])`로 갈라 **hover 그림자를 끄고** 라디오와 글을 가로로 앉힌다
  (`display: flex` · `align-items: center` · `gap: var(--sp-3)`). 이 분기를 빼먹으면 라디오가 글 위에 얹혀 줄이 어긋난다(§19-5).
- **라디오 점은 네이티브 그대로 두고 `accent-color: var(--point)`** 만 준다. 커스텀 원을 SVG·`::before`로 그리지 않는다
  (키보드 조작·낭독기·고대비 모드를 전부 다시 만들게 된다). 이 점은 **컨트롤의 기본 표시이지 강조 수단이 아니다.**
- **선택 상태는 면 `--point-soft` 하나뿐**(`:has(input:checked)`). §19-4 — 수단 하나다. 글자색·테두리·굵기를 함께 바꾸지 않는다.
  이 면은 킷에서 이미 "켜짐"의 뜻이고(칩 `aria-pressed`·재생 중 — §15-3), **§3-1 B 예산에서 세지 않는다** —
  §3-2가 선택된 칩을 예외로 둔 것과 같은 이유다(**선택은 상태이지 장식이 아니다**).
- **hover는 글자색 `--point`뿐. 그림자 금지** — 한 화면에 보기가 최대 **30개(6×5)** 다. 버튼 쪽 hover `--sh-2`가 그대로 걸리면 화면이 들썩인다.
  `:focus-visible`(`--sh-point`)은 그대로 둔다 — 키보드로 30개를 지나가는 화면이라 초점이 가장 잘 보여야 한다.
- **제출 전에는 몇 번이든 바꿀 수 있다**(09 §3-6). 고른 뒤 잠그거나 흐리게 만들지 않는다. **막힌 제출 뒤에도 같다**(기획 D23·A53) — 막혔다고 보기가 잠기지 않는다.
- **정오 상태를 라벨에 만들지 않는다** — 진단에서 `.correct`/`.wrong`은 어느 상태에서도 붙지 않는다.

**[모르겠어요] — 다섯 번째 보기, 성격이 다르다는 것만 보인다**

- 자리는 **언제나 맨 아래 고정**이고 셔플 대상이 아니다(09 §3-5). 문항마다·새로고침마다 위치가 바뀌지 않는다.
- 다르다는 표시는 **구분선 하나뿐**: 네 번째 보기와의 사이에 `--border` 1px 가로선(위아래 `--sp-2`).
  **글자색·면·크기·굵기는 나머지 넷과 완전히 같다.**
- ⚠️ **선은 알약의 테두리가 아니라 알약 사이의 빈 자리에 긋는다**(가상 요소). 알약에 `border-top`을 더하면
  이미 사방에 있는 1px 위에 또 선이 얹힌다(선 위에 선 금지 — §2 보조규칙).
- ⚠️ **선택자를 `.diag-question` 안으로 한정한다.** `.quiz-choices > :last-child`만 쓰면 **유닛 확인 문제·자료실 퀴즈의 네 번째 보기**에도 선이 그어진다 —
  같은 클래스를 두 화면이 공유하기 때문이다(§15-1의 공유 표). 공용 클래스에 화면 전용 규칙을 얹을 때의 기본 실수다(§19-7-2와 같은 계열).
- 왜 선인가(기획 §9-2 ③의 택일): ① 글자색을 낮추면 보기 라벨이 §19-2의 보조 텍스트 최소선 아래로 내려간다
  ② 색으로만 성격을 말하면 흑백·색각에서 사라진다(§15-1 "색만으로 전달하지 않는다"와 같은 계열)
  ③ 선은 **배치**로 말하므로 "여기서부터 다른 무리"라는 뜻이 09 §3-5의 맨 아래 고정 규칙과 그대로 겹친다.
- 선을 그리며 생기는 여백은 **선의 일부이지 두 번째 수단이 아니다.** 여기에 아이콘(자물쇠·물음표)·회색 면·이탤릭을 더하지 않는다.
- 선택했을 때의 표현은 나머지 넷과 **완전히 같다**(`--point-soft`). **"포기"를 시각적으로 벌주지 않는다** — 찍기를 걷어내려고 넣은 보기다.
- **유닛 확인 문제·자료실 퀴즈 화면에는 이 보기가 없다**(09 §3-5 — 진단 전용). 그쪽 `.quiz-choice` 스택은 4개 그대로다.

**kana 줄이 있고 없고는 맞추지 않는다** *(기획 §9-2 ②에 대한 판단)*

기획은 *"kana 줄 유무로 카드 높이가 흔들리지 않게 하는 방법을 designer가 정하라"* 고 넘겼다. **자리를 비워 두지 않는 쪽으로 정했다.**

- kana 줄은 **레벨이 결정한다**(09 §3-4). `REPLACE`(입문·N5)·`NONE`(N2·N1) 단계는 **6장 모두 kana 줄이 없다** — 맞출 것이 애초에 없다.
  `BOTH`(N4·N3)에서만 문항마다 갈린다(한자가 없는 지문에는 kana를 얹지 않는다).
- **문항이 세로로 쌓이기 때문에 높이를 맞출 이유가 없다.** §19-5가 높이를 맞추라고 한 곳은 **나란히 선 카드**였다
  — 가로로 놓인 것들의 **아래 끝**이 어긋나면 지저분해진다. 세로 한 줄에서는 어긋날 상대가 없다.
- 그래서 **빈 kana 줄도, 자리를 잡는 `min-height`도 만들지 않는다.** 여섯 문항에 빈 줄 여섯 개를 깔면 화면만 길어지고 얻는 것이 없다(§19-6).
- **리듬은 블록 높이가 아니라 일정한 여백과 구분선이 만든다** — 문항 사이 `--sp-6` + `--border` 1px이 고정이라
  지문이 1줄이든 2줄이든 **다음 문항이 같은 간격으로** 시작한다. 이것이 이 화면에서 §19-5를 지키는 방식이다.

**진행 줄 · 미응답 줄 · 제출 줄**

- 진행 줄 `.quiz-progress`: **`{레벨 표기} · {n}문항`**. **전체 분모를 쓰지 않는다** — 총 문항이 가변이라 "5 / 36"은 거짓 약속이다.
  레벨 표기는 시작 화면의 목록·결과 화면의 판정표와 **같은 값**을 쓴다(**API 값**. "문자"처럼 N 코드가 없는 값이 실제로 있다 — 09 §3-1).
  ⚠️ **2026-09-14 — "단계"라는 낱말은 계단 모델의 잔재다.** 한 판 모델에는 단계가 없다.
  최종 문구는 기획이 정하고, **화면 규칙은 "레벨 이름 + 만들어진 문항 수, 분모 없음"** 이다.
- **`{n}`은 "만들어진 문항 수"다.** 6을 못 채운 단계에서는 그 수가 **사실**이다(09 §3-6) — 4문항이면 *"· 4문항"* 이라고 적는다.
  6으로 고정하거나 *"6문항 중 4문항"* 처럼 변명하지 않는다. 화면은 **화면에 실제로 있는 것**을 말한다.
- **통과선(`ceil(n×2/3)`)을 화면에 적지 않는다.** 몇 개를 맞혀야 하는지 알려 주면 사용자가 자기 답을 세게 되는데,
  정오를 보여주지 않기로 한 규칙(09 §3-1)과 어긋난 기대를 만든다.
- 남은 수 줄(미응답 안내)은 **제출 버튼 바로 위 한 줄**, `.quiz-note`(`--t-sm` `--muted`) — 결과 화면의 "저장되지 않아요"와 **같은 급**이다.
  **경고 띠(`.k-alert--warn`)가 아니다** — 제출을 시도하기 전에는 오류가 아니라 **사실**이고, 시도한 뒤에는 **조건**이다. 문구 하나로 둘 다 된다(기획 D22·Q14).
  문구 *"아직 {n}문항을 고르지 않았어요 — 모두 고르면 제출할 수 있어요."* 미응답 0이면 **줄이 통째로 없다**(빈 자리도 남기지 않는다).
  ⚠️ **2026-09-20 — *"그대로 제출하면 모름으로 처리돼요"* 는 거짓이 됐다.** 그대로 제출되지 않는다. 이 문구는 화면 어디에도 없어야 한다(기획 A51).
  - 이 줄은 보기를 고를 때마다 바뀌므로 **`role="status"`를 붙이지 않는다** — 낭독기가 클릭마다 떠든다.
    읽히는 자리는 제출 버튼의 **`aria-describedby`** 다(**버튼에 닿았을 때만** 읽힌다). **연결한다** — 사실 안내였을 때는 안 해도 됐지만
    **제출 조건**이 된 지금은 버튼에 닿은 사람이 "왜 안 되는지"를 그 자리에서 들어야 한다(기획 D25·A55).
    줄이 없을 때(미응답 0)는 속성도 없다 — 없는 id를 가리키는 속성을 남기지 않는다.
- 제출 버튼: `.quiz-result-actions` 재사용, **화면에 버튼 하나**(`.k-btn--primary`).
  ⚠️ **2026-09-14 — 라벨 분기가 사라졌다.** 제출은 언제나 결과 화면으로 가므로 라벨은 **`제출하고 결과 보기 ›` 하나**다.
  *"제출하고 다음 단계로 ›"* 는 계단 모델의 라벨이라 폐기한다 — 다음 레벨로 갈지는 **결과 화면에서 사용자가 고른다.**
  라벨을 *"다 고르고 제출"* 류로 바꾸지도 않는다 — 라벨은 목적지를 말하는 자리다(기획 D22).
- **미응답이 있으면 제출되지 않지만, 비활성화하지 않는다**(2026-09-20 개정 — 09 §3-6 · 기획 D19·D20). **누르면 첫 미응답 문항으로 이동한다.** 모달도 없다.
  비활성 버튼은 "왜 안 되지"라는 질문을 만들고(§15-4와 같은 판단), 모달은 **지나가는 문에 문을 하나 더 다는 일**이다 —
  이 두 근거는 그대로 살아 있고, **이번 결정이 그 근거 위에 서 있다.** `disabled`는 "왜"는 답해도 **"어디"는 답하지 못한다**;
  실수로 건너뛴 사람은 자기가 어디를 건너뛰었는지 모른다는 것이 이 변경의 전제다. 그래서 막는 방식은 회색 버튼이 아니라 **누르면 화면이 데려가는 것**이다.
  - 누르면: ① **번호가 가장 작은 미응답 문항**으로 이동(필요한 만큼 스크롤 + 초점. 이미 보이는 자리면 초점만) ② **미응답 문항 전부**에 안내 한 줄(아래 "막힌 문항 안내 줄")
    ③ 남은 수 줄은 그 자리 그대로(화면이 위로 가서 안 보이는 것은 정상). 자동으로 무엇을 고르거나 바꾸지 않는다.
  - **막힌 제출은 잠그지 않는다**(기획 D23). 언마운트도 `useRef` 가드도 실제 제출에만 딸려 있다 — 막힌 뒤에도 보기·버튼이 그대로 살아 있고,
    답을 바꾸고(A4) 다시 누를 수 있다. 다 채웠다고 **자동 제출하지 않는다** — 다시 눌러야 제출된다(자동 진행을 없앤 2차 방향 그대로).
  - **[모르겠어요]는 답이다.** 6문항 전부 [모르겠어요]여도 미응답 0이라 제출된다(기획 D24) — "빈칸 금지"가 "모름 금지"로 읽히면 안 된다.
- **연타는 화면이 아니라 핸들러가 막는다**(첫 클릭만 처리 — 09 §3-6). 채점은 **로컬 계산이라 기다림이 없다** —
  제출 즉시 결과 화면으로 **화면 자체가 바뀌므로** 버튼 라벨을 *"채점 중…"* 으로 바꾸거나 스피너를 새로 만들지 않는다.
  두 번째 신호를 얹으면 **그 한순간을 위해** 상태가 하나 더 생긴다.
  막힌 상태의 연타는 **매번 같은 일**(그 시점의 첫 미응답으로 이동)이고 부작용이 없다(기획 E27) — 여기서도 중간 라벨은 없다.
  ⚠️ **제출과 결과 사이에 로딩 스켈레톤을 끼우지 않는다** — 2026-09-10 판에서 스켈레톤이 있던 자리는 *다음 단계 문항을 부르던* 구간이고, 그 구간은 사라졌다.
- ≤768px에서 버튼 세로 100% — `.quiz-result-actions` 기존 규칙 그대로다.

**막힌 문항 안내 줄 — 강조가 아니라 상태 표시다** *(2026-09-20 신규 — 기획 §24-2 · D20 · D21)*

> 기획이 정한 조건 넷: ① 그 문항 **안**에 있다 ② **수단은 이 한 줄뿐** — 면·테두리·번호 색·아이콘을 바꾸지 않는다 ③ 경고 띠·모달·토스트가 아니다
> ④ **훑어 내려오며 알아볼 수 있다**(초점이 떠난 뒤에도). 문구는 *"답을 골라 주세요 — 모르면 [모르겠어요]를 고르면 돼요."* (기획 D22 확정본).
> 제출을 **시도한 뒤**, 그 문항이 미응답인 **동안만** DOM에 있다 — 시도 전에는 어느 문항에도 없고(A50), 고르는 순간 사라진다.

- **자리는 `<legend>` 바로 아래, 지문 위**(fieldset의 **두 번째 자식**). §17-2가 말하는 "그 필드 아래"는 한 줄짜리 입력 기준이고 원칙은 **"원인이 있는 자리"** 다 —
  여기서 원인이 있는 자리는 fieldset 안이고, 그 안에서는 **위**가 맞다:
  ① 이동·초점이 도착하는 곳이 블록의 위다 — 눈이 떨어지는 자리에 안내가 있어야 한다.
  ② 읽는 순서로 **"어떻게"(안내)가 "무엇"(지문·보기) 앞**에 와야 한다. 지문을 읽고 보기를 다 지나서 안내를 만나면 이미 늦다.
  ③ 훑어 내려올 때 눈이 걸리는 곳은 legend 줄(블록의 첫 줄)이라 그 바로 아래가 가장 먼저 걸린다 — 조건 ④.
  ④ 보기 **아래**에 두면 [모르겠어요] 구분선 뒤에 붙어 **그 보기의 각주**로 읽히고, 초점이 블록 위에 놓였을 때 긴 블록에서는 화면 밖이다.
- **급은 `--t-sm`, 굵기 없음, 새 클래스 `.diag-question-help`.** 굵기가 없는 이유는 진행 줄·남은 수 줄과 같다 — **문장이지 라벨이 아니다**(§19-2 3단).
  - 킷 `.k-help--err`를 그대로 쓰지 않는다: **`--t-xs`(12px)** 라 회색 카드 위 라벨 최소선(§19-7-3 — `--t-sm`) 아래이고, 여백도 한 줄 입력 밑에 붙는 값이다.
    `.diag-question` 안에서 크기를 덮어쓰는 것은 **공용 클래스에 화면 전용 규칙을 얹는 일**이라 하지 않는다(아래 "CSS는 거의 다 이미 있다").
  - `.quiz-note`(`--muted`)를 쓰지 않는다: 그 급은 **"눈에 안 띄어도 되는 각주"** 로 설계된 것이고, 이 줄의 유일한 조건은 **"훑어 내려오며 알아볼 것"** 이다.
    회색 카드 위 `--muted`는 보조 텍스트의 **최소선**이고, 바로 위 legend가 같은 `--muted`라 답한 문항의 라벨 무리와 **구별되지 않는다** — 목적과 반대되는 급이다.
- **색은 `--err-text` 하나.** 면(`--err-soft`)·테두리·아이콘 없이 **글자색만**이다.
  - 근거 ① §2 보조규칙 — 의미색은 **상태 표시용**이고, 이것은 검증 상태다(§3-1이 "의미색 상태 표시"를 예산에서 세지 않는 이유와 같다).
    결과 화면의 통과/미달에 의미색을 금지한 것(아래 "결과 화면")과 어긋나지 않는다 — 그쪽은 상태가 아니라 **다음 행동의 근거**였다.
  - 근거 ② §17-2 — 특정 입력의 문제는 **그 자리에 `--err` 계열 글자 한 줄 + `aria-invalid`** 가 제품 표준이다. 진단 문항 화면은 문항 6개짜리 폼이다.
  - `--err`가 아니라 **`--err-text`** 인 이유: §15-1이 이미 판정했다 — *"순수 `--err`는 틴트 위에서 채도가 튄다."* 회색 카드 위 글자색 쌍은 `--err-text`다(킷 `.k-help--err`도 이 값이다).
    §19-7 점검: `--surface-alt` 위 `--err-text`는 킷이 쌍으로 준 값이라 밝은 테마·다크 모두 대비가 선다.
- **"6문항 전부 미응답이면 빨간 줄 여섯"** — 그렇게 된다(기획 E26). **괜찮은 이유 셋**:
  ① §17-2를 따르면 **원인이 여섯이면 표시도 여섯**이다. 첫 문항에만 붙이는 안은 이미 버렸고(기획 Q13 — 세 번 눌러야 한다),
     하나로 줄이면 버튼 옆 한 줄(기획 D20 (a)안)로 되돌아간다.
  ② 색은 **글자색 하나**다. 실패 카드에서 금지한 것은 `--err` **면**·아이콘이고, 필드 아래 글자색 한 줄은 §17-2가 제품 전체에서 **이미 치르고 있는 비용**이다.
  ③ **실제로 여섯이 한 번에 보이지 않는다.** 문항 한 장이 legend + 지문 + 보기 5개로 약 300px이라 한 화면에 두 장 남짓이고, 고르는 순간 사라진다(D21).
     사용자가 보는 것은 언제나 **"아직 안 고른 한두 장의 한 줄"** 이다.
- **§19-4·"6장이 같아 보이는 것이 규칙"과의 양립** — 이 줄은 **강조가 아니라 상태**다. 근거는 §3-2가 선택 칩을 예산에서 뺀 것과 같다(*선택은 상태이지 장식이 아니다*).
  "6장이 같아 보인다"는 **장식이 한 장만 튀지 않는다**는 뜻이고, 상태가 다른 장이 **그 상태만큼만** 다른 것은 예외다.
  **같은 상태 → 같은 표시**: 미응답 문항은 전부 같은 줄을 갖고, 답한 문항은 전부 없다. 문항 블록의 면·테두리·번호·보기·여백은 **그대로**다 — 수단은 이 한 줄뿐(조건 ②).
- **`aria-invalid` 문항에 따로 시각 표시를 만들지 않는다.** 이 줄이 곧 시각 표시다 — 줄은 `aria-invalid="true"`인 동안만 DOM에 있으므로 상태와 표시가 1:1이다.
  블록에 테두리·면을 더하면 수단이 둘이 되고(조건 ②), 면은 §19-7의 흰 알약 실종을 부른다. 킷의 `[aria-invalid]` 입력 테두리 규칙은 `.k-input` 것이라 여기 닿지 않는다.
- **낭독 연결**: 줄에 `id`, 문항 fieldset에 **`aria-describedby`**(그 id) + **`aria-invalid="true"`**. 라디오 다섯 개마다 붙이지 않는다 — 보기를 옮길 때마다 같은 문장을 다섯 번 듣는다.
  ⚠️ ARIA 1.2에서 `aria-invalid`는 `radiogroup`에는 허용되고 fieldset의 기본 역할 `group`에는 **허용되지 않는다** — 같은 `name`의 라디오 다섯 개를 담은 fieldset이므로
  **`role="radiogroup"`** 을 함께 준다. 최종 요소·속성 확정은 senior-dev(기획 D25). `role="status"` 라이브 영역은 여전히 없다 — 초점 이동이 이미 알린다.
- **이동은 즉시(instant)다 — 부드럽게 굴리지 않는다.** 목적은 **옮겨 간 곳을 찾는 것**이지 이동을 보여 주는 것이 아니다. 2~3화면을 부드럽게 넘기면
  초점 낭독(즉시)과 화면(늦게)이 어긋난다. `scrollIntoView`에 `behavior: "smooth"`를 **넘기지 않는다** — 넘기면 킷 `base.css`의
  `prefers-reduced-motion` 처리(`scroll-behavior: auto !important`)를 **우회**한다. 기본값(`auto`)이면 CSS가 정하고, 이 프로젝트는 어디에도 `smooth`를 두지 않는다.
  유닛 학습 스텝 바가 쓰는 호출(`scrollIntoView({ block })`)과 같은 방식이다.
  - **스크롤 기준점은 문항 블록의 위(fieldset)** 이지 라디오가 아니다 — 안내 줄과 legend가 보여야 한다. 초점은 **첫 보기 라디오**에 준다(키보드로 화살표가 바로 먹는다 — 기획 D25).
    초점을 주는 호출이 다시 스크롤하지 않게 한다(`focus({ preventScroll: true })`).
  - ⚠️ **GNB가 sticky(`--nav-h`)라** `block: "start"`로 올리면 legend가 헤더 밑에 묻힌다. `.diag-question`에 **`scroll-margin-top: calc(var(--nav-h) + var(--sp-4))`** 를 둔다.
    이것이 없으면 "이동은 했는데 안내가 안 보이는" 상태가 된다 — 조용히 깨지는 지점이다.

**정오를 숨기는 게 아니라 만들지 않는다** *(강화)*

- 진단 화면에는 `.quiz-verdict`·`.quiz-evidence`·"맞은 개수"가 **DOM에 없다**. CSS로 숨기면 "있는데 안 보이는 것"이라 계약과 다르다.
- **제출한 뒤에도 마찬가지다.** 방금 푼 6장을 정오와 함께 되돌려 주지 않는다 — 근거는 결과 표의 `4 / 6`이 준다(09 §3-1).
- 그래서 **"채점 결과" 중간 화면을 만들지 않는다.** 제출 → **결과 화면**, 하나뿐이다.
  ⚠️ **2026-09-14 — 통과/미달을 말하는 자리는 결과 화면 하나다.** 한 판 모델에서 결과 화면이 *"이 레벨은 충분해요"* 라고 말하는 것은
  이 규칙의 예외가 아니다 — 그것은 **판정**(레벨 단위 집계)이지 **정오**(문항 단위)가 아니다.
  판과 판 사이에 축하 화면·전환 연출을 끼우지 않는다는 결론은 그대로다.

**결과 화면 — 한 화면, 두 변형(통과 / 미달)** *(2026-09-14 전면 개정)*

> 와이어프레임·버튼 배치표는 **`진행사항/화면정의_2026-09_진단.md` §1-3**.

**한 화면이지 두 화면이 아니다.** 판이 끝나는 자리는 통과든 미달이든 **같은 자리**로 읽혀야 한다 —
조판을 두 벌 만들면 갱신이 한쪽만 되고(§7-1), 사용자에게는 "다른 화면으로 떨어졌다"는 인상이 남는다.
**갈리는 것은 세 가지뿐**이다: 머리글 문구 · 그 아래 한 줄 · 버튼 구성. 뼈대는 완전히 같다.

**통과/미달을 무엇으로 구분하나 — 글자다. 색이 아니다**

- 구분은 **`.diag-headline` 문구**가 한다. 그것이 이미 화면에서 가장 큰 글자(26px `--w-heavy` `--text`)라 **더 얹을 수단이 없다**(§19-4 — 수단 하나).
- ⚠️ **통과를 `--ok`로, 미달을 `--err`/`--warn`으로 칠하지 않는다.** 셋 다 걸린다:
  ① §2 보조규칙 — 의미색은 **상태 표시용**이고 여기는 상태가 아니라 **다음 행동의 근거**다.
  ② 통과를 초록으로 칠하는 순간 미달이 자동으로 빨강의 자리를 갖는다 — **진단이지 시험이 아니다. 미달을 실패로 낙인찍지 않는다.**
  ③ `.diag-headline`은 §19-2의 1단(제목)이고 1단의 색은 `--text`다. 색을 바꾸면 화면에서 가장 큰 글자의 규칙이 화면마다 달라진다.
- 면·아이콘·배지·일러스트·연출(폭죽·체크마크)도 없다. **이 화면의 인디고 강조 면(§3-1 B)은 0개, 오렌지(C)도 0개**로 유지된다.
- 판정이 낱말로 남는 자리는 **판정표의 판정 열 하나**다(아래).

**주 버튼은 "머리글이 내린 결론이 가리키는 행동" 하나다** *(§3-2 — 화면당 primary 1개)*

- 통과의 primary는 **[다음 레벨 도전하기]**, 미달의 primary는 **[추천 코스 시작하기]** 다. 나머지는 secondary → ghost.
- **왜 통과의 primary가 "다음 레벨"인가**: 화면이 방금 *"이 레벨은 충분해요"* 라고 말했다. 그 말과 주 버튼이 어긋나면 안 된다.
  방금 충분하다고 판정한 레벨의 코스를 주 버튼으로 권하면 **화면이 스스로를 반박한다.** (사용자 요구 원문도 *"다음 레벨에 도전해보세요"* 다.)
- **왜 미달의 primary가 "학습으로 나가는 버튼"인가**: §15-2가 실패 카드에서 이미 세운 원칙 —
  **"다시 눌러도 같은 곳에 머무를 수 있는 버튼을 주 버튼으로 두지 않는다."** [한 단계 아래로 해보기]는 또 미달할 수 있다.
  그리고 미달 화면에서 진단을 주 버튼으로 권하면 *"아직 멀었다"* 를 두 번 말하는 톤이 된다.
- **두 변형의 primary가 서로 다른 것이 맞다.** 규칙은 "언제나 학습으로"가 아니라 **"머리글의 결론을 잇는 행동 하나"** 다.
- **셋을 같은 급으로 두지 않는다.** [다시 진단하기]는 어느 변형에서도 `ghost` — 이 화면에서 가장 약한 선택지다.
- 순서는 primary → secondary → ghost 고정(`.quiz-result-actions` 기존 규칙). ≤768px에서 셋이 세로 100%로 쌓인다.
- 버튼이 **하나 빠지면 다음 순위가 primary를 물려받는다. 버튼이 둘이 되는 것이지 primary가 둘이 되지 않는다**(§3-2 — 라벨만 바뀐다). 아래 상태 표 참조.

**판정표 — 첫 판부터 표다**

> ⚠️ **2026-09-15 정정(senior-dev, 기획 D12·A32 기준)**: 아래 두 항목은 원래 *"판이 하나면 표 대신 본문 한 줄('{n} / {총} 맞혔어요')"* 이었다.
> 기획이 확정한 결과 문구(`진행사항/기획_2026-09_진단개편.md` §14-3)에는 그 문장이 없고 **정답 수는 표에만 있다** —
> 첫 판에서 표를 빼면 "같은 말 두 번"이 아니라 정답 수를 **한 번도 말하지 않는 것**이 된다(A19). 규칙 원본은 09 §3-7. designer가 문장을 다듬어도 뜻은 유지할 것.

- **행이 하나여도 기성 `.k-tablewrap` + `.k-table`을 그린다.** 근거가 언제나 같은 자리·같은 모양에 있어야 하고,
  첫 판에서 표를 본 사람만이 두 번째 판에서 **행이 쌓였다는 사실**을 알아본다. 한 행짜리 표는 헤더 + 한 줄이라 무게도 크지 않다.
- 머리글(`.diag-headline`)은 **판정만** 말하고 숫자를 말하지 않는다 — 숫자의 자리는 표 하나다(§19-6 — 같은 값을 두 자리에 두지 않는다).
- 열은 셋이고, 가운데는 **`정답 수 / 문항 수`를 한 칸에** 적는다. 09 §3-7이 세 값을 나열한다고 **열을 셋으로 쪼개라는 뜻이 아니다** —
  `5 / 6`은 한 덩어리로 읽혀야 의미가 서고, 쪼개면 640px 표에 숫자 열이 둘 생겨 헤더가 접힌다.
- **행은 친 판만**이고(안 친 레벨로 빈 행을 만들지 않는다 — §8), **레벨 순(낮은 것 → 높은 것)** 으로 세운다.
  시간순이 아니다 — 표의 쓸모는 "내 실력이 어디까지인가"라는 **지도**이고, 사용자는 위아래로 건너뛰며 칠 수 있다.
- **같은 레벨을 다시 치면 행을 늘리지 않고 최근 결과로 덮는다.** 같은 레벨 두 줄은 "어느 게 내 실력이냐"는 질문을 만든다(§19-6).
  *(판정 데이터 규칙의 원본은 09 §3 — 화면은 한 레벨 = 한 행을 전제한다.)*
- 판정 열은 **낱말**이다. 통과/미달 모두 글자로 적고 **색·배지를 쓰지 않는다.**
  ⚠️ 예전 값 `—`(미달)은 *미달 = 계단의 끝*이라 판정을 말할 필요가 적던 때의 표기다. 이제 미달은 **정상적인 판의 결말**이라
  `—`로 두면 `─`만 늘어선 열과 같은 잡음이 된다(§8). **최종 낱말은 기획이 정한다.**
- **"모름 개수" 열·문구, 갈래별 점수 열을 만들지 않는다**(09 §3-5 — 판정에 쓰지 않는 숫자를 화면에 두지 않는다, §19-6).
- 재료 부족의 사유 한 줄이 필요하면 **머리글 위**, `.quiz-note`다. **경고 띠를 쓰지 않는다** —
  사용자가 할 일이 없는 사정이고, 여기서 띠를 두르면 결과 화면의 주인공(머리글)보다 먼저 눈에 든다.
- "그 위 코스는 지금 준비하고 있어요"(`.muted-text`)는 **가장 높은 레벨을 통과 + 실제로 준비중 코스가 있을 때만** 그린다(09 §3-2·08 C-12 ②).
- "이 결과는 저장되지 않아요. 새로고침하면 사라져요." `.quiz-note` 한 줄은 **항상** 있다. 여러 판을 쳐도 마찬가지다.
- 코스명·레벨 표기는 전부 **API 값**이고 코드(`N2`)를 노출하지 않는다(§16-2). 시작 화면 목록과 **같은 표기**를 쓴다.

**재료가 모자랄 때 · 갈 곳이 없을 때 — 규칙** *(09 §3-6. 상황별 전수 표는 `진행사항/화면정의_2026-09_진단.md` §2)*

- **재료가 모자란 것을 사과하지 않는다.** 3~5문항이면 평소와 똑같은 레벨 화면이고, 진행 줄이 그 수를 사실대로 말할 뿐이다.
  사용자가 모르는 사정을 굳이 알리면 제품이 고장 난 것처럼 보인다.
- **문항을 만들 수 없으면 실패 카드**(`.quiz-card` + `.step-caption` + 사유 한 줄 + 버튼 줄).
  **`--err` 면·아이콘을 깔지 않는다** — 사용자가 뭘 잘못한 게 아니다. 진단은 목적이 아니라 수단이고, **학습으로 가는 길을 막지 않는다.**
  ⚠️ **한 판 모델에는 "첫 단계 / 2단계 이후" 구분이 없다.** 판마다 독립이라 **문항을 못 만들면 언제나 실패 카드**이고,
  앞 판의 기록이 있어도 결과 화면으로 넘기지 않는다(이 판은 판정이 없다).
  *"{레벨} 단계는 문제를 준비하지 못해 여기까지로 판단했어요"* 한 줄은 계단 모델의 문장이라 폐기한다.
- **갈 곳이 없는 버튼은 미렌더한다.** 가장 높은 레벨을 통과하면 [다음 레벨 도전하기]가, 가장 낮은 레벨에서 미달하면 [한 단계 아래로 해보기]가 사라지고
  **다음 순위가 primary를 물려받는다.** 비활성으로 남겨 두지 않는다 — 비활성 버튼은 "왜 안 되지"라는 질문을 만든다.
- 최고 레벨 통과에 **축하 연출·오렌지 배지를 새로 들이지 않는다.** 진단은 머무는 곳이 아니라 지나가는 문이다.
- **실패 카드의 버튼 셋** — `[일단 {첫 코스}부터 시작하기 ›]`가 **primary**, `[다른 레벨 고르기]`가 `secondary`, `[다시 시도]`가 `ghost`.
  §15-2가 이미 세운 원칙 그대로다: **다시 눌러도 같은 곳에 머무를 수 있는 버튼을 주 버튼으로 두지 않는다.**
  `[다른 레벨 고르기]`가 `[다시 시도]`보다 위인 이유는 **재료 사정이 레벨마다 다르기 때문**이다 — 성공 확률이 높은 행동이 위에 온다.
- ⚠️ **재료 부족과 호출 실패가 카드를 공유한다.** 문구는 같고 `[다시 시도]`의 뜻만 다르다.
  두 상황의 문구를 갈라 쓰고 싶어지면 먼저 물어라: **사용자가 다르게 할 행동이 있는가.** 없으면 화면도 하나다.
- **실패 카드에는 판정표를 얹지 않는다.** 기록은 사라지지 않는다 — `[다른 레벨 고르기]`로 돌아가면 시작 화면 목록의 판정 표시가 그대로 있다.
- 어느 상태에서도 **상단 안내 띠는 한 번에 하나**다. 사유 한 줄과 다른 띠가 같이 서면 하나를 지운다.
- **[다시 진단하기]는 시작 화면(레벨 선택)으로 돌아가되 판정표 기록은 유지한다.** 기록을 지우는 길은 새로고침뿐이고,
  그 사실은 *"이 결과는 저장되지 않아요"* 한 줄이 이미 말하고 있다 — 초기화 버튼을 새로 만들지 않는다.

**로딩 — 두 곳이고, 둘 다 기성 스켈레톤이다**

- 첫 진입(코스 목록 대기)과 **레벨 시작**(고른 레벨의 문항 준비), 두 곳 다 **`.diag-wrap` 안 카드 한 장 + `.k-skeleton` 줄**이고
  `<section aria-hidden="true">`로 낭독기에서 통째로 뺀다(§19-6 — `aria-hidden`이 붙은 장식은 잃을 것이 없다).
  **제출 뒤에는 로딩이 없다** — 채점은 로컬이고 다음 문항을 부르지 않는다.
- 레벨 시작 스켈레톤은 **진행 줄 + 지문 + 보기 덩어리**를 암시하는 줄 세 개(`sk-line w40` · `sk-line w70` · `sk-row`)다.
  **문항 6장·갈래 제목을 흉내 내지 않는다** — 실제로 몇 문항이 올지(3~6), 갈래가 몇 개일지(2~3) 모르고,
  6장을 그렸다가 4장이 오면 **있던 것이 사라져** 실패처럼 보인다.
  스켈레톤은 "무엇이 올지"가 아니라 **"여기가 채워질 자리"** 만 말하면 된다.
- **진단 전용 스켈레톤 클래스를 만들지 않는다.** 로딩 중에는 제출 버튼도 그리지 않는다 — 누를 것이 없다.

**CSS는 거의 다 이미 있다** *(선택자·속성까지 적은 인계 목록은 `진행사항/화면정의_2026-09_진단.md` §4)*

- **새 디자인 토큰은 0개다.** 진단이 쓰는 값은 전부 킷 `tokens.css`(+ `project-tokens.css`)에 이미 있다.
  ⚠️ 없는 토큰 이름을 써도 **CSS는 아무 말 없이 투명하게 렌더한다** — 쓰기 전에 파일에서 실재를 확인한다(§19-8 마지막 항목).
- **새 클래스는 다섯뿐**이다: `.diag-levels`(레벨 선택 fieldset) · `.diag-level-mark`(이미 친 레벨의 판정 낱말) ·
  `.diag-group` / `.diag-group-title`(갈래 묶음) · **`.diag-question-help`**(막힌 문항 안내 줄, 2026-09-20 — `--t-sm` · `--err-text` · 굵기 없음).
  나머지는 `.diag-wrap`·`.quiz-card`·`.quiz-choices`/`.quiz-choice`·`.quiz-note`·`.quiz-result-actions`·`.diag-headline`·`.k-table`·`.k-skeleton` 같은 **기성**이다.
  - 2026-09-20에 더한 값은 둘이고 **둘 다 토큰이 실재한다**(`tokens.css` — `--err-text` `--nav-h` `--sp-2` `--sp-4`):
    `.diag-question > .diag-question-help { margin: 0 0 var(--sp-2); font-size: var(--t-sm); color: var(--err-text); }` ·
    `.diag-question { scroll-margin-top: calc(var(--nav-h) + var(--sp-4)); }` (sticky GNB 밑에 목적지가 묻히지 않게).
    **킷 `.k-help--err`를 진단 안에서 크기만 덮어써 쓰지 않는다** — 아래 "화면 전용 규칙" 항목과 같은 이유다.
- ⚠️ **화면 전용 규칙을 공용 클래스에 얹지 않는다.** `.quiz-choice`는 세 화면(유닛 확인 문제·자료실 퀴즈·진단)이 공유한다 —
  라벨형 규칙은 `.diag-question`/`.diag-levels` **안으로 한정**하고, 선택자를 `:has(input[type="radio"])`처럼 일반화하지 않는다
  (특이도가 올라가 저쪽 버튼 규칙과의 우선순위가 조용히 뒤집힌다 — §19-7-2).
  **`.diag-levels`는 [모르겠어요] 구분선 규칙에 넣지 않는다** — 마지막 레벨 위에 선이 그어진다.
- **새 미디어쿼리는 없다.** 640px 한 단이라 ≤768px에서도 배치가 같고, 버튼 줄의 기존 `.quiz-result-actions` 규칙이 세 버튼을 알아서 세로로 세운다.

**플랫폼 차이**: 앱(Flutter)은 아직 없다. 도입할 때 6문항 화면은 **스크롤 한 화면 + 하단 고정 제출 바**가 되겠지만,
**웹은 제출 버튼을 고정하지 않는다** — 640px 한 단이라 스크롤 끝에서 자연히 닿고, 고정 바는 마지막 문항을 가린다.
**레벨 선택은 앱에서도 세로 목록이다** — 네이티브 피커·드롭다운으로 접지 않는다. "한눈에 다 보인다"가 이 화면의 요구 자체다.

**이 절을 적용한 결과물** — 와이어프레임 4종 · 상태별 UI 전수 표 · 탈락 시안 비교 · CSS 선택자 목록 ·
**§19-8 체크리스트 17항목 통과 확인**은 `진행사항/화면정의_2026-09_진단.md`에 있다.
**규칙의 원본은 이 절(§15-2)과 §19**이고, 그 문서는 **이번 구현에 적용한 결과**다 — 어긋나면 이 절이 이긴다.
구현·QA가 끝나면 그 문서는 지우고, 새로 생긴 "다음 화면에도 쓰이는 규칙"만 여기로 올린다.

### 15-3. 음성(TTS) — 줄 끝에 붙되 줄을 밀지 않는다

- **재생 버튼은 `.tts-btn` 하나뿐이다.** 붙는 자리가 몇 곳이든 컴포넌트는 하나다.
  28px 원형 + `flex: 0 0 28px` **고정** — 3줄 병기의 줄 높이가 흔들리지 않게 하는 값이다.
- **아이콘은 이미 로드된 Material Icons 글리프를 재사용**한다(대기 `volume_up` / 재생 중 `stop`).
  **새 아이콘 폰트·SVG를 들이지 않는다**(★가 텍스트 글리프인 것과 같은 원칙).
- 상태: 대기 = `--muted`, **배경 없음**(문장을 밀어내지 않는다) → hover `--point` →
  재생 중 `--point-soft` 배경 + `--point` + **`aria-pressed="true"`**. 강조 면·그림자 금지(반복 요소다).
- 같은 버튼이 재생/정지 토글이고, **클릭 전파를 막는다**(행 아코디언·행 이동으로 번지지 않게 — ★와 동일).
- 지금 읽는 대사 줄은 `.dialog-line.playing` — `--point-soft` **불투명** 배경.
- **붙이지 않는 곳**: 활용표, 한자 글자 자체. 낱자 음성은 학습에 쓸모가 없다.
- **속도는 칩 하나다** — 라벨 "느리게", 켜짐은 `.k-chip` + `aria-pressed="true"`. 2단계에 셀렉트·슬라이더는 과하다.
  **화면당 1개**, 눈에 띄지 않는 우측 끝(`unit-topbar` / `RefTopbar` / 표 위 / 결과 카드 캡션 줄).
  **선택은 localStorage에 전역 저장**되어 화면을 옮겨도 유지되고, **다음 재생부터** 적용된다.
  전용 클래스를 만들지 않는다 — 기성 `.k-chip` 그대로다.
- 캡션 줄에 컨트롤을 얹을 땐 `.step-caption.row-caption`(회화 스텝·결과 카드 공용).
- **음성이 없는 기기에서는 재생 버튼·전체 재생·속도 칩을 전부 미렌더하고 안내도 하지 않는다.**
  버튼이 전부 **줄 끝 append**라 미렌더 시 레이아웃이 음성 없는 화면과 100% 같다 — 이것이 자리 선정의 숨은 기준이다.
- 재생 실패(음성은 있는데 소리가 안 남)는 그 패널 상단 `.k-alert--warn` 한 줄, **화면당 1회만**. 닫기 버튼 없음.
- 화면·스텝을 옮기면 재생을 멈추고 시각 상태(`playing`·`aria-pressed`)도 함께 해제한다.

### 15-4. 편집 모드 — **로컬 전용 도구다**

- **켜지는 조건은 서버 상태 응답 하나뿐**이고, 꺼진 환경에서는 띠·[고치기]·패널이 **전부 미렌더**되어
  화면이 운영과 100% 동일하다. 상태 조회 실패 = 꺼짐으로 취급한다. 로딩·스켈레톤에도 [고치기]를 그리지 않는다.
- **앱에는 넣지 않는다.**
- 편집 모드 띠 `.editor-mode-bar`: **GNB보다 위**, `--warn-soft` 면 + `--warn-text` 글자, 얇은 한 줄, 중앙 정렬.
  **sticky 아님** — GNB만 sticky다. 겹쳐 붙는 층을 두 개 만들지 않는다. "상시"의 뜻은 **모든 화면에 렌더**다.
- 진입점은 **고칠 대상 블록의 제목 줄 우측**([고치기]는 `.k-btn--ghost .k-btn--sm`). 대상이 있는 자리에만 있다.
- **편집 패널은 모달이 아니라 원본 블록 바로 아래 인라인 펼침**이다(`.editor-panel`).
  §12가 입력 폼 모달을 금지하기 때문만이 아니라, **변경 전 값을 보면서 고쳐야** 하기 때문이다 — 대조가 오탈자 수정의 본질이다.
  **한 화면에 패널은 1개**, 열려 있는 블록의 [고치기]는 숨긴다.
- **패널 밖 클릭으로 닫지 않는다.** 인라인에서 밖 클릭은 스크롤·본문 클릭과 구분되지 않아 입력을 날린다.
  닫기는 [취소]·[✕]·ESC뿐이고, **고친 내용이 있으면 `ConfirmDialog`로 확인**한다(§12-1 ④의 정당한 적용 — 입력 폐기는 되돌릴 수 없다).
- **고칠 수 없는 값은 입력칸을 만들지 않는다**(제목에 읽기 전용으로만 보인다). 비활성 input은 "왜 안 되지"라는 질문을 만든다.
- 검증은 **어긴 칸 바로 아래 `.k-help--err` + 입력에 `aria-invalid="true"` + [저장] 비활성**. 서버가 400을 줘도 **같은 자리·같은 형식**으로 표시한다.
- 저장 실패·404는 **패널을 닫지 않고 입력값을 보존**한 채 패널 상단 `.k-alert--err`로 알린다.
  변경이 없으면 요청 없이 패널만 닫는다.
- 저장 결과는 `.k-alert--ok` + **`.editor-diff`(`--surface-alt` + `--font-mono`)** — 복사 대상임이 모양으로 읽힌다.
  복사 성공은 **버튼 라벨을 2초간 바꿔** 알린다(토스트 금지).
- 반복 행(`.editor-row`)은 좁아지면 **세로 스택**이다. 규칙표는 가로 스크롤을 허용하지만(§10)
  **편집 칸은 행 간 비교가 목적이 아니다** — 같은 표라도 목적이 다르면 정책이 갈린다.

## 16. 과정별 화면 규칙 (일본어 · 영어)

> 영어 과정은 **뼈대**다. 화면 셸은 일본어 것을 그대로 쓰되, 아래 다섯 가지가 갈린다.

### 16-1. ⚠️ 영어 화면에는 학습 도구를 켜지 않는다 (2026-08-25 판정 — `08 C-14`)

**영어 화면에는 `.quiz-*`·`.tts-*`·`.editor-*` 요소가 하나도 없다.** 확인 문제 스텝도, 재생 버튼도, 속도 칩도 없다.

- 근거: 영어는 콘텐츠가 없는 뼈대다. **미완성 학습 도구를 먼저 켜면 일본어 조판(`--font-jp`)·일본어(ja) 음성·
  빈 근거 상자를 영어 학습자에게 제품으로 보여주게 된다.** 도구는 콘텐츠가 찬 뒤에 켠다.
- 한 번 켰다가 되돌린 적이 있다(테스트가 초록이라 아무도 의심하지 않았다). **다시 붙이지 마라** —
  붙이려면 영어 콘텐츠가 먼저 차야 하고, 그때 일본어와 **같은 틀로 함께** 얹는다.
- 파생 규칙: 영어 회화 스텝의 캡션 줄은 `.step-caption` 단독이다(`.row-caption`이 아니다 — 얹을 컨트롤이 없다).
- **진도는 학습 도구가 아니다.** "어디까지 봤나"의 기본 기록이므로 영어 유닛에서도 그대로 동작한다.

### 16-2. 레벨 표기 — 코드는 화면에 나오지 않는다

**`levelCode`는 필터 값(요청 파라미터)으로만 쓰고, 사람이 읽는 문구는 언제나 표시 맵을 거친다.**

| 과정 | 화면 문구 |
|---|---|
| 일본어 | `입문` `N5` `N4` `N3` `N2` `N1` |
| 영어 | `코스 1` … `코스 5` (그룹 라벨도 **"레벨"이 아니라 "코스"**) |

- `N5`가 화면에 보이는 건 코드라서가 아니라 **JLPT 공인 표기라 학습자가 이미 아는 말**이기 때문이다.
  `INTRO`·`E1` 같은 DB 값은 아무도 본 적이 없다 → 코스를 부르는 이름 그대로 쓴다("입문", "코스 1").
  자료실 필터는 **"어느 코스에서 배운 항목인가"** 를 고르는 장치이므로 코스 이름이 정확한 말이다.
- **맵은 코드 → 문구 단방향이다.** 문구에서 코드를 되만드는 역변환·문자열 가공 함수를 만들지 않는다.
- **맵에 없는 코드는 코드를 그대로 표시**한다. "알 수 없는 레벨" 같은 사과 문구를 만들지 않는다(§12).
- **적용처 네 곳을 한 군데도 빠뜨리지 않는다**: ① 필터 칩 ② 적용 칩 ③ 0건 안내의 조건 되읽기 ④ `.lv-badge`.
  넷이 어긋나면 "고른 것"과 "행에 붙은 것"이 다른 말이 되어 같은 조건으로 읽히지 않는다.
- **영어에는 `levelLabel`을 쓰지 않는다.** 코스 상세 h1·완주 안내·`WhereLearn`은 **코스명 단독**이고,
  일본어가 쓰는 `{title}({levelLabel})` 괄호를 붙이지 않는다. 코스 카드도 레벨 라벨 없이 `코스 {n}`이다.
- 칩 순서는 **학습 순서 고정**(입문 → N5 → … → N1 / 코스 1 → 코스 5). 정렬 셀렉트와 무관하다.
- **선택지에서 뺀 것과 거부하는 것은 다르다** — 한자 자료실에 `입문` 칩이 없는 것은 그 탭의 사실이고,
  **설명하지 않는다**(§12). 주소로 들어오면 §8의 적용 칩 규칙대로 표시해 해제하게 한다.
- 자료실 탭도 `.k-tabs` 기반이라 **4번째 탭이 붙어도 안 깨진다**(확장은 구조로 확보한다 — §12).

### 16-3. 영어 자료실은 3탭, 기본 탭은 **표현**

- 탭 = **표현 / 문법 / 어휘**. **한자 탭이 없고**, `/en/library`는 **표현 탭으로** 보낸다.
- **"한자"라는 낱말이 영어 화면에 한 번도 나오지 않는다** — 한자가 있던 자리는 전부 **"표현"**이다
  (유닛 스텝, 코스 상세 집계 줄, 유닛 행 메타, 자료실 탭).
- 페이지 아바타(`.k-avatar`) 글리프는 `abc`(일본어 `辞` 자리·크기 그대로).
- **정렬 셀렉트를 렌더하지 않는다** — 영어에는 가나순 같은 제2 정렬이 없다.
  선택지가 하나뿐인 셀렉트는 조작할 것이 없으므로 `result-bar`의 `· 학습 순서` 표기만 남긴다.
  (일본어 자료실의 정렬 셀렉트는 그대로다 — 두 과정의 화면이 갈리는 유일한 지점이라 회귀 시험 대상이다.)
- 품사 필터는 **그 과정의 품사만** 노출한다. 일본어 7종(い·な형용사 포함)과 영어 7종(전치사·접속사·표현 포함)을 섞지 않는다.
- 영어 보관함(★)은 아직 열지 않았다 — **열 때 유닛·자료실 여러 곳에 한 번에 붙인다**(한 곳씩 늘리면 규칙이 흩어진다).

### 16-4. 영어 표기 — 라틴 자형과 발음

- **영어 문장에 `--font-jp`를 씌우지 않는다.** 기존 표기 컴포넌트에 `latin`을 얹어 자형만 본문 폰트로 되돌린다(§6).
  영어 데이터는 `kana`가 null이라 **2줄 병기(원문 / 한국어 뜻)** 가 자동으로 된다.
- **판정 기준은 한 줄이다 — 영어 화면에는 `.jp` 클래스 요소가 하나도 없다.** 자리를 하나씩 세어 맞히는 방식은
  **새로 열리는 자리**를 놓친다(2026-09-21 결함 1: 복습 블록이 `unitNo % 5 == 0`에서만 떠서 영어 유닛 5가
  열리는 날까지 아무도 밟지 않았고, 칩이 `jp`로 하드코딩된 채 제품에 나갔다).
  `.jp`를 쓰는 자리는 **전부 `latin ? "latin" : "jp"` 분기**로 쓴다 — 고정값 `"jp"`를 마크업에 적지 않는다.
  CSS가 `--font-jp`를 직접 박은 요소(`.jp-sentence`·`.vocab-table`·`.speaker-badge`)는 영어에서 `latin`을 단다.
  고정 테스트: `frontend/src/pages/UnitStudyPage.latin.test.jsx`(영어 그물 + 일본어 대칭).
- **발음은 `ipa`와 한국어 근사 표기 둘 다**, 없으면 `─`(가나 규칙 그대로).
  어휘 표는 **3열을 유지**하고 읽기 열 자리의 한 셀에 **두 줄**로 넣는다 — **4열로 늘리지 않는다.**
  둘 다 없으면 줄째 생략, 전량 없으면 열째 생략(§8).
- **표현 카드 `.expr-card`는 세로 1열 스택**이다. 한자 타일처럼 격자로 깔지 않는다 —
  표현은 가로로 길고 예문이 딸려 있어 2열로 쪼개면 줄바꿈이 지저분해진다.
  구성: 표제 20px → 발음 한 줄(`{ipa} · {근사표기}`) → 뜻 → 용법(있을 때만) → 예문 박스(`--surface-alt`, 0개면 박스째 생략).
  **강조 면·hover 부상 금지**(6~10장 반복이다 — §7-6과 같은 이유).
- 표현 카드를 **한자 카드로 대신하지 않는다**(한자 카드는 글자 1자를 큰 배지로 세우는 구조라 배지 자리가 빈다).
  **문법 블록으로도 대신하지 않는다**(문법은 유닛당 2~3개에 설명이 길고, 표현은 6~10개라 훑는 목록이어야 한다).
  자료실 표현 상세는 문법 상세와 같은 골격에 **같은 `.expr-*`를 재사용**한다(같은 내용 = 같은 컴포넌트, §7-1).
- 영어 원문은 그대로 두되 **설명·라벨·안내는 전부 한국어**다(학습자 언어는 한국어다).
- **문장 안에 코스명·닉네임이 들어가는 자리는 조사 처리 함수를 거친다**("일상 말하기**은** 준비하고 있어요"가 나오면 안 된다).
- 막다른 화면을 만들지 않는다 — 준비중 카드·404의 "돌아갈 곳"은 **그 과정 안**이어야 한다.
  일본어 코스로 고정된 링크를 영어 화면에서 그대로 쓰면 과정을 배신한다. 같은 이유로 **GNB·와일드카드 404도 경로의 과정을 따른다.**

## 17. 계정 화면 규칙 (마이페이지 · 프로필 · 비밀번호 · 탈퇴)

> 계정 화면의 **동작·검증 규칙은 `설계/04 §4-1`(계약)** 이 원본이다. 여기 적는 것은 **보여주는 방식**뿐이다.
> 문구 목록(로그인 방식 라벨 등)은 **여기에도 04에도 두지 않는다** — 값의 단일 출처는 `hooks/useAccount.js`의 라벨 맵이다.
> 문구를 문서로 복사하면 코드와 문서가 조용히 갈린다(08 C-11).

### 17-1. 못 하는 일은 **회색 버튼이 아니라 미렌더**

소셜 계정에는 [비밀번호 변경]을 **아예 그리지 않는다.** 비활성 회색 버튼은 "언젠가 되는 것"으로 읽혀
사용자가 왜 안 되는지 찾게 만든다. 분기의 근거는 **`passwordChangeable` 플래그 하나**이고(04 §2-1),
화면이 `provider === "LOCAL"`을 직접 해석하지 않는다. 대신 **왜 없는지**를 한 줄 안내로 남긴다
("○○ 계정으로 로그인하고 있어요. 비밀번호는 ○○에서 관리해요").
같은 판단이 **0인 값**에도 적용된다 — 지울 것이 없으면 [학습 기록 초기화]를 그리지 않는다(08 C-12 ①).

### 17-2. 오류는 **원인이 있는 자리**에 붙인다

| 오류 | 표시 자리 |
|---|---|
| 특정 입력의 문제(닉네임 중복·비밀번호 불일치·현재 비밀번호 틀림) | **그 필드 아래** `.k-help--err` + `aria-describedby` + 입력에 `aria-invalid="true"` |
| 요청 전체 실패(네트워크·5xx) | 폼 상단 `.k-alert--err` 한 줄 |
| 서버 검증 목록(400 `errors[]`) | **메시지만** 나열한다 — 필드 변수명(`username:`)을 사용자에게 보여주지 않는다(2026-08-25 판정 B-L5) |

### 17-3. 되돌릴 수 없는 것은 **세 번 확인하고, 빨갛게 하지 않는다**

탈퇴는 ① 본인 확인 입력 ② "위 내용을 확인했어요" 체크 ③ 최종 모달 — 셋을 다 지나야 실행된다.
버튼은 구분선 아래 **danger-zone**에 떼어 놓되 화면을 빨갛게 물들이지 않는다. 겁주는 화면이 아니라 **되돌릴 수 없다는 사실**이 방어선이다.
확인 문구는 **지워질 것이 실제로 있을 때만** 수를 말한다 — "완료한 0개 유닛과 보관함 0개가 지워져요"는 판단에 도움이 되지 않는다(08 C-12 ①).

### 17-4. 로그인 유도는 **원래 자리로 돌아온다**

로그인 화면으로 보내는 모든 진입점은 복귀 주소를 함께 넘긴다(`state.from`). 끝나면 그 자리로 되돌린다 —
보관함에서 유도한 로그인이 홈에서 끝나면, 방금 담은 것을 사용자가 다시 찾아가야 한다.
SPA 안의 이동은 항상 라우터 링크다(`<a href>`는 화면을 통째로 새로 그린다).

## 18. 화면별 절을 두지 않는 이유

코스 상세·유닛 학습·정리/복습 같은 **화면 단위 절은 만들지 않는다.**
그 화면들이 쓰는 것은 §7(컴포넌트 재사용)에 있는 부품이고, 화면별 절을 만들면 같은 규칙이 두 곳에 생겨 갈린다(08 C-11).
화면 고유의 판단이 필요했던 것들은 이미 **결정으로** 남아 있다 — 0인 집계 숨김(08 C-12 ①),
영어 유닛의 학습 도구 미노출(C-14, §16-1), 학습 도구의 동작(`설계/09`).

**새 화면을 만들 때 순서**: **킷 `클래스-목록.md`에서 `.k-*`를 찾는다** → 없으면 §7의 도메인 부품을 찾는다 →
없으면 §2~§6의 토큰으로 조립한다 → 그래도 새 언어가 필요하면
**그때 결정으로 남긴다**(08). 화면마다 절을 늘리는 것은 마지막 수단이다.

## 19. 이 제품이 추구하는 화면 — 사용자 취향 기준

> 2026-09-09~10 코스 목록(`/courses`)을 사용자와 한 줄씩 맞춰 가며 **드러난 취향**을 규칙으로 옮긴 것이다.
> 그 화면의 이력이 아니라 **다른 화면에도 그대로 적용하는 기준**이다.
> §1~§18이 "이 킷을 어떻게 쓰나"라면, 여기는 **"이 사람이 무엇을 좋아하나"**다.
> 새 화면을 다듬을 때 §19-8 체크리스트부터 훑는다.

### 19-1. 한 줄로 — 차분하고 균일하게, 대신 위계는 분명하게

여섯 번의 요구를 관통하는 기준이다:

- **화려한 것보다 정돈된 것.** 강조는 아껴서 한 곳에만.
- **한 장만 튀는 것을 싫어한다.** 같은 종류는 같게 보여야 한다.
- **대신 무엇이 제목이고 무엇이 내용인지는 한눈에** 갈려야 한다.
- **군더더기는 뺀다.** 같은 말을 두 번 하지 않는다.
- **줄은 칼같이 맞는다.** 어긋난 줄을 "지저분하다"고 느낀다.

### 19-2. 읽히는 것이 먼저다

> *"컨텐츠내용도 잘 읽히면서 전체적으로 눈에 확 들어오도록"*

**읽으라고 있는 글이 화면에서 가장 잘 읽혀야 한다.** 당연해 보이지만 기본값은 자주 반대다 —
코스 카드는 제목이 본문과 같은 크기(15px)였고, 정작 내용이 13.5px에 흐린 회색이었다.

**세 단으로 벌린다. 굵기는 1단에만 쓴다.**

| 단 | 무엇 | 크기 | 굵기 | 색 |
|---|---|---|---|---|
| 1 | 제목 | `--t-xl` | `--w-heavy` | `--text` |
| 2 | **내용** — 읽어야 하는 것 | `--t-md` | 기본 | `--text` |
| 3 | 라벨·부가 정보 | `--t-sm`~`--t-md` | `--w-bold` | `--muted` |

- **2단과 3단은 크기를 같게 둬도 된다.** 라벨을 작게까지 줄이면 한 줄 안에서 두 번 꺾여 산만하다 — 굵기와 색으로만 가른다.
- **보조 텍스트의 최소선은 `--muted`다.** `--muted2`는 회색 면 위에서 대비가 약 2:1까지 떨어져 **배경과 같은 색으로 보인다.**

### 19-3. 면은 색으로 구별한다 — 선만으로는 부족하다

> *"바깥 전체 배경색이랑 이거의 배경색이 같음 둘다 흰색"* / *"단순히 파란색 테두리가 아니라 이 카드의 배경색이 있었으면"*

킷 기본값은 페이지와 카드가 **둘 다 `#ffffff`**라 1px 선 하나로 버틴다. 이 취향에는 부족하다.

| 면 | 토큰 | 쓰임 |
|---|---|---|
| 페이지 | `--bg` | 바탕은 흰색 그대로 |
| **카드** | `--surface-alt` | 내용이 얹히는 판 — **회색** |
| 카드 속 인셋 | `--surface` | 진도 막대 트랙, 중립 배지 |
| 비활성 | `--bg-sunken` | 들어갈 수 없는 것은 **눌러** 둔다 |

**강조색 면(`--point-soft`)도 대 봤지만 회색을 골랐다.** 연보라는 안내 띠가 이미 쓰고 있어
카드까지 같으면 역할이 섞인다 — **면 색은 역할당 하나씩** 배정한다.

### 19-4. 강조는 한 곳에만, 나머지는 같게

> *"입문만 다른색으로하는거 말고 다 똑같은색으로 하자"* / *"입문 카드 원판 주황색 없애는걸로"*

시작점 카드에 면 색·테두리·주황 번호판까지 세 겹으로 강조를 줬더니 **그 한 장만 튀어** 오히려 거슬렸다.
지금 시작점을 알리는 것은 **배지 문구 하나뿐**이다.

- 같은 종류(카드·행·칩)는 **면과 크기를 같게** 둔다.
- 강조가 필요하면 **한 가지 수단만** 쓴다(색 *또는* 테두리 *또는* 배지).
- ⚠️ **강조에 hover와 같은 값을 쓰지 않는다.** 시작점 카드에 hover 그림자(`--sh-2`)를 줬다가
  **그 카드만 hover 반응이 사라질** 뻔했다 — 강조는 색으로, 눌림 신호는 그림자로 나눈다.

### 19-5. 줄이 맞아야 깔끔하다

> *"높이가 안 맞아서 지저분"* / *"메뉴목록이 본문이랑 왼쪽 위치가 안맞음"*

"지저분하다"는 대개 글자가 아니라 **줄이 어긋난 것**이다. 네 곳을 본다:

1. **가변 길이는 한 블록이 흡수한다** — 카드마다 글이 1~3줄로 달라지면 그 아래 요소가 제각각 높이에 놓인다.
   글을 자르지 말고 가운데 블록에 **`flex: 1`**을 줘서 아래 요소가 **바닥에서 같은 거리**에 오게 한다.
2. **글리프와 글의 높이를 맞춘다** — 40px 아이콘 옆 83px 글 블록은 아이콘이 떠 보인다. 크기를 가깝게 맞추고 세로 가운데로.
3. **죽은 여백을 찾는다** — 킷 `.k-page-desc`의 아래 여백은 헤더 안에서 **블록 높이만 부풀린다**(헤더가 이미 그 여백을 갖는다).
4. **헤더와 본문의 왼쪽 선을 맞춘다** — 헤더는 화면 끝, 본문은 `--content-max` 가운데 기준이라 넓은 화면일수록 어긋난다.
   띠(배경)는 화면 끝까지 두고 **안쪽 여백만** 본문 선에 맞춘다. `100vw`가 아니라 **`100%`** — `vw`는 스크롤바 폭을 포함한다.

**라벨과 내용은 줄을 나눈다.** 붙여 두면 긴 문장이 라벨 뒤에서 접혀 카드마다 시작점이 흐트러진다:

```
대상
- 일본어를 처음 접하는 분
```

글머리표는 **CSS `::before`로** 넣는다 — 실제 문자로 쓰면 낭독기가 "대시"라고 읽는다.

### 19-6. 덜어내는 것도 디자인이다

> *"코스 0 · 문자 이거 없애줘"* / *"숫자없이 입문 왕초보 … 만 있으면 될듯"*

같은 정보를 두 번 말하지 않는다. 코스 이름이 이미 순서를 말하고 있으면 **번호와 레벨 줄은 군더더기다.**

⚠️ **덜어낼 때 접근성을 함께 본다.** 눈에서 지우는 것과 화면에서 없애는 것은 다르다:

| 대상 | 처리 | 이유 |
|---|---|---|
| `aria-hidden` 이 이미 붙은 장식 | `display: none` | 낭독기가 **원래 안 읽었다** — 잃는 것이 없다 |
| 화면에만 안 보이면 되는 정보 | **시각적 숨김**(`.k-sr` 방식) | 지우면 낭독기 사용자가 그 정보를 통째로 잃는다 |

### 19-7. ⚠️ 면을 칠하면 그 위에 얹힌 것을 전부 다시 본다

**가장 값비싼 교훈이다.** 카드 배경을 흰색 → 회색으로 바꾸는 **한 줄** 때문에 같은 색을 쓰던 것들이 한꺼번에 사라질 뻔했다:

| 요소 | 그대로 뒀다면 |
|---|---|
| 진도 막대 트랙 | 빈 구간이 묻혀 **채운 부분만 떠 보임** |
| 중립 배지 | **통째로 사라짐** |
| 비활성 카드 | 일반 카드와 **구별 불가** |
| 카드 속 안내 알약 | **통째로 사라짐** |
| 흐린 회색 글자 | 대비 **약 2:1** — 배경과 같은 색 |

> **사라지는 것은 에러를 내지 않는다.** 테스트도 콘솔도 조용하다.
> 면을 바꾼 뒤 **그 면 위의 모든 색을 눈으로 훑는 것**이 절차의 일부다.

**지금 화면에 안 나오는 조합도 미리 막는다** — 안내 알약은 그것을 가진 코스가 한 장뿐이라 우연히 안 겹쳤을 뿐이다.

### 19-7-1. 면 계층은 절차가 아니라 **구조**로 지킨다 — `--surface-inset`

§19-7을 "칠할 때마다 눈으로 훑는다"로 두면 언젠가 빠뜨린다. 그래서 **상속으로 대신 계산한다.**

```
:root            --surface-inset: var(--surface-alt)   /* 흰 페이지 위 → 회색 인셋 */
카드(회색 면)    --surface-inset: var(--surface)       /* 회색 카드 위 → 흰 인셋 */
```

진도 막대 트랙·배지·알약·스켈레톤·아바타는 **이 토큰 하나만 본다.**
새 카드를 만들 때는 공용 목록에 **이름만 더하면** 그 안쪽 색이 저절로 맞는다 — 각각을 다시 칠하지 않는다.

### 19-7-2. ⚠️ `:not()`은 인자의 특이도를 얹는다 — 공용 기본값은 `:where()`로

공용 규칙을 `.k-alert:not([class*="k-alert--"])`로 썼더니 특이도가 **(0,2,0)**이 되어
화면별 규칙 `.courses-start-notice`**(0,1,0)**를 이겼다 — **연보라 안내 띠가 회색으로 되돌아갔다.**

`:where()`는 거르는 일만 하고 **특이도가 0**이다:

```css
/* ❌ 공용이 화면별을 이긴다 */
.k-alert:not([class*="k-alert--"]) { ... }
/* ✅ 공용은 기본값 자리에, 화면별이 그 위에 */
.k-alert:where(:not([class*="k-alert--"])) { ... }
```

**공용 층의 기본값은 특이도를 0에 둔다.** 이것도 §19-7과 같은 계열의 "조용한 실종"이다 —
에러 없이 화면별 의도만 사라진다.

### 19-7-3. 크기에도 최소선이 있다

- **라벨 최소선은 `--t-sm`.** 그보다 작으면 회색 면 위에서 읽히지 않는다.
  단 **글자가 아니라 표시**인 것(번호 원판·화자 배지)과 좁은 화면 밀도 보정(§10)은 예외다.
- **목록 행 제목은 `--t-lg`** — 카드 제목(`--t-xl`)과 다르다.
  8~20행이 이어지는 목록에서 카드 제목 급을 쓰면 행 높이가 두 배가 되어 **지도로서 못 읽는다.**

### 19-8. 새 화면에 적용할 때 — 체크리스트

- [ ] **읽어야 할 글이 가장 크고 진한가?** 제목 > 내용 > 라벨 순으로 벌어졌나(§19-2)
- [ ] 굵기를 **제목에만** 썼나
- [ ] 보조 텍스트가 `--muted2`가 아니라 **`--muted`** 인가
- [ ] 카드·패널이 **페이지 배경과 다른 면**인가(§19-3)
- [ ] 면을 칠했다면 **그 위 요소의 색을 전부 확인**했나(§19-7)
- [ ] 같은 종류 중 **한 장만 튀지** 않는가(§19-4)
- [ ] 강조 수단이 **하나뿐**인가. hover 값과 겹치지 않는가
- [ ] 길이가 다른 글 아래 요소가 **같은 높이**에 놓이는가(§19-5)
- [ ] 아이콘·글리프가 옆 글과 **높이가 맞는가**
- [ ] 헤더·본문의 **왼쪽 선이 맞는가**
- [ ] 같은 정보를 **두 번 말하고** 있지 않은가(§19-6)
- [ ] 무언가를 감췄다면 **낭독기는 여전히 읽는가**
- [ ] 카드 안쪽 요소를 **직접 칠하지 않고** `--surface-inset` 을 쓰는가(§19-7-1)
- [ ] 공용 기본값의 특이도가 **0**인가 — `:not()` 대신 `:where()`(§19-7-2)
- [ ] 라벨이 `--t-sm` 이상, 목록 행 제목이 `--t-lg` 인가(§19-7-3)
- [ ] 새로 쓴 토큰이 `tokens.css`에 **실재하는가** — 없는 이름을 써도 CSS는 알려주지 않는다
- [ ] 이유가 사라진 규칙을 **남겨 두지** 않았나

### 19-9. 요구는 해법 형태로 온다 — 원인을 먼저 잰다

지적 9건 중 **셋은 첫 진단이 틀렸다.** 말한 대로 실행했다면 더 나빠졌다:

| 말한 것 | 그대로 했다면 | 실제 원인 |
|---|---|---|
| "글씨체 전부 굵은고딕으로" | 전부 굵게 → **위계 소멸**(실제로 겪었다) | 크기·대비가 뒤집힘 |
| "높낮이가 안 맞음" | 글자 크기 조정 | 가변 영역 미확보 |
| "배경이 같은 흰색" | 테두리만 진하게 | **면 색**을 달라는 것 |

**증상을 그대로 실행하기 전에 원인을 재 본다.** 특히 해법 형태로 오는 요청일수록,
그 해법이 진짜 원인을 겨냥하는지 먼저 확인한다.
