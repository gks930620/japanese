# 07. 운영 · 배포

> **이 문서는 무엇인가**
> 이 제품을 실제로 서버에 올릴 때 필요한 것 전부다 — **배포 전 반드시 해야 하는 일**, 환경변수 목록, OAuth 설정,
> 보안 화이트리스트 관리 규칙. 배포를 맡은 사람은 물론이고, 새 API·새 화면을 만드는 사람도 §5를 읽어야 한다.

기준일: 2026-08-10

## 0. 한 줄 원칙

> **같은 코드가 코드 변경 없이 로컬에서도, 운영에서도 동작한다.**
> "배포한다고 코드를 고치지 않는다." 환경 차이는 **Spring 프로파일 + 환경변수로만** 흡수한다.

이 원칙이 금지하는 것:

- 코드 안의 `if (로컬) ... else (운영) ...` 환경 분기
- 운영 도메인·시크릿을 소스에 하드코딩
- "배포용 브랜치"에서만 설정을 바꿔치기

배포하면서 아래를 소스에서 고치고 있다면 원칙 위반이다:
DB 접속정보 → `SPRING_DATASOURCE_*` / 앱 공개 URL·OAuth redirect·WS 출처 → `APP_BASE_URL` /
시크릿 → 각 환경변수 / 포트 → `${PORT}` / 쿠키 secure·로깅 레벨·SQL 초기화 → `application-prod.yml`.

## 1. ⚠️ 배포 전 필수 — 운영에는 학습 콘텐츠가 자동으로 들어가지 않는다

**가장 중요하고 가장 잊기 쉬운 항목이다.**

운영 프로파일은 `spring.sql.init.mode: never`다.
코스·유닛·문법·한자·어휘 시드 SQL이 **운영 MySQL에는 실행되지 않는다.**

> **적재하지 않고 배포하면 사이트는 뜨지만 코스 목록이 텅 빈다.**

### 적재해야 할 파일 (순서대로)

```
data-courses.sql
data-course-content.sql          data-course-units.sql          (N5)
data-course-n4-content.sql       data-course-n4-units.sql
data-course-n3-content.sql       data-course-n3-units.sql
data-course-n2-content.sql       data-course-n2-units.sql
data-course-intro-content.sql    data-course-intro-units.sql    (입문 — 코스 0)
data-course-n1-content.sql       data-course-n1-units.sql       (N1)
data-course-en-content.sql       data-course-en-units.sql       (영어 — 코스 5행 + E1)
data-course-en2-content.sql      data-course-en2-units.sql      (영어 코스 2 — E2)
```

`*-content.sql`이 반드시 같은 코스의 `*-units.sql`보다 먼저다(매핑이 콘텐츠를 참조한다).

> ⚠️ **위 목록에 `data-users.sql`·`data-user-roles.sql`·`data-community.sql`·`data-comment.sql`·`data-files.sql`은 없다 — 운영에 적재하지 않는다.**
> `data-user-roles.sql`은 `data-users.sql`의 짝이다(테스트 계정의 권한 행) — **둘은 함께 넣거나 함께 뺀다.** 한쪽만 넣으면 권한 없는 계정이 남는다.
> 커뮤니티 시드는 보일러플레이트 유래의 **인형뽑기 게시글**이다(2026-09-03 사용자관점 점검 D-8). 로컬 개발용이며 학습 사이트와 무관하다.
> 운영 적재는 사람이 하므로 "안 넣는다"가 기억에 의존한다 — 배포 체크리스트에 **"커뮤니티·사용자 시드 미적재 확인"** 한 줄을 둔다.

> ⚠️ **이 목록의 단일 기준은 `src/main/resources/application.yml`의 `sql.init.data-locations`다.**
> 코스가 추가될 때마다 여기도 함께 갱신한다 — 이 문서가 낡으면 운영에 콘텐츠가 통째로 빠진다
> (실제로 4단계에서 입문·N1·영어 6개 파일이 누락된 채 남아 있었다).

### 적재 방법

첫 배포 시 스키마가 만들어진 뒤(`ddl-auto: update`), 위 파일들을 운영 MySQL에 1회 수동 실행한다.
`data-h2-reset-identity.sql`은 **실행하지 않는다** — H2 전용이다.

**번들 한 파일로 묶어서 실행한다(권장).** 17개(2026-09-22 E2 파일 2개 추가)를 손으로 하나씩 실행하는 대신 `gradlew prodSeedBundle` 을 실행하면
`build/prod-seed.sql` 하나가 만들어진다(UTF-8). 위 순서 그대로 이어 붙이고(`*-content.sql` → 같은 코스의 `*-units.sql`),
운영에 넣으면 안 되는 6개(`data-users.sql`·`data-user-roles.sql`·`data-community.sql`·`data-comment.sql`·`data-files.sql`·`data-h2-reset-identity.sql`)는
빼며, 파일마다 `-- ===== <파일명> =====` 경계 주석을 남겨 어디서 온 SQL인지 보이게 한다. 목록에 적힌 시드가 하나라도 없으면
태스크가 **실패**하므로 "조용히 빠진 코스"가 생기지 않는다. 적재는
`mysql -h <HOST> -P <PORT> -u <USER> -p --default-character-set=utf8mb4 <DB> < build/prod-seed.sql` 한 번이면 된다.
**이 번들의 목록은 `src/main/resources/application.yml` 의 `sql.init.data-locations` 를 그때그때 읽어서 만든다 —
코스가 늘어도 태스크에 따로 고칠 곳이 없다.** (`build/` 는 `.gitignore` 대상이라 생성물은 커밋되지 않는다. 결과물을 직접
고치지 말고 시드 SQL을 고친 뒤 다시 생성한다. 아래·위의 수동 목록은 태스크를 못 쓰는 상황의 대비책 겸, 사람이 무엇이
들어가는지 알기 위해 그대로 둔다.)

#### ⚠️ 이미 적재된 운영 DB에 시드 수정분을 반영할 때 — `UPDATE` 줄은 번들로 들어가지 않는다

시드에 **기존 행을 고치는 `UPDATE`** 가 추가되면 첫 배포용 번들(`prodSeedBundle`)로는 반영되지 않는다.
운영에는 그 행이 이미 있어 번들을 다시 돌릴 수 없기 때문이다(INSERT 중복). **해당 줄만 따로 실행한다.**

**2026-09-21 — `course.planned_unit_count`** (`설계/04 §2-3-A` · `08 C-29`)

```sql
UPDATE course SET planned_unit_count = 15 WHERE id = 101;   -- E1 계획 유닛 수
```

- 컬럼은 `ddl-auto: update`가 배포 시 자동 생성한다. **값은 자동으로 들어가지 않는다.**
- **빠뜨려도 아무것도 실패하지 않는다** — `NULL`은 "계획값 없음"이라는 **적법한 값**이라 API는 200을 돌려준다.
  대신 E1의 열린 마지막 유닛에서 화면이 **"🎉 끝까지 봤어요"라는 거짓 안내**를 낸다(2026-09-21 검수 결함 2의 재발).
  로그에도 남지 않으므로 **사람이 체크리스트로 보증해야 한다**(§3-2와 같은 종류 — 조용히 틀리는 값이다).
- 적재 후 확인: `SELECT id, planned_unit_count FROM course WHERE id = 101;` → **15**.
  (일본어 코스는 전부 `NULL`이 정상이다 — 값을 채우지 않는다.)
- E1이 15유닛을 다 채우면 `totalUnits >= 15`가 되어 **사람이 플래그를 내리지 않아도** 자동으로 완주가 된다.
  그때 남는 사람 일은 `course.notice`를 `NULL`로 지우는 것뿐이다(`06 §11-12` R4 · 기획 AC-16). **↓ 그 일이 2026-09-22에 왔다.**

**2026-09-22 — `course.notice` 삭제** (E1이 15유닛을 채웠다)

```sql
UPDATE course SET notice = NULL WHERE id = 101;   -- "앞 유닛부터 순서대로 채우는 중이에요" 삭제
```

- E1은 **완성**됐다. 그 안내는 이제 **거짓**이다.
- `planned_unit_count = 15`는 **지우지 않는다** — `totalUnits(15) >= planned(15)`가 되어 화면이 저절로 완주로 바뀐다.
  개수로 둔 덕에 **플래그를 내리는 사람 일이 아예 없다.** 사람이 할 일은 이 `notice` 한 줄뿐이다.
- ⚠️ **빠뜨리면 운영에서만 거짓 안내가 뜬다.** 로컬·테스트는 시드를 새로 적재해 `NULL`이지만, 운영은
  `sql.init.mode: never`라 **INSERT가 다시 돌지 않는다.** 코드도 테스트도 전부 초록인 채로 **운영 화면에만**
  "채우는 중이에요"가 남는다 — `planned_unit_count`와 정확히 같은 종류의 조용한 실패다.
- 적재 후 확인: `SELECT id, notice FROM course WHERE id = 101;` → **`NULL`**.

**2026-09-22 — 코스 102(E2) 개통** (유닛 1~5 부분 공개 · `설계/06 §11-12 ③` · `04 §2-3-A`)

```sql
UPDATE course
   SET status = 'AVAILABLE',
       planned_unit_count = 20,
       notice = '앞 유닛부터 순서대로 채우는 중이에요 — 열려 있는 유닛까지는 지금 그대로 학습하면 됩니다',
       description = '학교에서 시제를 표로 외웠는데도 말할 때 헷갈리는 이유부터 다시 답합니다. 지난 일과 지금 하는 중인 일, 앞으로의 일과 지금까지의 일을 세 가지 질문으로 가려내, 시제와 의문·부정을 한 문장 안에서 다룰 수 있게 되는 것이 이 코스의 도착점입니다.'
 WHERE id = 102;
```

- 운영 DB에는 course 102 행이 **이미 `PREPARING`으로 들어가 있다** — `data-course-en2-*.sql`을 적재해도
  **코스가 열리지 않는다.** 유닛·콘텐츠만 들어가고 코스는 준비중인 채다(상세는 빈 목록, 유닛은 404 `COURSE_PREPARING`).
- ⚠️ **빠뜨리면 로컬·테스트는 전부 초록인데 운영에서만 E2가 없다.** `planned_unit_count`·`notice`와 같은 종류의
  조용한 실패이고, 여기서는 **세 개가 한 덩어리**다(§06 §11-12 ③ R3 — 셋 중 하나만 들어가도 화면이 거짓말을 한다:
  status만 → 유닛 5에서 "🎉 끝까지 봤어요" · notice만 → 준비중인데 "채우는 중" 안내).
- 적재 후 확인: `SELECT id, status, planned_unit_count, notice IS NULL FROM course WHERE id = 102;`
  → `AVAILABLE / 20 / 0`.
- **E2가 20유닛을 채우는 날** 할 일은 E1과 같다 — `notice`를 `NULL`로 지우는 `UPDATE` 한 줄(§06 §11-12 ③ R4).
  `planned_unit_count`는 그대로 둔다(개수 비교로 완주가 자동 전환된다).

> **이 세 항목의 공통점**: 전부 *"배포하면 자동으로 되는 것"* 처럼 생겼는데 아니다.
> 컬럼은 자동으로 생기고 시드 파일에도 줄이 들어 있지만, **이미 적재된 운영 DB에는 그 줄이 닿지 않는다.**
> 새 `UPDATE` 줄을 시드에 넣을 때마다 **이 절에 한 항목을 추가**한다 — 그러지 않으면 다음 사람이 모른다.

콘텐츠 시드는 테스트 픽스처가 아니라 **실참조 데이터**다. 시드를 고칠 때마다 운영에도 반영해야 한다.
콘텐츠 편집 API는 **로컬 전용**이고 운영에서는 빈이 등록조차 되지 않으므로(3단계 계약 §5-1),
운영 콘텐츠를 바꾸는 경로는 이 수동 적재가 유일하다.

> 이 절차를 자동화(마이그레이션 도구 도입)할지는 아직 정하지 않았다. 지금은 수동이고, 그래서 이 문서에 크게 적어 둔다.

## 1-1. ⚠️ 배포 전 필수 — **H2 콘솔이 운영에서 닫혔는지** (감사 2026-08-25 H1)

> **감사 당시(2026-08-25) 상태 — 지금은 고쳐졌다(아래 게이트 1·2·3이 그 증거).**
> 그때는 `spring.h2.console.enabled: true`가 기본 `application.yml`에만 있고 `application-prod.yml`이 덮지 않아
> 이 상태로 배포하면 운영에도 H2 콘솔이 떴고, `SecurityConfig`가 `/h2-console/**`를 무조건 permitAll해 인증도 없었다.
> 지금은 `application-prod.yml:52-55`가 `false`를 명시하고, `SecurityConfig`는 콘솔이 켜진 환경에서만 그 규칙을 등록한다.
> (2026-09-03 정정 — 이 문단이 현재형으로 남아 있어 "열린 구멍"으로 읽혔다.)

⚠️ 남아 있는 구조적 약점: 기본 `application.yml`이 **여전히 콘솔·편집 모드를 켠 채**이고 방어는 전부 `prod` 프로파일에 매달려 있다
(`RailwayDeploymentValidator`도 `@Profile("prod")`). prod가 아닌 새 실행 경로가 생기면 열린 채로 뜬다 — **기본값의 방향**은 사람 결정 대기(`진행사항/미결_사람결정.md` 2026-09-03 항목).

> H2 콘솔은 접속자가 **임의 JDBC URL을 입력**할 수 있는 화면이다. 단순 정보 노출이 아니라 원격 코드 실행으로 이어지는 알려진 경로다.

**배포 게이트 — 셋 다 충족해야 배포한다.**

| # | 조건 | 확인 방법 |
|---:|---|---|
| 1 | `application-prod.yml`에 `spring.h2.console.enabled: false`가 **명시**돼 있다 | 파일 확인 |
| 2 | prod인데 콘솔이 켜져 있으면 **기동을 거부**한다(`RailwayDeploymentValidator`) | `RailwayDeploymentValidatorTest` 통과 |
| 3 | 콘솔이 꺼진 환경에는 `/h2-console` permitAll·frameOptions 완화가 **남아 있지 않다** | `H2ConsoleSecurityContractIntegrationTest` 통과 |

**설정 한 줄로 끄는 것(1)은 방어가 아니다** — 다음에 누가 다시 켜면 조용히 열린다.
편집 모드(`app.editor.enabled`)와 **같은 자세**로 다룬다: 꺼진 환경에는 규칙 자체가 존재하지 않고(3), 켜진 채로는 뜨지 않는다(2).
로컬은 그대로 `/h2-console`을 쓴다 — 닫는 것은 운영뿐이고, 그 사실을 `H2ConsoleEnabledLocalContractIntegrationTest`가 고정한다.

## 2. 배포 구조

```
Dockerfile (멀티스테이지)
 ├ Stage 1  gradle:8-jdk17 + Node 20
 │          gradle bootJar -x test
 │          → frontendInstall(npm ci) → frontendBuild(vite) → copyFrontendBuild → bootJar
 └ Stage 2  eclipse-temurin:17-jre-alpine
            ENTRYPOINT java -jar -Dspring.profiles.active=prod app.jar
            HEALTHCHECK curl /actuator/health
```

- **`prod` 프로파일은 Dockerfile ENTRYPOINT가 고정한다** → `SPRING_PROFILES_ACTIVE`를 따로 등록할 필요가 없다.
- 프론트 번들은 `bootJar`가 `copyFrontendBuild`에 의존하므로 **배포 산출물에는 항상 최신 번들이 들어간다.**
- 타임존 `Asia/Seoul`.

### 3-2. 사실상 필수 — 기본값이 있어서 **조용히 깨진다** ⚠️

| 변수 | 반드시 설정할 값 | 미설정 시 |
|---|---|---|
| `APP_BASE_URL` | `https://<본인 도메인>` | OAuth redirect가 `localhost`로 나가 **카카오/구글 로그인 전면 실패**, WebSocket 허용 출처가 placeholder라 **핸드셰이크 거부** |

`APP_BASE_URL`은 `application-prod.yml`에 기본값이 있어 **없어도 기동은 된다.**
fail-fast 검증이 잡지 못하는 유일한 항목이므로 **사람이 체크리스트로 보증해야 한다.**

### 3-3. 설정 불필요

| 변수 | 상태 |
|---|---|
| `PORT` | Railway가 자동 주입 → 앱이 `${PORT:8080}`으로 수신 |
| `BUCKET_REGION` | 기본값 `us-east-1`. 대부분 그대로 |
| `ORPHAN_GRACE_HOURS` | 기본 24시간 |

## 5. 보안 — 화이트리스트 관리 (새 기능을 만들 때마다 확인)

### 5-1. 기본이 차단이다

`SecurityConfig`의 마지막 규칙은 `.anyRequest().authenticated()`다.
"로그인이 필요한 곳을 하나씩 막는" 방식이 아니라 **"공개할 곳만 명시하고 나머지는 전부 인증 필요"**로 뒤집혀 있다.

- 장점: 새 엔드포인트를 깜빡해도 **자동으로 보호**된다.
- 비용: **공개해야 할 경로를 빠뜨리면 즉시 깨진다**(화면이 안 뜨거나 로그인이 안 된다).

### 5-2. 세 곳을 항상 함께 관리한다 ⚠️

| 파일 | 역할 |
|---|---|
| `jwt/config/SecurityConfig.java` | 경로 권한(permitAll 목록) |
| `HomeController.java` | SPA forward 대상 경로 |
| `frontend/src/App.jsx` | React 라우트 |

**새 화면을 추가할 때 체크리스트**

- [ ] 새 공개 API를 만들었나 → SecurityConfig permitAll에 **메서드 + 경로**를 명시 추가
- [ ] 새 SPA 페이지 라우트(비로그인 접근)를 추가했나 → permitAll **+ HomeController forward**에도 추가
- [ ] 새 정적 경로(폰트·이미지 디렉터리)를 쓰나 → permitAll에 추가
- [ ] 로그아웃 상태에서 화면 진입 시 정적 자산이 200인지 확인(로그아웃 후 새로고침)
- [ ] 카카오/구글 로그인이 실제로 되는지 — `/login/oauth2/**` 콜백이 막히면 실패한다

반대로 **인증이 필요한 API는 아무것도 하지 않아도 자동 보호**된다.

### 5-3. 인증(Authentication)과 인가(Authorization)를 구분한다

> **SecurityConfig는 "로그인했는가"만 판정한다.**
> **"로그인한 그 사람이 이 리소스를 건드릴 권한이 있는가"는 SecurityConfig가 막아주지 않는다.**
> 서비스 계층에서 소유자 검증을 하지 않으면 **IDOR 취약점**이 된다.

- 수정·삭제 API는 `authenticated()`만으로 부족하다. 서비스에서 대상 리소스를 조회한 뒤
  **작성자 == 요청자**를 확인하고 불일치면 `AccessDeniedException`(403).
  참고 구현: `CommunityEntity.isWrittenBy(username)`.
- **파일 API도 마찬가지다.** 파일은 FK 없이 `refId + refType`으로 느슨하게 연결되므로,
  업로드·삭제 시 대상 리소스의 소유권을 되짚어 검증한다(`FileService.verifyOwnership()`).
  `refId=0`(임시 업로드)은 미연결로 간주해 통과시킨다.
- **앱 네이티브 OAuth(`POST /api/oauth2/providers/{provider}/tokens`)는 permitAll이므로
  클라이언트가 보낸 사용자 id를 절대 신뢰하지 않는다.** 앱은 provider access token을 보내고,
  서버가 provider API로 검증해 식별자를 **직접** 획득한 뒤에만 JWT를 발급한다.
  검증 없이 id를 신뢰하면 누구나 임의 계정으로 로그인할 수 있다(인증 우회).
  참고 구현: `ProviderTokenVerifier` / `AppOAuth2Service.login`.

**인가 체크리스트**

- [ ] 특정 사용자 소유 리소스를 수정·삭제하나 → 서비스에서 소유권 검증(403)
- [ ] 리소스가 id로 직접 지정되나(`/{id}`, `refId`) → 남의 id를 넣어도 막히는지 확인(IDOR)
- [ ] 통합 테스트에 **"다른 사용자가 남의 리소스에 접근 → 403"** 음성 케이스를 넣었나
- [ ] 인증 전 호출되는 엔드포인트가 외부에서 받은 신원 정보를 신뢰하나 → 서버 검증으로 대체

### 5-4. 학습 API의 네임스페이스 규칙 (영구)

`/api/courses/**`와 `/api/library/**`는 **GET 전용·전부 공개**로 와일드카드가 열려 있다.
따라서:

> **인증이 필요한 학습 기능은 `/api/courses/**` 아래에 두지 않는다.**
> 진도 저장 등은 `/api/progress/**`, `/api/me/**` 같은 **별도 네임스페이스**에 만들고 그 경로를 `authenticated()`로 명시한다.

**콘텐츠 조회(공개)와 사용자 상태(인증)를 경로로 분리**하는 것이 화이트리스트 방식과 함께 쓰는 정석이다.
와일드카드를 쓴 이유는, 좁은 패턴(`/api/courses/*/units/*`)이면
미매핑 하위 경로가 시큐리티에서 401로 끊겨 **계약이 요구하는 404에 도달하지 못하기 때문**이다.
401은 "로그인하면 되나?"로 읽히지만 실제로는 존재하지 않는 주소다.

## 6. 파일 저장 — 버킷이 표준

- 업로드 파일은 **S3 호환 버킷(Railway Storage Buckets)** 에 저장한다. **Volume을 쓰지 않는다.**
  컨테이너 파일시스템이 ephemeral이어도 재배포에 파일이 보존된다.
- **로컬은 `BUCKET_ENDPOINT`가 비어 있으면 자동으로 로컬 디스크(`LocalFileStorage`)로 폴백**한다.
  같은 코드가 환경만으로 갈리는 예다.
- 버킷은 private이므로 **백엔드 프록시 `GET /uploads/{저장파일명}`이 바이트를 스트리밍**한다
  (같은 오리진, presigned 만료 없음, 프론트 계약 불변).
- prod에서 `BUCKET_*`이 없으면 `RailwayDeploymentValidator`(`@Profile("prod")`)가 **기동을 막는다.**
- 고아 파일(`refId=0`) 정리 배치가 유예시간(기본 24h) 경과 후 메타 + 실제 바이트를 삭제한다.

## 9. CI — GitHub Actions (`.github/workflows/ci.yml`)

배포 전 조건인 "세 스택 테스트 통과"의 **자동 확인 장치**다. 테스트가 646건(백엔드 230 · 프론트 416)이라
손으로 돌리면 빠뜨린다. **이 워크플로가 초록이 아니면 배포하지 않는다.**

### 9-1. 언제 도나

| 트리거 | 동작 |
|---|---|
| **모든 브랜치 push** | 전체 실행 |
| **master 대상 PR** | 전체 실행 |
| Actions 탭 → Run workflow | 수동 실행 |

같은 브랜치에 연달아 푸시하면 이전 실행은 자동 취소된다(러너 시간 절약).

### 9-2. 무엇이 도나 — 잡 2개 병렬

| 잡 | 러너 | 하는 일 | 캐시 |
|---|---|---|---|
| `backend` | ubuntu + JDK 17(temurin) | `chmod +x gradlew` → `./gradlew test --no-daemon` | `actions/setup-java`의 gradle 캐시 |
| `frontend` | ubuntu + Node 20 | `npm ci` → `npm test` → `npm run lint` → `npm run build` | `actions/setup-node`의 npm 캐시 |

두 잡은 서로 기다리지 않는다. **백엔드 테스트가 프론트 번들 빌드를 타지 않기 때문**(`build.gradle` 주석 ·
`02_아키텍처.md`)에 완전 분리가 안전하다.

- **시크릿이 필요 없다.** 테스트는 H2 인메모리이고, `src/test/resources/application.yml`이 DB·OAuth·JWT를
  전부 테스트값으로 덮는다(classpath 우선). 운영 yml의 `${KAKAO_CLIENT_ID}` 류는 테스트에서 아예 해석되지 않는다.
  → **`.env` 없는 클린 체크아웃에서 도는 것을 확인했다.** CI에 시크릿을 등록하지 말 것.
- `gradlew`는 git 인덱스에 비실행(100644)으로 들어 있어 리눅스 러너에서 `chmod +x`가 필요하다. 지우지 말 것.
- Node 20은 `Dockerfile` 빌더 스테이지(`setup_20.x`)와 맞춘 것이다 — **배포에서 실제로 빌드되는 런타임**과
  같은 메이저로 검증한다. (로컬 개발기는 24.x)

### 9-3. lint는 정식 게이트다 ✅

`npm run lint`가 실패하면 **CI가 실패한다** — `ci.yml`의 `Lint` 스텝에 `continue-on-error`가 없다.

승격 이력: 도입 시점엔 `AuthContext.jsx`의 `react-refresh/only-export-components` error 1건이 기왕증으로
남아 `continue-on-error: true`로 두었으나, `useAuth` 훅을 **`context/authStore.js`로 분리해 해소**했다(error 0).

> 경고 3건은 `react-hooks/exhaustive-deps`로 원래 warning이라 실패 요인이 아니다.
> ⚠️ `ci.yml`에 남아 있는 `continue-on-error: true`는 **테스트 실패 시 JUnit 리포트를 다시 만드는 스텝**의 것이다 — lint와 무관하다.

### 9-4. 실패하면 어디를 보나

| 증상 | 볼 곳 |
|---|---|
| `backend` 빨강 | 실행 화면 → **Artifacts → `backend-test-results`** 다운로드 → `reports/tests/test/index.html` 열면 실패 테스트·스택트레이스 목록. XML은 `test-results/test/*.xml` |
| `frontend` 빨강 | `Test` 스텝 로그에 실패 파일·케이스가 그대로 찍힌다. 추가로 **Artifacts → `frontend-test-results`**(실패했을 때만 JUnit XML로 한 번 더 돌려 올린다) |
| `Lint` 스텝만 주황 | 잡은 통과다. §9-3의 기왕증이면 무시, **새로 늘어났으면 frontend-dev에게 넘긴다** |
| `Build` 빨강 | 번들이 안 만들어진다 = **배포도 깨진다.** 배포 금지 |

재현은 로컬에서 CI와 같은 명령으로:

```
./gradlew test
cd frontend && npm ci && npm test && npm run lint && npm run build
```

### 9-5. CI가 커버하지 못하는 것

CI는 **테스트만** 돌린다. 아래는 여전히 사람이 확인한다.

- 운영 시드 적재(§1) — CI가 대신해 주지 않는다. **배포 전 필수.**
- Docker 이미지 빌드·기동, OAuth 웹 흐름, 실제 버킷 연동, 정적 서빙(§7)
- qa 판정 — CI 초록은 "테스트가 통과했다"일 뿐, **qa 통과와 같지 않다.**
